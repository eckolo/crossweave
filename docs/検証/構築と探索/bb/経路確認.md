# BB1 — C初踏破前の購入経路の読取り確認

入力基点: `7b288fe2df44ceabb598de4e90e97f80407f865e`。対象は既存AU結果の読取りと既存純関数による診断。**新戦闘0、戦闘再実行0**。

初帰還4状態はいずれも4ptの購入資金がない。既存AUの初帰還からA/Bへ進む枝には、C初踏破前に購入資金を作れる第二帰還がある。反対側へ進む4枝を同じ母集団として残すと、全て未使用3pt・既払PS02 2ptで、明示返還後は4ptの購入資金が足りる。購入個体が既存C用札選択に入る候補は純計算上2枝、見送りは2枝である。C戦績や購入の有効性を示す結果ではない。

## 証拠の区別

| 項目 | この確認で用いたもの | 証拠としての範囲 |

以下は全てAU `paired` の `first_clear`、`progress_first`、`use_owned`。初帰還からの派生結果で、互いの報酬は合算しない。未使用額は第二帰還の領収処理直後、追加習得・購入・売却前の値。全枝で既払習得はPS02の2pt、無料返還可能額も2pt、Cは未踏破。

## 反対側へ進む4入口の候補と採用診断

全4入口とも返還購入なら `未使用3 + PS02返還2 − 購入4 = 未使用1pt`、習得なし。各心得の基礎習得は2ptなので、購入心得をこの残額から装備可能にできない。

| 第二帰還状態ID | 純生成候補：choice順、AO1省略 | 純計算による判断 |
|---|---|---|
| `0-A-first_clear-B-progress_first-use_owned` | `passive:PS04`、`passive:PS03:focused_B`、`passive:PS01`、`passive:PS03` | 全て心得。返還購入後は基礎習得資金がなく見送り |
| `0-B-first_clear-A-progress_first-use_owned` | `passive:PS02:swift`、`card:brace:light`、`card:r`、`passive:PS03:forceful` | `choice-1` の購入 `brace:light` 個体がC用札に選ばれる |
| `8-A-first_clear-B-progress_first-use_owned` | `card:read:sturdy`、`passive:PS03`、`passive:PS01:borrowed`、`card:sweep` | `choice-0` の購入 `read:sturdy` 個体がC用札に選ばれる |
| `8-B-first_clear-A-progress_first-use_owned` | `card:salve`、`card:stored`、`passive:PS02` | 通常札の購入個体は選ばれず、心得も基礎未習得となるため見送り |

`8-B→A` の通常 `salve` は既存方策の修飾付き初期札置換の対象外。通常 `stored` は既存所持と同性能で、既存のAP UID個体が選ばれる。`0-B→A` の通常 `r` と `8-A→B` の通常 `sweep` も購入個体が選ばれない。これらは好みや戦闘評価ではなく既存選択規則の帰結である。

購入候補採用あり2入口と見送り2入口を同じ4入口に残せる。総額5ptの基礎優先準備ならPS02・PS03に計4ptを支払い未使用1pt、候補購入成立時は明示返還後の購入で未使用1pt・習得なしとなる。次のC seedはoffset 0が2、offset 8が10。これらは比較の入口候補の整理であり、BBではC探索を実行していない。

AU `paired` の出力には第二帰還の領収書・準備・境界・戦績があるが、完全保存状態やそのハッシュがない。購入後Cを比較するには、別作業で既存経過を復元し、該当第二帰還結果との照合、保存状態と実オファーの固定を行う必要がある。BBの候補純生成結果を、その照合済み状態の代わりにはしない。

## 再集計

リポジトリ直下で `node docs/検証/構築と探索/bb/aggregate.cjs` を実行すると、BB内の `results.json` だけを書き出す。既存結果・既存コードは編集しない。`--check` 付きでは再計算結果と保存済みJSONの一致だけを検査し、ファイルを書かない。

コードが呼ぶ処理は既存JSON読取り、入力ハッシュ、静的設定・blueprint参照、候補の純生成、領収UIDからの札選択の純計算である。AUの `study.cjs` は実行せず、Sessionも作らない。AUモジュールの読込みに伴う既存AR commonのPython呼出しは乱数入力列の生成だけであり、戦闘を行わない。

`results.json` は `first_returns` 4件、`ab_branches` 8件、`opposite_route_entries` 4件を保存する。各入口の `generated_offer` に文脈と完全な候補列、`candidate_checks` に候補ごとの仮UIDと純計算の採否を持つ。`selected_candidate_id` / `selected_candidate_key` は採用候補がなければ `null`。入力ハッシュも同ファイルにある。

根拠: `au/results.json`・`au/study.cjs`・`au/session.cjs`、`../../資源用途/at/offers.cjs`、`../../装備制限/ar/session.cjs`、`../../装備制限/aq/equipment.cjs`、`ba/results.json`。BBの作成物は本書・`aggregate.cjs`・`results.json` の3ファイル。
