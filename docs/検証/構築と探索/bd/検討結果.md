2026-09-12。入力基点 `002804daa8942c3faedb7b85d70152015f220c11`。基本設計0.53・D53は据置。[条件](conditions.json)を先に保存し、[BC完全保存4入口](../bc/checkpoints-manifest.json)と保存済み8準備結果だけを使った。新戦闘0、BC・BA等の旧比較再実行0。

## 判断と範囲

現在の帰還・拠点状態と、人が明示した「残す習得・取消基礎・候補・次準備」から、購入・返還・習得・所持・装備・札組の前後差を読み取り専用データにできた。[preview.cjs](preview.cjs)は既存APIをコピー上で呼び、表示項目だけを新規構成して返す。保存への適用関数、候補選択AI、出発・戦闘・新画面は作っていない。

BCの8準備について、実装備、未順序の実札組、現在・候補検討時・取消後・購入直前・購入後・準備後の経済と習得支払が一致した。購入2対と見送り2対を区別し、同じ最終残額でもその前に行った操作と時点を残した。これは共通UI接続用の仮データ契約であり、人の理解・任意選択のしやすさ・楽しさの評価、正式ルール採用ではない。

## UIへ渡す境界

公開関数は `inspect(snapshot)` と `preview(snapshot, plan)` の2つ。`inspect` は現在の未使用、既払、習得、装備、所持、実札組と、実候補の価格・現在の金額上可否、選べる無料札・基礎習得候補を返す。最初にこれを使って人の明示計画を作る。

`preview` の入力例は次の形になる。装備・札組は全体を明示し、札組中の同じ無料札は必要枚数だけ繰り返す。`owned-N` は当該入力に対する所持handle、`$purchase` はこの計画の購入個体、`base:…` は既存の無料札または習得済み基礎からの選択肢。

```js
{
  retain_learning: [],
  cancel_learning: ['PS02'],
  candidate: 'choice-1',
  purchase_timing: 'before_preparation',
  next_preparation: {
    learn: [],
    equipment: [],
    deck: [/* inspectのhandleによる12枚。購入札を使う位置は'$purchase' */]
  }
}
```

| 入出力 | 意味・制約 |
|---|---|
| `retain_learning` / `cancel_learning` | 現在の既習得を重複なく全て二分する。省略した基礎を暗黙取消にしない |
| `candidate` | 現在の実候補IDまたは `null`。候補選択・順位付けは行わない |
| `purchase_timing` | `before_preparation` は取消→購入→次準備、`after_preparation` は取消→次準備→購入。後者で未購入の `$purchase` を先に装備・札組へ入れる計画は拒否する |
| `next_preparation.learn` | 取消後に残る習得への明示的な追加だけ。取消した基礎の再習得も指定でき、実返還と再支払を別記する |
| `current` / `prepared` | 未使用と既払を別フィールドで表示。現在・準備後の習得、装備、所持、未順序札組も分離する |
| `candidate_consideration` | 返還購入側は取消・準備前、基礎優先側は準備後の経済。取消後の購入直前残額へ置き換えない |
| `stages` | 取消後、購入直前、購入後、準備後の経済。既払を今すぐ使える残額へ合算しない |
| `cancellation` / `learning` | 明示取消基礎、実返還額、取消で外れる装備、維持・新規・再習得・最終的な習得喪失、実支払 |
| `purchase` | 候補・実価格・購入直前残額・コピー上の購入有無・実準備への採用有無。見送りは `requested:null` であり購入禁止ではない |
| `owned` | 所有の維持と、習得条件による装備可否、現在/準備後の選択有無を別記。`eligible` は基礎と所有の条件であり、残容量へ無条件に追加できる意味ではない |
| `equipment` / `differences.equipment` | 実装備、各コスト、容量8、使用量・残量・合法性、追加・削除handle |
| `deck` / `differences.deck` | 所持個体・無料札ごとの構成数、総12枚・同基礎2枚、基礎別枚数、実追加・削除。配列は表示順であり山札順ではない |
| 拒否時 | `ok:false`、拒否段階とコード、現在の公開情報。購入不足なら価格・購入直前残額・不足額も返す。部分適用用のコピー状態は返さない |

返還は `Q.learn` の履歴上の支払を使い、2ptを定数で返さない。購入は `M.purchase`、習得と装備は `Q.learn/Q.equip`、札組は `U.canonical/U.assess` をそのまま使う。自動準備 `AR.equipForRoute/U.chooseDeck` は、BCの固定方策を**照合用の明示計画へ写すstudy内だけ**で使い、公開moduleには置かない。BAの候補コピー評価を読んだが、候補順位や「固定方策で選ばれないなら買わない」という判断を取り込んでいない。

handleは入力snapshotごとの局所参照であり、保存を跨ぐ恒久IDではない。新しい状態を取得したら `inspect` から作り直す。元所持の生UID・探索タグ・出所主体は表示に出さない。`$purchase` はコピー上でのみ存在し、保存への適用権限や永続IDを表さない。

## 非表示と保存の境界

表示出力はallowlistの公開項目から作り、seed・乱数・相手私有札・過去/未来の山札順・過去の勝敗・行動列・隠し状態・元snapshot・保存ハッシュを含まない。`game/bundle/active/nextRun/stats/receipts` および過去の知識/探索記録を変更しても公開出力は同じだった。現在の実AT候補は既存 `M.view` の保存整合性検証を通して読み、生成文脈は返さない。これは過去ゲーム全文の合法性を再検証する保存ローダーではなく、固定BCハッシュと現在の拠点API検証を入口にした表示adapterである。

[results.json](results.json)には照合用の入口ID、明示計画、各 `display_data` と境界例を保存した。**UIへ渡すのは `display_data` だけ**であり、その外側の入口ID・BC参照・検証メタデータを表示payloadへ混ぜない。完全snapshotは一切複製せず、BCのパス・JSON位置・SHA-256だけを参照する。[verification.json](verification.json)に既存入力と今回の成果のハッシュを保持した。

今回作ったものはこのディレクトリ内の条件・preview・study・results・verification・本報告の6ファイル。UI原本・旧runtime・旧成果・基本設計を変更せず、保存へ適用するruntime、人評価、推奨方策の製品採用は次の仕事にも自動的に含めない。
