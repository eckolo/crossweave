# RD-PACK-02 配布処理を読む

入口は `apps/crossweave-godot/README.md`。本書のパスはリポジトリルート相対。C#に慣れていてGodotが初めての人を想定する。

## 何を配るか

C#のソースやsolutionを渡すだけでは遊べない。C#をコンパイルした本編・保存・画面DLL、それを動かす.NET runtime、画面と入力を扱うGodot実行体、Godotが読むscene・フォント・画像、本編が読むJSONを一緒にする。利用者は `Crossweave.exe` を起動するだけでよい。

| 仕組み | この構成での仕事 | 主なファイル・所有者 |
|---|---|---|
| Godot標準 | scene・Control・描画・入力、export templates、PCKへ資源梱包、user://の解決 | `apps/crossweave-godot/Godot/project.godot`、`apps/crossweave-godot/Godot/export_presets.cfg` |
| C#／.NET標準 | コンパイル・DLL・runtime、JSON、ファイル、Process、SHA-256 | `apps/crossweave-godot/Godot/Crossweave.Proof.csproj`、`apps/crossweave-godot/Directory.Build.props` |
| Python標準ライブラリ | 子プロセス起動、ZIP生成・展開、hash、JSON、ファイルコピー | `apps/crossweave-godot/packaging/m1/build.py`、`apps/crossweave-godot/packaging/m1/verify.py`。生成・確認する側だけに必要 |
| 本作独自 | 固定版・一意版名、全payload一覧、差替え検査、通常／隔離保存の区別、提出記録 | 同上、`apps/crossweave-godot/Godot/Application/PackageEvidence.cs` |
| 既存本編 | GameApplicationの規則、FileGameSessionの保存境界、GameScreenの表示と操作 | `apps/crossweave-godot/Core/Application/GameApplication.cs`、`apps/crossweave-godot/Infrastructure/Application/FileGameSession.cs`、`apps/crossweave-godot/Godot/Application/GameScreen.cs`。今回変更しない |

.NET SDKは開発用、runtimeは実行用。ZIPにはruntimeを含むので利用者にSDKを要求しない。内部assembly名のCrossweave.Proofは既存のままでも、通常sceneはMain.tscn→AppEntry→GameScreenで本編を開く。exe名だけをCrossweave.exeにして既存の参照を無用に変えない。

## 読む順と制御の流れ

1. `apps/crossweave-godot/packaging/bootstrap.py` と `apps/crossweave-godot/packaging/toolchain.lock.json`。既存の固定URL・hash照合でSDK／engine／templates／日本語フォントを取得する。新版を自動追従しない。既存の生成関数を共用し、旧proof検査は変更しない。
2. `apps/crossweave-godot/packaging/m1/build.py` の `main`。清潔なGit checkoutを確認し、SDK・Godot・フォントの版とhash→既存72試験→Debug restore/build→Godot import→ExportRelease/win-x64のlockでrestore→export→開発用restoreと進む。`run` は終了コードだけでなくGodotのERRORも拒否し、工程別ログを残す。
3. 同ファイルのexport後。毎回空の新規ディレクトリーを使い、exe・PCK・本編DLL・CLR・CoreLibの存在を確認する。ライセンス・案内をコピーし、資源入力と全payloadのhashをmanifestに記録する。最後に再度Git差分を拒否する。exportによるprojectやlockの自動変更を「固定SHAの成果」と偽らない。
4. 同ファイルのZIP化。manifestは自分自身のhashを持たず、ZIP外のdelivery.jsonがmanifestと完成ZIP全体を同定する。完成後は一切再梱包せず、確認結果は同じZIP hashを参照する別のverification.jsonへ書く。24MiB分割は転送のためで、連結すると元ZIPの完全なバイト列になる。
5. `apps/crossweave-godot/packaging/m1/verify.py`。完成ZIPのhash→安全な展開先→内容一覧・全ファイルhashを確認し、その中のexeだけを起動する。実行cwdを展開先にし、PATHをWindowsシステムディレクトリーだけにする。これは「CIからSDKが消えた」という意味ではない。
6. `apps/crossweave-godot/Godot/Application/PackageEvidence.cs`。隔離検査時だけCLR／CoreLib／Core assemblyの実ロード先、PCKからの画像・日本語glyph、Core埋込JSONのhashを返す。Python側は実ロード先が展開フォルダー内か照合する。単にDLLファイルがあることより強い実行証拠を残す。
7. `apps/crossweave-godot/Godot/Application/UiAutomation.cs`。既存のGodot実Controlへ合成InputEventを送り、本編FileGameSessionを実行する。今回足したのは明示fixtureパスと配布差替えのcheckpoint／resume。fixtureはZIP外の試験入力であり通常起動のデータではない。通常起動で `--ui-check` が無ければ検査クラスを生成しない。
8. `.github/workflows/rd-pack-02.yml`。完全checkoutで上記入口を順に実行し、ZIPとログを保存する。アップロード成功・headless成功だけでは合格にせず、検査結果と画面画像を読む。

## 保存先が実行物の隣ではない理由

`res://` はアプリ資源で、配布時は主にPCK内にある。ここへ保存すると展開先権限や上書き更新に依存する。`user://` はOSのユーザー領域で、custom_user_dir=crossweaveを継承する。通常は `%APPDATA%\crossweave\saves\local\m1.json`。実行フォルダーを入れ替えても同じユーザーの保存を読める。

検査だけは `user://proofs/d04b-ui-save-01/<一意slot>/m1.json` に置く。通常ユーザーの保存を汚さず、同じFileGameSession／保存v1を検査する。通常保存先の解決が変わっていないことも別に照合する。利用者に検査slotやfixtureの操作は要求しない。

入替確認は自然初回の代表一巡・取得編成・再出発後、全DTOを読み取り専用で控える→終了→同じZIPを別フォルダーへ展開→同じslotを別プロセスで開く→全DTO一致→次の通常命令と保存内容を純Coreの期待結果へ照合、という順。乱数状態・所持・編成・進行・精算済み情報を含み、単なる残高比較ではない。将来の異なる保存形式・別版の移行試験は後続になる。

## 読むときに区別する点

- Core／保存形式／画面操作意図は受領済み原本。今回の変更は配布境界だけで、旧JSや仮素材・固定試験を捨てない。
- C#のawaitはGodotフレームや保存待機を進める。UiAutomationのマウスイベントは実Controlの経路を通るが、実マウスを動かした証拠ではない。
- Windows Server CIのANGLEソフトウェア描画や音デバイス欠落は、その環境の記録として扱う。Windows11・GPU・DPI・音・反応の受入は同梱確認票へ残す。
- 途中エラーは工程ログとverificationのfailedへ残す。修正後は新しいソースSHAでZIPを生成し直し、完成ZIP確認をやり直す。失敗した版を成功した版と同一視しない。
- 本編には現状音声プレーヤーがない。音出力だけ必要な場合は旧proofの診断音を使い、旧代表盤面の全項目を無条件に再確認しない。
