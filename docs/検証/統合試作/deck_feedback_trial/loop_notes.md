# 自作構築・精算・次探索の接続：AE1

2026-09-09 UTC。基本設計0.42の採用済み方針を使う別試験。UI-R-001／PT-Z-001の画面・入力を差し替えない。操作画面と製品の保存基盤は未接続。

## 目的と仮プロフィール

本人が札を選び、成果を持ち帰り、次の出発に使うための入力と処理を用意する。手動の成長配分と自動適用の方式判断の前に、同じ精算から具体的な次状態を比較できるようにした。構築・戦術の優劣や面白さの実証ではない。

- 開始元コミット：`968e9e68c7f323558d8fe7255930207ec2903790`。参照ファイルのSHA-256は`loop_results.json`。
- 12枚、同一札2枚まで。属性比は固定しない。これは試行制約で、製品の枚数・同名上限の決定ではない。最初の10種類で合法な枚数配分は6,765通り。強い構築数・有意味な選択数ではなく順序を区別しない枚数ベクトル数。
- 初期解放：牽制、重撃、踏み込み、小突き、防御、受け流し、速撃、見切り、打ち払い、回復草。既存3構成で使う札を保持する。弱札・補填札や未解放の札は選択集合に入れない。
- 新規の札効果は追加しない。性能は現在のZでの補正適用後を使用。回復草は回復16・期限16の消費型。未ドロー／手札・場・回収山の借り札は恒久解放へ変換しない。

| 取得元 | 仮の成果 | 同じ札を解放済みの場合 |
|---|---|---|
| 大岩R | 溜め打ちを解放 | 成長点1 |
| 最初の環境T0 | 踏ん張りを解放 | 成長点1 |
| 敵E | 鋭撃を解放 | 成長点1 |
| 後続環境T1 | 成長点1 | 同じ |

T0を旧案の見切りから踏ん張りへ、T1を初期利用可能な打ち払いから成長点へ変え、最初から使える札を新規解放と呼ぶ不整合を除いた。仮の報酬表であり、獲得意欲の評価・正式採用ではない。報酬の具体内容を初見の出発時から全公開しない。`preparation`は解放済み札と既に知る情報だけを返す。

## 成長方式の比較用入力

| 方式 | 仮の操作と次状態 |
|---|---|
| 選択する | 帰還後に成長点を保持。3点で最大HP+2、または3点で常時軽減+1を選べる。使わずに残すこともできる |
| 自動適用 | 精算後に累積3点ごとに最大HP+2へ自動反映。端数を保持 |

自動側のHPのみ、両強化の同一価格は接続確認用の具体例である。選択方式では常時軽減以外の能力も設計候補になり得る。常時軽減+1は弱い攻撃を0ダメージへ寄せ、防御札の価値も変え得るため、その強化自体を推奨・採用しない。方式選択と能力項目・費用・上限・振り直しの決定は別。

## 再現と機能の境界

```sh
node docs/検証/統合試作/deck_feedback_trial/loop_study.cjs
```

Node.js／Python 3の標準機能のみ。新しい`loop_results.json`を再生成する。旧Z/AA/AB/AC/AD結果を更新しない。

| 関数 | 入力 → 出力・境界 |
|---|---|
| `initialProfile(mode)` | 比較方式 → 未経験・初期10種類解放・成長0の拠点プロフィール |
| `catalog(source)` | 固定入力 → Zの補正適用後の札面。手札・札順・相手の現在札は取得しない |
| `validateDeck(counts, profile, cards)` | 札種と枚数 → 合計・属性・役割。未知／未解放／不正枚数／合計違いを拒否 |
| `preparation(...)` | プロフィールと粗い案内 → 解放札・構築制約・成長の選択肢・公開済み知識。未確認の報酬一覧は含めない |
| `depart(source, input, profile, counts, runId)` | 拠点状態・固定乱数入力・構築 → 探索中プロフィール、bundle、既存`T.Game`。キー順で札順を選べないよう札種順を正規化してからシャッフル |
| `finish(profile, runId, game, knowledge)` | 既存ゲームの精算とD42で記録した知識 → 拠点プロフィール。持帰り分だけ解放・加点、知識はD41で保持。二重帰還は再加算しない |
| `buy(profile, purchaseId, kind)` | 帰還後プロフィール・購入識別子・候補 → 次回出発用の強化。探索中・残高不足・同一IDの矛盾を拒否 |

`loop_study.cjs`の観測アダプターは公開使用・遭遇・処理済み攻略・獲得した報酬を既存`knowledge.js`へ渡し、開示方式をD42の`first_resolution`に固定する。初期構成は固定プロフィールから与え、現在の相手の私有札を開示元にしない。受動効果・材料由来等を網羅した製品用観測器ではない。

`finish`や`buy`は入力を複製して結果を返す。呼出側は返されたプロフィールを次操作に使う。JSONによるローカル受渡しを前提とし、複数端末・同時操作・破損ファイルを含む製品の永続化や認証は対象外。

## 確認結果と限界

1. 初期合法構築3例、不正5例、報酬解放3種と初期集合の非重複、同じ枚数配分の入力キー順による開始状態の不変を確認した。
2. 人工的な精算条件4件で、未保護撤退／保護済み撤退／死亡／クリアを確認した。成長は人工的な重複報酬3点のプロフィールで、温存・HP・軽減・自動の4通りを次探索へ接続した。自然に3点を獲得した実績ではない。
3. 先に固定したZ系列seed0→1、2成長方式×3方策×2探索の12経過。共通の初期構築と同じ公開情報方策を使用した。成長方式2案で同じ経過になるため、独立した12種類の戦闘標本ではない。
4. 最後まで進む岩優先／環境優先の計8経過はすべて死亡、持帰りなし。両方式の各4経過は同一であり、成長方式の攻略性能差を測れない。自作構築の札種正規化で元Zとは初期札とIDの対応が変わるため、元Zの同seedとの一要因比較にも使わない。
5. その不足を受け、seedは変えず、環境踏破の処理が完了した境界で帰還する方策を追加した。両方式で1回目はP5手でT0を持帰り、踏ん張りを解放。次回は踏み込み1枚と交換し、seed1でP34手死亡した。前回解放と環境の構成知識は保持した。新しい札を入れたことの有利不利は、この比較からは判定しない。AIの交換方針を本人の意図とは扱わない。
6. 12終端で帰還時に元のゲームが不変、JSON読み戻し後の同帰還の再実行が不変。P5手後の保存を取れた10経過は残りの戦闘を復元して終端一致（P5手で終了した2件は対象外）。購入の再実行と同IDの内容矛盾、未精算入力、探索中購入も確認した。
7. D42について、生存退場では開示せず、他主体が敵を撃破した後に死亡しても開示を保持する2条件を確認。既存ADの網羅比較を再実行・再計数しない。

この結果は、成果の持帰り・構築変更・異なる札順での次探索を処理として接続できたことを示す。人が何を欲しがるか、成長速度、浅い反復の優劣、自由構築の納得感、UIの読みやすさは未評価。次の人試験はUI担当の成果を確認し、別IDと固定条件で構築操作・終了後の選択へ接続してから提示する。
