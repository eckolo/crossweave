# 画面解像度・表示密度の基準

2026-09-25（日本時間）／Work `20260910-ui-readability`。

状態：**Steam想定の1920×1080をUI設計の基本として採用**（2026-09-25ユーザー指示）。この基準の操作サンプルを依頼され、[横並び版 `two-stage-ui-5.1`](co-u02/acquisition-preview/README.md)で「取得可能／所持／編成」を表示。2026-09-25に画面構造のユーザー了承を受領した。実機確認は別。スマホ向け配置とその他の確認解像度は参考案として保持し、今回のサンプル作成の前提条件にしない。

## 見直し前の寸法と問題

前版の二段階取得UI `two-stage-ui-4` は、容量を **1024×576 CSS px** で検討していた。`acquisition-preview/structure.css` の外枠上限は1280px、ゲーム部分は16:9なので最大1280×720。実際は親の表示幅へ合わせるため、幅736pxならゲーム部分は736×414になる。会話内の個々の表示幅は実測していない。

枠は212×48 CSS px、名称12px、主要操作44×44px、項目間隔2px。1024×576に候補4件・手元20種類・編成12枚を収めるため、3領域を縦に積んでいた。提示枠の狭さを設計基準に持ち込み、容量を優先して間隔を詰めたことが、窮屈さと上下移動の要因という判断である。これは数値・構造からの推定で、実ブラウザーでの知覚評価ではない。

この寸法は前版の操作案についての値。旧UI0.13や探索画面には別の最大幅・最低高があり、プロジェクト全体が一つの正式な対応解像度へ統一済みだったわけではない。

## 外部の根拠

公式資料を2026-09-25に確認した。画面解像度の利用比率は、ゲーム内UIの標準寸法を意味しない。

| 根拠 | 確認できたこと | 設計への使い方 |
|---|---|---|
| [Steam Hardware & Software Survey](https://store.steampowered.com/hwsurvey/)・2026年8月 | 主ディスプレイ1920×1080が50.52%、2560×1440が21.86% | PCの主設計は1920×1080が妥当という判断。全利用者・全ゲームの強制規格ではない |
| [Steamworks・互換性審査](https://partner.steamgames.com/doc/steamhardware/compat) | Steam Deckでは1280×800を優先し、1280×720も推奨。文字は1280×800時の最小9px、可能なら12pxを推奨 | 1280×720での縮小・可読性確認を残す。9pxを今回の文字設計の目標にしない |
| [Android・画素密度](https://developer.android.com/training/multiscreen/screendensities) | UIの大きさはdp、文字はspで扱う。物理pxと別 | スマホの高い画素数を、そのまま情報を置ける広さとして扱わない |
| [Android・多様な画面](https://developer.android.com/games/develop/all-screens) | ゲームも画面比率・ウィンドウサイズへ対応する必要がある | スマホを単一の物理解像度で固定しない |
| [Google Pixel・端末仕様](https://support.google.com/pixelphone/answer/7158570?hl=en) | Pixel 9の例では1080×2424、20:9表記 | 横長の端末を含める根拠の一例。スマホ全体の最多解像度とはしない |
| [Apple・UI Design Dos and Don’ts](https://developer.apple.com/design/tips/)／[Android・アクセシビリティ](https://developer.android.com/guide/topics/ui/accessibility/apps) | タップ領域の目安はApple 44×44pt、Android 48×48dp | スマホの確認では実効タップ領域を確保。44物理pxや48物理pxとは区別する |

## 採用基準と補助確認案

| 対象 | 基準 | 扱い |
|---|---|---|
| PC・Steamの主設計 | **1920×1080、16:9** | ゲームの描画領域の制作基準。OSのタイトルバー等は含めない。文字・枠・余白をこの広さで設計する |
| 小さいPCウィンドウ・Deck | **1280×720**、Deckの外画面は1280×800 | 主操作が全て届く縮小確認点。16:9部分は1280×720として扱える。文字・操作を縮め続けず、必要ならUI表示倍率と配置を調整する |
| 高解像度PC | 2560×1440／3840×2160 | 基準から鮮明に描画し、表示倍率を選べる方向。解像度だけで項目数を際限なく増やさない |
| スマホ横持ち | 短辺360〜430程度の論理表示高を検証対象にする。横長の外画面例は800×360／960×432 | 本案の検証サイズであり市場の最多値ではない。セーフエリア・OSの表示倍率・実効タップ領域を別に確認する |

制作基準の1920×1080は、全端末で1920 CSS pxを確保する指定ではない。実出力の画素数、OSの倍率、アプリの利用可能領域、UI倍率を区別する。Webで確認するときはCSS viewportとdevicePixelRatioも記録する。

既に了承された**ゲーム外枠16:9**と、ゲーム全体を縦スクロールさせない原則は維持する。20:9等はスマホの外画面を確認する値で、16:9のゲーム画面を黙って20:9へ変更する決定ではない。例えば800×360の外画面に16:9を収めると、セーフエリア控除前でもゲーム部分は640×360となる。スマホ側ではPCと同じ件数が無条件に一画面へ収まるとは約束しない。

スマホの文字・タッチ対象は論理寸法で確保し、PC用の画面全体を単純縮小して済ませない。ゲーム上の取得・編成・取消・確定の意味は端末で変えず、列数・余白・同時表示件数を調整する。具体的なスマホ配置と対応下限は操作画面で評価する残件。

## 横並びの方針

- 取得可能を左、所持を中央、編成を右へ置き、取得から編成までを主に横方向へ移動できるようにする。ユーザーの操作上の希望として扱い、人間全般に横ドラッグが優位という研究結果にはしない。
- 各領域の幅は同じにする必要はない。少数の候補は狭く、手元を広く、編成には12枚を見渡せる幅を割り当てる。同じ札・心得の枠寸法は全領域・移動中で統一する。
- 最大25文字の名称、主要操作、数量・状態印を基準に枠を決める。解像度を上げた分をそのまま枠の拡大だけに使わず、文字の読みやすさ・領域間の余白・一覧容量へ分けて使う。
- 通常件数の検証目標「候補4件・手元20種類・編成12枚」は継承する。新配置での同時表示容量は再計算する。これは所持上限や実際の通常所持数を確定した値ではない。
- 会話内の縮小提示と、ゲーム本来の想定サイズを明示して分ける。縮小版だけで文字サイズ・指での扱いやすさが合格したとは判定しない。

## 成果と残件

1920×1080固定の横並び操作サンプル `two-stage-ui-5` を作成。5.1で指定見出しを反映。取得可能1列・所持2列・編成2列、共通枠352×80、名称20pxの2行。候補4件・手元20種類・編成12枚の容量を限定検査で確認した。

会話内の提示では「全体」で縮小率を明示し、「原寸」で1設計pxを1CSS pxとして表示する。1920 CSS px幅を会話枠へ無理に広げず、原寸時は確認用の外側表示をスクロールできる。ゲーム自体の配置・16:9は変えない。

[前版5の20項目の限定確認](co-u02/acquisition-preview/fhd-checks.json)が通過。過去の操作検査は全再実行していない。取得・編成の意味と入力数量は維持した。

1920×1080の基準と取得・編成の画面は了承済み。名称修正は[限定読戻し](co-u02/acquisition-preview/labels-check.json)で確認した。続行指示を受け、[探索画面のFHD調整](co-u02/journey/full-hd.md)をUI0.14.0へ実装。通常外枠・盤面・手札・人物・予測・窓とドラッグ座標を揃え、前後遷移を含む変更26項目を確認した。探索FHDを登録のみ・未着手の状態へ戻さない。

実ブラウザー描画・フォント実測・実ポインター・タッチ・IndexedDBは未確認。[二段階取得の本編接続](co-u02/acquisition-preview/integration-handoff.md)、所持数の長期分布も残件として保持する。共通外枠のFHD化で、旧本編の取得方式まで統一管理へ変わったとは扱わない。
