状態：**全30項目＋条件待ち4候補の機能要件整理案。画面配置・演出・文言は未決定。今回の画面実装・再提示は行わない。**

## 1. 今回の要求と整理範囲

ユーザーは、状態を丁寧な文章で説明する表示から、対象と「どうなったか」がすぐ分かる表示へ改めるよう指示した。これは帰還結果だけでなく全画面に適用する。獲得品と短いテロップの例は、伝える内容の簡潔さを示す例であり、大きな「獲得！」表示や派手な演出の採用ではない。

前回の回答では帰還結果について役割・表示・更新・移動先を整理したが、具体的な分離案はまだ承認されていない。今回はその4観点に、**きっかけ／対象の変化／変化後に残す表示**を加えて全体を洗い出す。既存の[UI検討](UI検討.md)のIDを維持する。30項目には窓・通知・共通状態が含まれ、独立した画面を30枚作る意味ではない。

全画面の機能を洗い出す今回の明示指示を、CO-U02の表示改善に先行する文書作業として受領した。既存の実接続・保存コード、正式探索UI-R-002 v0.15、UI-F／UI-G、PT-Z／PT-NTの固定原本を維持する。ゲーム規則、共通runtime、保存装置、経済、シナリオ原本の担当は変更しない。

## 2. 全画面で必要な機能

| 観点 | 必要なこと |
|---|---|
| 判断する前 | 次の操作を選ぶために必要な対象・状態・量を見せる。変化のない情報まで常時説明しない |
| 選択した時 | どれを選び、どこへ作用するかを対象同士の位置・輪郭・対応で示す。詳細を見る操作と実行を分ける |
| 確定前 | 費用、増えるもの、減るもの、外れる装備などを該当する対象に結びつける。まだ案であることが分かる表示を保つ |
| 出来事が起きた時 | 対象の移動・出現・退場、数の増減、置き換わり、短い強調で「何がどうなったか」を示す。名称は対象の識別に必要な場所へ置く |
| 変化した後 | 更新後の状態を落ち着いた表示で残す。見逃した差分は詳細・結果一覧・必要な履歴で読み返せるようにする |
| 次の行動 | 操作対象か移動先が分かる入口を置く。「修正する」「次へ」だけでは作用を特定できない場面を点検する |

変化の見せ方は、短い表示の切替や対象付近の増減だけでもよい。全操作に長いアニメーションや確認画面を追加しない。演出を短縮・省略しても、対象・増減・最終状態は把握できる必要がある。色や音だけに意味を預けず、形・位置・数などでも区別する。具体的な演出時間や設定項目は今回確定しない。

所持・装備などの**確定表示は本体の成功応答後**に更新する。操作待ち、下書き、比較、保存中、成功、失敗を区別し、演出の終了を保存や報酬処理の実行条件にしない。同じ結果の開き直しで再加算・再購入・再解放を起こさない。画面の切替で下書きや窓の選択を不用意に失わない。

## 7. 帰還結果の責任と、起きた変化の区別

帰還結果は今回の探索を振り返る場所として、次の分担を提案する。

| 機能 | 帰還結果で扱うこと | 続きの場所 |
|---|---|---|
| 今回の成果 | 対象を一覧として出し、増えた着想と合計を示す。詳細は対象から開く | 所持品、調査記録、選択可能になった対象の一覧 |
| 喪失 | 今回失った対象と量が分かる表示を残す。以前からの所持まで減ったように見せない | 結果内の詳細 |
| 解放・依頼進行 | 変わった対象を短く知らせ、その状態を関連先へ残す | 探索先、心得など該当する一覧 |
| 次の構成を変える | 行き先を用意し、変更の選択・比較は編集側で行う案 | S06〜S12。毎回すべて通らせない |
| 結果を閉じる | 既に精算済みの結果を確認し、拠点へ進む | S03。直接S06へ進む近道の有無は未決定 |

現在のUI-G-001 v0.2は、帰還に「心得を選び直す」と「札を組む」を置いている。CO-U02指示は帰還phaseでの基礎取消比較とack後の意図の再検証を維持するため、**結果の閲覧と編集を分ける提案と、既存の比較機能を削除することは同一ではない**。別窓・移動先への分離、ackの時点、下書き保持を具体化する段階で接続を点検する。今回はコードを変更せず、拠点導線や帰還後の分離を採用済みと扱わない。

説明ラベルを繰り返さず区別するため、変化が落ち着く場所を明確にする。

| 起きたこと | 変化する対象・場所 | 必要な伝達 |
|---|---|---|
| 探索中の循環へ札が入った | 今回の札の領域 | 札と領域の対応。恒久所持への追加と同じ見せ方にしない |
| 撤退に対して成果が保護された | 今回の成果の状態 | 対象の保護状態が変わったこと。帰還時の受取りを先取りしない |
| 札や心得の種類が解放された | 対応する候補・選択肢 | 対象が選択可能になったこと。個体の所持数を勝手に増やさない |
| 候補を取得した | 対象個体の所持と着想 | どの個体が何個増え、いくら使ったか。編成・装備への採用は別の操作 |
| 基礎心得を覚えた／外した | 習得状態と着想、影響する装備 | 対象の変化と支出／返還、外れる装備。探索成果全体の巻戻しとして見せない |
| 札組・装備を変えた | 次回の構成 | 加わったもの・外れたもの。所持個体の消滅と混同しない |

## 8. 条件待ちの4候補

| ID・候補 | 仕様が定まったら必要になる機能 | 今回の扱い |
|---|---|---|
| UI-C01 探索中の地図・進路選択 | 現在地と選べる道、選択で移る先、移動後の位置を対応づける | 経路選択方式が未採用。地図や進路を追加しない |
| UI-C02 素材の利用・加工 | 対象素材、使う数、できる物、実行後の消費と生成を対応づける | 加工・製作・付替え条件待ち。独自レシピを作らない |
| UI-C03 同行・救出の管理 | 誰が同行し、出来事でどう変わり、帰還で何が成立したかを示す | 同行状態と操作条件待ち。枠・料金等を設けない |
| UI-C04 終幕・クリア後 | 何が終わったかと、以後できること・行き先を示す | ゲーム全体の終点と継続条件待ち。個別探索の踏破と混同しない |

## 9. 次の具体化で確かめること

機能要件の整理後に、関連する画面のまとまり・配置・操作を具体化する。今回の資料作成だけで表示や理解しやすさを検証済みとはしない。

1. 対象を選び、実行し、結果を見る一連の操作で、「何がどうなったか」をすぐ言えるか。
2. 未確定の案と確定済みの変化を、金額・所持・装備それぞれで取り違えないか。
3. 演出を見逃した時や短縮した時も、結果を確認して次の操作へ進めるか。
4. 待ち・失敗・再試行で成功表示を先取りせず、選択と下書きが保持されるか。
5. 件数増加・長い名称・1024／736／600／320px・resizeでも、一覧末尾・詳細末尾・主要操作へ届くか。

将来のユーザー確認は従来の3点（画面内に収まり操作できる／準備・比較・確定と帰還後の流れが分かる／現在・案・確定後の金額・所持・装備が分かる）へまとめる。今回は質問や画面の再提示を追加しない。
