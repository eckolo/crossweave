## 1. 今回の要求と整理範囲

ユーザーは、状態を丁寧な文章で説明する表示から、対象と「どうなったか」がすぐ分かる表示へ改めるよう指示した。これは帰還結果だけでなく全画面に適用する。獲得品と短いテロップの例は、伝える内容の簡潔さを示す例であり、大きな「獲得！」表示や派手な演出の採用ではない。

前回の回答では帰還結果について役割・表示・更新・移動先を整理したが、具体的な分離案はまだ承認されていない。今回はその4観点に、**きっかけ／対象の変化／変化後に残す表示**を加えて全体を洗い出す。既存の[UI検討](UI検討.md)のIDを維持する。30項目には窓・通知・共通状態が含まれ、独立した画面を30枚作る意味ではない。

全画面の機能を洗い出す今回の明示指示を、CO-U02の表示改善に先行する文書作業として受領した。既存の実接続・保存コード、正式探索UI-R-002 v0.15、UI-F／UI-G、PT-Z／PT-NTの固定原本を維持する。ゲーム規則、共通runtime、保存装置、経済、シナリオ原本の担当は変更しない。

0.2では、ユーザーの追加指示「心得関連はプレイヤー視点1画面」「札組と心得の円滑な往復」「全般を通した行動チャートに対する操作量の削減」を要件として記録する。機能を別IDで管理していることを、別々の画面へ移動させる理由にしない。習得・所持・装備・取得・変換の機能の違いは維持し、操作の場所をまとめる。

## 2. 全画面で必要な機能

| 観点 | 必要なこと |
|---|---|
| 判断する前 | 次の操作を選ぶために必要な対象・状態・量を見せる。変化のない情報まで常時説明しない |
| 選択した時 | どれを選び、どこへ作用するかを対象同士の位置・輪郭・対応で示す。詳細を見る操作と実行を分ける |
| 確定前 | 費用、増えるもの、減るもの、外れる装備などを該当する対象に結びつける。まだ案であることが分かる表示を保つ |
| 出来事が起きた時 | 対象の移動・出現・退場、数の増減、置き換わり、短い強調で「何がどうなったか」を示す。名称は対象の識別に必要な場所へ置く |
| 変化した後 | 更新後の状態を落ち着いた表示で残す。見逃した差分は詳細・結果一覧・必要な履歴で読み返せるようにする |
| 次の行動 | 操作対象か移動先が分かる入口を置く。「修正する」「次へ」だけでは作用を特定できない場面を点検する |
| 表示枠 | 16:9の主画面はスクロールなし。常時必要な情報と主操作を枠内へ配置し、長文・内訳の小窓のみ縦スクロール可。一覧の全対象へのページ送りと、resize後の位置・選択・下書き保持を確保する |
| 囲いと背景 | 文字枠だけのために専用面積を確保しない。背景への重ね、囲いの縮小・省略で場所感と可読性を両立する。操作対象・選択・押せる入口の識別は保つ |
| 一連の操作量 | プレイヤーの目的と開始地点ごとに完了までの経路を数える。画面往復、タブ切替、窓の開閉、対象の再検索、選択、確定、スクロール、待ちを含めて評価する |

変化の見せ方は、短い表示の切替や対象付近の増減だけでもよい。全操作に長いアニメーションや確認画面を追加しない。演出を短縮・省略しても、対象・増減・最終状態は把握できる必要がある。色や音だけに意味を預けず、形・位置・数などでも区別する。具体的な演出時間や設定項目は今回確定しない。

所持・装備などの**確定表示は本体の成功応答後**に更新する。操作待ち、下書き、比較、保存中、成功、失敗を区別し、演出の終了を保存や報酬処理の実行条件にしない。同じ結果の開き直しで再加算・再購入・再解放を起こさない。画面の切替で下書きや窓の選択を不用意に失わない。

### 4.1 「所持品」が指していたもの

| 対象 | 仕様上の意味 | プレイヤーが扱う場所の案 |
|---|---|---|
| 取得した札 | 修飾のある札、通常の札、同種の重複など、個体と数量を持つ取得物 | 札組の選択元へ含める。そこで性能比較・追加・不要個体の変換を行う |
| 取得した心得 | 基礎の習得状態とは別に持つ、修飾違い・重複を含む心得の個体。基礎条件と装備制限を確認して使う | 心得画面の対象一覧へ含め、基礎の習得と個体選択・装備を同じ場所で扱う |
| 素材 | 基本方針・試行入力に存在する用途限定報酬。具体的な使い道は未決定 | 用途が決まるまで専用の所持・加工画面を新設しない |

初期無料札、札の解放、基礎心得の習得、調査知識を、一律に個数付きの所持品へ変換しない。共通仕様の区別はデータとして維持するが、これらを扱うたびに別画面へ送る必要はない。所持品機能を札組・心得へ内包する案は、前版の独立した所持品一覧を経由する案に優先する。

### 4.2 心得1画面と札組の往復

**受領済み要件**：心得関連はプレイヤー視点で1画面。札組と心得は円滑に行き来できること。全般にプレイヤーの行動経路を基準として操作量を抑えること。

**構成案**：S06〜S12を一つの編成領域にまとめ、札組と心得を直接切り替える。心得側で、基礎の習得・取り直し、所持個体の比較、装備、心得の取得候補、不要個体の変換を扱う。選択対象の詳細や必要な確認は同じ画面内に重ね、別の所持品・購入・装備画面への巡回を要求しない。札側でも同様に、使える札・所持個体・取得候補を用途に沿って扱う。候補は共通本体の同一集合を表示し、札用・心得用に別の抽選や別会計を作らない。

- 札組から心得へ1操作、心得から札組へ1操作を移動の目標とする。切替時の確定操作は0回。
- 画面ごとの選択対象、絞込み、並び、スクロール位置と、共通の変更案を保持する。戻るたびに対象を探し直させない。
- 行き先、使える着想、構成の差分・制限は共通に参照する。同じ金額や説明を画面の各所へ重複表示しない。
- 習得して装備する、候補を取得して札組へ入れる、といった一続きの意思を同じ対象から指定できるようにする。自動で習得・購入・装備を選ばず、本人が選んだ内容を公開プレビューで確認する。
- 対応する変更案は共通の確定操作へまとめる。個体の変換など別の実行境界を持つ操作は、その場で対象・数量・見積を確認して実行する。未対応の複数購入や一括取引をUIだけで追加しない。
- 名前が同じ別個体や失効した候補を選び直した扱いにしない。成功・失敗後も同じ対象を追えるかを公開IDと更新されたviewで確認する。

1画面にまとめることは、全説明・全候補・全操作を同時に敷き詰めることを意味しない。狭い表示でも対象の選択・編成・詳細・確定へ届く構成を比較する。今はタブ等の方式・配置・ボタン名を確定せず、上記を満たす案として記録する。

## 7. 帰還結果の責任と、起きた変化の区別

帰還結果は今回の探索を振り返る場所として、次の分担を提案する。

| 機能 | 帰還結果で扱うこと | 続きの場所 |
|---|---|---|
| 今回の成果 | 対象を一覧として出し、増えた着想と合計を示す。詳細は対象から開く | 所持品、調査記録、選択可能になった対象の一覧 |
| 喪失 | 今回失った対象と量が分かる表示を残す。以前からの所持まで減ったように見せない | 結果内の詳細 |
| 解放・依頼進行 | 変わった対象を短く知らせ、その状態を関連先へ残す | 探索先、心得など該当する一覧 |
| 次の構成を変える | 行き先を用意し、変更の選択・比較は編集側で行う案 | S06〜S12。毎回すべて通らせない |
| 結果を閉じる | 既に精算済みの結果を確認し、次の目的へ進む | S03へ送る。編集と再出発は拠点側で選び、結果との行き来を要求しない |

現在のUI-G-001 v0.2は、帰還に「心得を選び直す」と「札を組む」を置いている。CO-U02指示は帰還phaseでの基礎取消比較とack後の意図の再検証を維持するため、**結果の閲覧と編集を分ける提案と、既存の比較機能を削除することは同一ではない**。別窓・移動先への分離、ackの時点、下書き保持を具体化する段階で接続を点検する。今回はコードを変更せず、拠点導線や帰還後の分離を採用済みと扱わない。

説明ラベルを繰り返さず区別するため、変化が落ち着く場所を明確にする。

| 起きたこと | 変化する対象・場所 | 必要な伝達 |
|---|---|---|
| 探索中の循環へ札が入った | 今回の札の領域 | 札と領域の対応。恒久所持への追加と同じ見せ方にしない |
| 撤退に対して成果が保護された | 今回の成果の状態 | 対象の保護状態が変わったこと。帰還時の受取りを先取りしない |
| 札や心得の種類が解放された | 対応する候補・選択肢 | 対象が選択可能になったこと。個体の所持数を勝手に増やさない |
| 候補を取得した | 対象個体の所持と着想 | どの個体が何個増え、いくら使ったか。編成・装備への採用は別の操作 |
| 基礎心得を覚えた／外した | 習得状態と着想、影響する装備 | 対象の変化と支出／返還、外れる装備。探索成果全体の巻戻しとして見せない |
| 札組・装備を変えた | 次回の構成 | 加わったもの・外れたもの。所持個体の消滅と混同しない |

## 9. 次の具体化で確かめること

機能要件の整理後に、関連する画面のまとまり・配置・操作を具体化する。今回の資料作成だけで表示や理解しやすさを検証済みとはしない。

1. 対象を選び、実行し、結果を見る一連の操作で、「何がどうなったか」をすぐ言えるか。
2. 未確定の案と確定済みの変化を、金額・所持・装備それぞれで取り違えないか。
3. 演出を見逃した時や短縮した時も、結果を確認して次の操作へ進めるか。
4. 待ち・失敗・再試行で成功表示を先取りせず、選択と下書きが保持されるか。
5. 件数増加・長い名称・1024／736／600／320px・resizeでも、一覧末尾・詳細末尾・主要操作へ届くか。

将来のユーザー確認は従来の3点（画面内に収まり操作できる／準備・比較・確定と帰還後の流れが分かる／現在・案・確定後の金額・所持・装備が分かる）へまとめる。今回は質問や画面の再提示を追加しない。

### 9.1 プレイヤーの行動経路と操作量

以下は**設計目標であり、現UIの実測値ではない**。開始地点と目的を固定して比較する。「移動」は画面・タブへの移動、「決定」は保存・購入・出発等の明示操作を指す。内容を選ぶ入力、窓の開閉、スクロール、修正、待ちを別に数え、下表の数字だけを総操作数として報告しない。

| 行動ID・目的／開始地点 | 経路案 | 減らす操作・目標 |
|---|---|---|
| ACT-01 同じ構成・同じ場所へ再出発／帰還結果 | 結果→拠点へ→出発 | 進行2操作。編集・別確認画面への巡回0回。拠点を経る1操作は明確な区切りとして維持 |
| ACT-02 行き先だけ変える／帰還結果 | 拠点へ進み、行き先を選んで出発する | 拠点へ1回、行き先選択1回、出発指示1回を目標。詳細は任意。札組・心得の通過0回 |
| ACT-03 札を入れ替えて出発／帰還結果 | 拠点へ→札組で入替→確定して出発 | 編集まで2操作、内容を選ぶ入力、確定と出発の指示1回。独立した比較画面の通過を必須にしない |
| ACT-04 心得を覚えて装備する／心得画面 | 対象を選び、習得と装備の意図を指定し、同じ場所で差分を確認する | 独立画面への移動0回。習得後の対象の再検索0回。対応する案は共通の確定1回 |
| ACT-05 札組と心得を交互に調整／札組 | 札を変更し、心得へ切替、調整後に札組へ戻る | 往復は切替2操作。切替のための確定0回。下書き・選択・絞込み・位置を保持 |
| ACT-06 候補を比べ、取得して使う／札組または心得 | 同じ画面で候補と現在のものを比べ、取得・使用の意図を指定する | 独立した買い物・所持品・装備画面への往復0回。取得後の対象の再検索0回。実行は提供された取引単位に従う |
| ACT-07 着想の使い道を見直す／心得画面 | 既習得を外す案と、別の習得・候補・装備を同じ場所で比較する | 取消専用画面への移動0回。同じ変更案と残高差を保つ。自動取消・自動購入なし |
| ACT-08 不要個体を変換／札組または心得 | 対象から数量・見積を開き、明示実行後は同じ一覧へ戻る | 別画面への移動0回。対象を別の所持品一覧で選び直さない。個体を失う決定は省略しない |
| ACT-09 今の対象へ札を出す／探索 | 札を選んで出す、または既存のドラッグ操作で出す | 正式UIの最頻操作を維持。毎手の確認窓・全体メニュー経由0回。対象を変える時だけその操作を加える |
| ACT-10 詳細を比べて作業へ戻る／任意の対象一覧 | 対象付近で詳細を開き、比較し、閉じる | 元画面の再読込・再検索0回。選択中の窓から対象を切り替えられることを検討。窓の開閉数も計測する |
| ACT-11 中断地点から続ける／起動 | 続きからを選び、保存地点へ戻る | 状況要約の必須確認0回。複数枠等が必要になった場合の選択数は別に数える |
| ACT-12 保存失敗から同じ操作を再試行／失敗表示 | 案を保持したまま、必要なら原因を直して再試行する | 同じ内容の再入力・再選択0回。単に保存側が復旧した場合は再試行の指示1回 |
| ACT-13 新しい成果の詳細を見て使う／帰還結果・通知 | 対象を開き、対応する札組／心得／記録へ直接移る | 拠点から対象を探し直す経路を省く。解放だけの対象を所持済みとして編成へ入れない |

各案では操作数に加え、探す対象数、スクロール量、戻った時の文脈、処理待ちを記録する。画面移動を減らしても、巨大な一覧を何度も探させる案は改善と扱わない。日常的な再出発、札組・心得の調整、毎手の出札を優先する。不可逆な個体喪失や費用を伴う決定では、結果の判断に必要な表示を残す。

ACT-01〜03の拠点経由と、編成後の確定・出発をまとめる案は、明示されたユーザー操作を本体の順序に沿って処理する接続案。`ack_return`・必要な`commit_preparation`・`depart`はそれぞれ成功を待つ。途中で失敗した場合はそこまでの実状態と未完了の意図を表示し、完了済み処理を再実行しない。新しい一括APIや原子的な巻戻しが存在すると仮定しない。購入・変換等のD03待ちも維持する。今回はこの案を実装したり、目標操作数を達成済みと扱ったりしない。
