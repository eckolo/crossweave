# 予測・詳細窓を開いたまま攻撃できない不具合の修正

予測窓を見ながら攻撃を一回クリックしても進まない不具合を、固定本編の隔離コピーで再現し、Godotのボタンを押下から解放まで保つ修正を加えた。フレームを跨ぐ攻撃、長押し、取消、予測・別操作の15条件と既存の操作・別プロセス再開を確認できた。ここで確認したのはLinux上の実Godotノードと合成入力・実保存であり、統合後の実画面確認、GitHub保存、Windows実機、正式UI受入、M1完成とは分ける。

## 出所と今回の範囲

- 本編基点：027a7b4b87a0018f46130fb2d3200bcb6ef5fc6a、Work 20260927-game-application、枝 impl/m1-godot-application-20260927。
- 計画：48c43dc0c745bc066e1196fa532e48fd94466f6b、全108件を同一パスへ実同期して照合。技術09741d506d08b4c6bb1d57048ea594f89141effcに新差分なし。
- 操作契約：UI原本36e13494367e21bb2776fc7317ed9149d0336c82 の `docs/検証/UI/readability/co-u02/journey/select-details.md`、blob b8bea6b69037102df03e7218746e3fbdafd82e39。相手詳細を閉じず、次の相手・札・操作ボタンへ移れるという既存の要件を回復する。
- 変更はGodot画面の入力・ノード寿命と検査入口。Coreのルール、保存形式、カード値、素材、固定ツール、旧証拠、UI原本は変更しない。

## 原因と修正

`GameScreen.Exploration.cs` の `_Input` は、予測／詳細窓の外側でマウスを押したときに窓を閉じ、全体の再描画を予約する。次の `_Process` による `Render` は古いControlを全て外して作り直す。一方、Godotの通常Buttonは押した瞬間ではなく、押して離した時に `Pressed` シグナルを送る。押下と解放の間にButtonが交換されると、押下を覚えた元のButtonが消えて実行されない。

既存の `UiAutomation.Click` は押下・解放を同一フレームへ入れるため、この時間差を通っていなかった。手動再現と同じ状態の不変コピーでは、修正前の100msクリックが `Pressed` 0回、命令なしのまま予測窓だけ閉じる失敗になった。修正前の結果は `attack-results/baseline-observed-failure.json` に残した。

新しい `GameScreen.ButtonInput.cs` は、そのButtonが実際に `ButtonDown` を受け取った間だけ参照を持ち、`ButtonUp` で解除する。`_Process` は保持中の全体再生成を保留する。窓外クリックだけでなく、180ms後の自動予測表示も押下対象を交換しなくなる。札ドラッグはButtonではないため従来どおり更新する。

Esc、右クリック、フォーカス喪失、表示サイズ変更や複数タッチによる取消では、保持しているButtonを一時無効化して押下を解除する。次の描画は公開viewから通常の有効状態を作り直す。これにより、取消後の解放で遅れて攻撃されることも、以後のボタンが無効のままになることも避ける。

## コードを読む順序

すべてリポジトリルートからの相対パス。

1. `apps/crossweave-godot/Godot/Application/GameScreen.Layout.cs` の `Button`。Godot標準シグナルと本作の実行処理を接続する入口。
2. `apps/crossweave-godot/Godot/Application/GameScreen.ButtonInput.cs`。押下中のノード保持と取消を所有する新しいpartial。partialはC#のファイル分割であり、別のゲームsessionではない。
3. `apps/crossweave-godot/Godot/Application/GameScreen.cs` の `_Process`。完了処理・hover更新を継続しながら、全体Renderだけを解放まで待つ。
4. `apps/crossweave-godot/Godot/Application/GameScreen.Exploration.cs` の `_Input`。Esc／右クリック等から同じ取消へつなぐ。対象選択ロジックとは別の変更。
5. `apps/crossweave-godot/Godot/Application/UiAutomation.ClickRegression.cs`。実Buttonの矩形へ押下、100msまたは350ms待機、解放を送る。ゲームviewを直接実行してUI合格にしていない。

Godot固有の `ButtonDown`、`ButtonUp`、`Pressed` と `Disabled` の意味は、採用したGodot 4.7.2同梱の `GodotSharp/Api/Debug/GodotSharp.xml` のBaseButton記述で確認した。`Pressed` はActionModeがReleaseならButtonUp時、保持中のDisabled変更はButtonUpを送る。参照保持・partial・ラムダはC#側の仕組み、全Controlの再生成と保持中の保留は本作の設計である。

## 確認済み

- 固定Godot C# 4.7.2、SDK 10.0.401、runtime 10.0.12でoffline build成功、警告0・エラー0。
- 正規oracleのnatural record、step 1（continue_scene直後）を固定。既存fixture生成と同じくschema／engine_versionの表記だけをC#へ合わせ、状態・乱数・ルール値を変更していない。入力とhashは `fixtures/attack-natural-step1.json` と `attack-results/summary.json`。
- 予測窓あり100ms／350ms、窓なし100ms／350ms、自動予測、相手詳細、Enterの攻撃が一回だけ確定し、Coreの期待結果・UI view・実保存が一致。
- Esc、右クリック、フォーカス喪失、ボタン外解放は命令を出さず、続く通常クリックは成功。
- ボタン外へ移動して戻ってから解放、メニュー、予測ボタンの開閉、連続クリックで必要な操作だけ通る。
- 既存 `interaction` 20チェック成功。編成ドラッグ、未確定案取消、所持不足、ロック、探索、札スワイプ、予測、フォーカス喪失等を含む。
- 既存 `resume` は同じ隔離slotの別プロセス再開と確定命令・保存一致を確認。詳しくは対応JSON。

## 再実行

ビルド済みの同じソースと検証済みGodot.NETを用意し、次を実行する。各条件には一意の隔離slotが作られ、通常セーブへは書き込まない。出力先は新しいディレクトリにする。

```sh
python apps/crossweave-godot/UiProbe/verify_click_input.py --godot /absolute/path/to/Godot --output /absolute/new/evidence/directory
```

描画も採取する場合だけ `--rendered` を加える。これも合成入力の検査であり、OSの実マウス操作に読み替えない。対応する既存検査は `interaction` と、その同じslot・出力先を読む `resume`。

## 限界と実行中に分かったこと

- 既存xUnit依存はoffline一式にないため、.NET全体回帰は未実行。headless成功を画素適合、Windows 11物理入力、正式配布、人の面白さ評価へ広げない。
- 初回SDK解決はコマンドの `--configfile` だけではGodot SDKへ届かず失敗した。承認済みの同じローカルnupkgのみを隔離HOMEのNuGet設定へ与え、固定project・lock・runtime値を変えず再ビルドして成功した。新たな配布元取得や通信設定変更はしていない。
- 既存 `review-fixtures` による全fixture生成は対象が広く、途中で停止した。成功扱いにせず、今回の限定試験には同じ正規oracleから取り出した上記の固定入力を用いた。
- 統合後は対象選択修正も入れた最終ソースで回帰し、実画面から操作できることを親担当が確認する。保存コミットと受領は親の統合・読戻し記録に従う。
