# Codex Cloudへの手動引継ぎ手順

現状ではCloudを次の成立性検査の候補として優先する。専用desktop継承案は、PowerShell・Pythonとも入力desktop上で前提不成立だった。Cloudの描画成功はまだ未確認。この資料はCloudへ渡す手順を準備したもので、Cloud実行済みの証拠ではない。

## 利用者が行う操作

1. Codexの「Work in」から「Cloud」を選び、「Select environment」を開く。Web・デスクトップアプリとも公式の起動経路を利用する。ログインや接続が必要なら利用者が行う。
2. `eckolo/crossweave` 用の公開済み環境があれば選ぶ。複数ある場合は、このrepoだけを対象とする個人用の検査環境を選ぶ。公開済み環境がない場合は「Create environment」でこのrepoを選び、環境準備チャットに[環境準備プロンプト](環境準備プロンプト.md)の本文を渡す。
3. 環境の準備報告を確認する。確認対象は「対象repo」「固定Godot/.NET」「Xvfb・Mesaの利用可否」「Cloud内の検査保存先」「停止・未確認」であり、コードやhashの検算を利用者が代行する必要はない。準備未了・別版への変更・本編変更があればPublishせず、その報告をこの窓口へ戻す。検算済みの準備報告なら、環境を保存してPublishする。
4. 公開された環境からCloudタスクを開始する。枝を選べる画面では既存 `impl/m1-godot-application-20260927` を指定し、[検査引継ぎプロンプト](検査引継ぎプロンプト.md)の本文を渡す。枝指定UIがなくても、プロンプトに開始条件を入れている。Cloudが別枝・別repoで始まった場合は、そのまま検査せず停止報告を戻す。
5. Cloudの結果本文と証拠ファイルを、この会話へ利用者が持ち帰る。[結果の持ち帰り](#結果の持ち帰り)の欄を参照する。ローカル側では本編編集を継続せず、Cloud側も今回の本編は読取り専用にする。CloudのUI上で別チャットができても、正式WorkIDを新設せず、同じWorkの検査として扱う。

既存WorkIDは `20260927-game-application`。新しい本編Work、作業枝、PR、並列実装は作らない。現在窓口から他Workへの自動送信・起動・停止もしない。利用者がCloudへプロンプトを渡して開始する方式。

## この手順で確認する範囲

| 項目 | 今回の範囲 |
|---|---|
| 本編 | 固定e480ef45のapps/crossweave-godotと同一。本編候補9ファイルはa01c5c27 |
| UI入力 | 固定合法fixtureのrepro-normal-dark-homeのみ |
| 実状態 | 通常暗色の拠点・設定・編成・編成設定。既存modeの遷移をそのまま使う |
| 付随検査 | 既存verify.pyが最後に実行するheadlessのproof入口回帰1回。別の全回帰検査は追加しない |
| 描画 | Linux x64、Xvfbの1920×1080×24、MesaソフトウェアOpenGL、既存gl_compatibility。実ViewportのPNGとnodes |
| 保存 | Cloud内の専用XDG領域と新規検査slot。形式は既存のまま。ローカル通常セーブを持ち込まない |
| 判定 | Cloudで同本編の実描画・実入力・証拠取得が成立するか。Windows原本の全画面適合・実機・人の試遊の合格にはしない |

OS書体が変われば実行環境差として記録する。Yu Gothic UI／Georgiaの欠落を、書体追加・別素材・本編font設定の変更で埋めない。既存fallbackで描画できても、Windowsでのfont metrics・wrap・AA比較は未確認を保つ。

Cloudへの切替は、ローカルのサンドボックス外へ検査を持ち出すことではない。Cloud内で新しく検査を起動する。Cloudの提供環境であることはタスク画面・環境名と実行コンテキストで確定し、LinuxというだけでCloudと断定しない。

## 固定SHAと開始条件

基準本編は `e480ef45c39c9e3398884931c3129b5500524fe3`。この後の手順資料コミットを含む枝HEADで開始しても、`apps/crossweave-godot` がこの基準と完全一致することをCloud側が検算する。ローカルGit HEAD0ec63342は以前の基点のため、Cloudの実行対象に使わない。

計画5c61d64a、技術21ddd349、UIab1b6fa0を継承する。検査中に別SHAへ同期・更新したり、計画枝／配布枝を全体マージしない。相違があれば停止して差分を返す。

## 結果の持ち帰り

Cloudから次を含む一つの証拠ZIPをダウンロードし、この会話へ添付する。Cloudでファイル添付が提供されなければ、取得可能な形式を報告してから経路を決める。CI artifact、旧PNG取得、Page／Dropboxへの転送を自動で代替にしない。

- 結果本文：成立／不成立、実際のrepo・枝・HEAD、基準本編との一致、OS／CPU／Godot／SDK／GL／font、停止地点、残件。
- 全ログ：準備・GL確認・restore/build/import・mode・proof入口回帰。成功だけを抜き出さない。
- 機械証拠：manifest.json、repro-normal-dark-home.json、実PNG・同状態nodes.json、source／fixtureのhash一覧、実行前後のsource差分。
- 見るための画像：normal・normal-settings・normal-preparation・normal-preparation-settingsの原寸PNG。拡大・再構成・描き直しで原寸の代用をしない。

利用者がまず見るのは結果本文の「成立／不成立」と「停止・未確認」。画像は描画された内容を確認する入口。UI適合の判定やhashの検算を求める段階ではない。持ち帰り後に、この窓口で原票・入力・source・状態・使用先との対応を検算する。
