# D04B-UI-02 コード解説・読む順

同じMain.tscnから一つのGameScreenを起動し、一つのFileGameSessionへ操作を渡す構成を維持した。札の見た目やドラッグ像は公開viewを描くもので、札の計算や保存DTOの複製ではない。

## 2026-10-02 UIレビュー追補の読む順

初回のR1〜R6と、レビューのR01〜R07／U01は別の番号体系。初回提出2102acaを継承し、この追補では次の順に読む。

1. [固定レビュー原本](review-20261002/received/適合確認.md) → [追補結果](review-20261002/README.md)。修正と未確認の境界を先に見る。
2. `GameScreen.ReviewFixes.cs`の`PredictionSummary`・`ActorVitals`・`StatDelta`。公開予測の投影と、現在のバーに添える差分を見る。
3. `Core/Application/Expedition.cs`の`Predict`。Coreのforkが解決した未使用手札の`expires`と`destination`を公開する境界を読む。
4. `GameScreen.Exploration.cs`の`DropCard`。公開回収先に消滅がある場合は予測で止め、確定ボタンからだけ`play`を送る。
5. `PreparationSummary` → `CanStage` → `DropPlan`。Comparison／Planからの表示、公開取得群上限、受入表示と解放時の共通判定を読む。
6. `DestinationScroll`・`AutoScroll` → `ListViewport._GuiInput`・`BlankPointerDown`。札の保持と、余白からの左マウス送りを別状態で追う。
7. `UiAutomation.Review.cs` → `UiProbe/verify.py`。同じ実Controlへ入力し、DTO・保存・Plan・プロセスを照合する。限定回帰のfilterは[確認入口](確認入口.md)を参照する。

`PreviewAction`は既存と同じCoreの複製上で解決する。消滅を伴うかをGodotでconsume／doomed／fillerから再計算せず、解決後の札がdestroyedかを公開する。保存DTO、回収規則、乱数の方式は変えない。`CardView`と準備の公開コピーには既存guard規則の既定2回を付記する。原本札・保存にはその項目を追加しない。明示nullは「制限なし」、項目がなければ「未公開」であり、0として表示しない。

攻撃の隠蔽は、リセット後の値だけでは打撃が隠れる。既に解決済みの`posture_before − hit_gain`を打撃直後として示し、リセット後の`posture_after`を別文で示す。機転・身構・攪乱・余力・隠蔽は公開before／afterの差分を使う。原本が扱う一閃倍率`critical_multiplier`と軽減量`reduction`は公開actor_changesにないため「未公開」とする。既存actionの`posture_multiplier`は別の値であり、一閃倍率の代用にしない。相手の将来手札や非公開乱数を推測しない。

`PreparationSummary`は取得候補ごとの価格とpending_selection_idの編成有無を表示する。編成の数量差分は公開blueprint keyごとに現在／案を比べ、変更された心得は既存trigger_text／effect_textを載せる。表示のために値引き、枠、支払いを再計算しない。公開handleは確定後の新Viewから取り直す。

行動順は公開予約の同じatを一群として描く。同時刻内の本人位置は例えば「2〜3」とし、その群の内部順を断定しない。「本人・今」と「本人・次」を区別し、既存アイコンからの詳細入口を維持する。

受入判定は`DropPlan`を描画と解放時で共用する。正式所持の取得列への取消は拒否し、未払い個体の取消は受け入れる。端送りは現在の移動先ScrollContainer内にポインターがある場合だけ進める。余白送りはその実ScrollContainerが受け取った左マウス押下から始め、Esc等の共通取消で解除する。UIの未払いPlanは確定するまで保存されない。

U01のM1合法状態はFHDでは手札3枚・場4属性が収まる。検査は自然寸法の画像と範囲を先に記録し、同じ実ノードの幅／高さだけを限定してoverflowも測る。札や仮数値を増やした模擬UIではない。限定寸法での結果を通常FHDにoverflowがあるという証拠には使わない。

固定oracleの合法状態はそのまま隔離slotへ復元する。schema名の既存C#接続への置換以外にゲーム数値を書き換えない。補充札の状態探索では検査用Randomが合法な入力候補を選ぶだけで、Coreの乱数を差し替えない。取得用fixtureは既存の合法取得記録であり、通常利用者の所持・残高へ注入しない。

## Godot標準・C#/.NET・本作独自の区別

| 種別 | この実装での例 | 担うこと |
|---|---|---|
| Godot標準 | Control、Panel、Button、ScrollContainer、HBoxContainer、TextureRect | 配置、スクロール、フォーカス、描画・入力の配送 |
| Godot標準 | _Ready、_Process、_Input、_GuiInput、_Draw、Pressed、QueueFree | ノードの起動、フレーム更新、入力イベント、signal、フレーム末の解放 |
| Godot標準 | FontVariation、TextServer.NameToTag、GradientTexture2D | 既存フォントの太さと背景上の読みやすさ。新しい画像素材は作らない |
| C#/.NET | partial class、Action、Task.Run、JsonObject、LINQ | 一つのクラスのファイル分割、処理の受渡し、ファイル作業の待機、公開JSONの投影 |
| 本作独自 | GameScreen、Plan、ViewData、PointerGesture、Can、Send、Adopt | 本編の画面状態、操作意図、入力の意味、公開view更新 |
| 本作独自 | GameApplication、FileGameSession、GameCommand、SaveFileCodec | ゲーム規則、要求の一意性、保存と再開。Godotの組込み保存機能ではない |

`partial`は画面を複数作る仕組みではない。同じGameScreenの実装を読みやすく分けるC#構文。`Render`は本作の通常メソッドで、Godotの標準描画callbackは`_Draw`である。

## 取得編成：表示集約と個体を分ける

所持の同性能札を数量表示しても、Coreへ送るIDは一つの公開個体ID。未払い／正式所持、ロック、変換可否が違う個体は別の行にする。編成へ動かすと次の個体が代表になる。まとめた数を勝手にまとめて購入・変換しない。

取得時はPlan.acquireへ候補IDを加え、画面用のpending_selection_idを表示する。正式所持・着想は変えない。確認窓からcommit_preparationを送って保存成功が返った時だけAdoptする。保存が失敗した場合には未確定案を保持し、成否不明なら通常操作を停止する。この境界は今回も同じである。

## 掴んだ位置を維持する

PointerDownで`grabOffset = 押下位置 − 元札左上`と元札寸法を記憶する。ホールド成立後は元と同じMakeTileでドラッグ像を生成し、毎フレーム`pointer − grabOffset`へ置く。画面の外だけを制限するため、札の中心へ飛ばない。GodotのContainerが配置を確定した後のGlobalRectを使い、論理1920×1080座標を一貫して用いる。

120msは進行リングが見え始める時点で、既定220msはドラッグが成立する時点。設定150／220／320msは判定器へ渡す時計を換算して表現し、Core側のゲーム時間・乱数・保存を変えない。短クリックの自動検査では押下と解放を同フレームに送り、フォントの初回描画時間を長押しと誤認させない。

右クリック、Esc、画面離脱、サイズ変更、複数touchはCancelGestureへ集約する。ドラッグ像は入力を受けず、解放が古い札から二重送信されない。場へ落とす場合も、公開予測で通常の設置かつ消滅なしならquick実行し、それ以外は予測窓から行動ボタンへ進む。

## 詳細・予測・親子窓

手札・場・予測札は同じ札面を描くが、場の効果値はfield_power／field_hitを使う。予測札には破線と予測印を付け、クリックでは詳細しか開かない。ShowDetailは同じ対象の再クリックを閉じる操作として扱う。外クリックは窓を閉じ、別の札を押した入力はそのまま新しい札へ渡す。

選択した手札と行動対象は別に保持する。行動順アイコンは主体の公開詳細を開く入口で、本人を誤って攻撃対象にしない。予測窓を開くたびに手札の位置から反対端を求め直すので、直前の主体詳細の位置を流用しない。

調査記録は既に観測したprofileだけを一覧にする。基本構成の公開前は観測札だけ、公開後は初期枚数付きの基本構成を表示する。親と子は16px離し、札詳細から戻っても親の選択とスクロール位置を保つ。推測した敵の現在手札を表示しない。

## 保存と検査の読み方

UIはMain.tscn、保存はFileGameSession。UiAutomationだけが隔離slot・既存固定fixture・故障注入に触れる。製品の通常起動では生成されない。画像はviewportの実レンダーから取得し、原本画像との合成やmockの描画で置き換えていない。

73件の.NET回帰は規則・実保存・別プロセスを確認する。UI検査では入力から生じたGameCommandを同じ開始DTOのCoreへ適用し、画面session・ファイル・期待結果を比較する。resumeはプロセスIDが異なることと全DTO一致、次の一手の乱数を含む結果を確認する。保存待機中の終了はGodot終了後の別.NETプロセスでもrevisionを読戻す。

自動検査の「実InputEvent」は物理マウス・タッチの受入を意味しない。検査ごとのprocess_id、logical_viewport、actual_window、physical_input、source_sha256を読み、[確認結果](確認結果.md)の未確認範囲と合わせて判断する。
