# サンドボックス内の描画確認が止まった理由

2026-10-08追補：利用者の承認後に専用desktop継承案の前提を実測した。今回のプロセスはWinSta0\Default、UOI_IO=trueで入力desktopと同じだったため、Godot起動前に停止した。専用desktopが提供されるという一般仕様はこの経路の実測では成立していない。[継承案の検査記録](../desktop-inherit-20261008/README.md)を現時点の再開条件として読む。以下のCreateDesktopW停止は前回の実ログとして保持する。

今回止まったのは、Godotを起動する前のWindows隔離desktop作成です。検査launcher `background_desktop.py` の `CreateDesktopW(...,0x01FF,...)` がWinError5（アクセス拒否）を返しました。Godotの描画やGPU初期化が失敗した結果ではありません。

既定の検査は、利用者の入力desktopを切り替えず、別のdesktopに子PythonとGodotを配置して実描画を採る設計です。一方、今回の設定ファイルの既知キーを読取り確認すると、Windows sandboxはelevated、sandbox_private_desktopの明示設定はありません。OpenAI公式資料ではelevatedが専用の低権限ユーザー・filesystem境界・firewall等を使い、両sandboxモードが既定でprivate desktopも使うと説明されています。[Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox)

したがって、サンドボックスの隔離境界の中から、検査側がさらにdesktopを新規作成する手順が権限と整合していない可能性があります。これは実ログと公式の一般説明からの推測です。今回どのACL／個別権限が拒否したか、実プロセスの全設定、GPUの利用可否は未特定です。「サンドボックスではGodotを一切描画できない」と判定したわけではありません。

現行手順で確定している停止地点は、desktop作成・検査process起動前です。通常desktop、sandbox設定の変更、別renderer、別保存先、外部実行、CIへの代替移行は準備／試行していません。利用者の「サンドボックス内に規定された操作を外部へ持ち出すのは原則禁止」を保持します。

同じ手順の前提をサンドボックス内で成立させられる条件を受領するか、手順の変更が必要なら具体的な理由・範囲・影響を示して明示承認を受けることが再開条件です。GPU故障やコードの外観不適合という理由に置き換えず、未描画を合格にしません。

.NETの既存8検査で起きたtesthost接続timeoutは別の停止です。90秒で接続できず0実行になった事実はありますが、今回のログだけで通信拒否と遅延のどちらかを断定しません。
