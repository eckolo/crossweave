# 手札切替時の対象保持：修正・検査・読む順

手札を切り替えて予測を確認しても、選んだ相手が勝手に水路へ戻らないよう、重複していた対象の初期化を取り除いた。固定された既存の自然進行データを使い、修正前の失敗と修正後の設置・身構・回復を挟んだ往復を確認した。これは対象保持修正単独の検査結果であり、攻撃入力修正との統合後検査・GitHub保存・Windows実機受入・人の試遊は別である。

2026-11-05（日本時間）。正式Work `20260927-game-application`、枝 `impl/m1-godot-application-20260927`。対象保持修正単独は実装・限定検証済み。依頼全体は未完了・進行中。GitHub保存と全体の引継ぎは本編統合担当が行う。

ユーザーの報告にある「水路を選択して戻すと水路」だけは、保持方針と矛盾しない。対照試験では潜水者を明示選択してから同じ往復を行い、活動中の潜水者が水路へ変更されることを不具合として固定した。設置中の照準を隠す、新しい自動選択規則を導入する、といった未承認の見た目変更は行っていない。

## 原因と修正

修正前は `SelectHand` が、その札の合法行動に現在の対象IDがなければ対象を選び直していた。設置・身構・回復は合法行動の `target` が `null` なので、相手IDが一致せず、UIの `selectedTarget` が空文字へ変わる。

直後の `RefreshAction` は `RetainPublicTarget` を呼ぶ。ここでは対象不要札でも活動中の主体をUI選択候補として扱い、空になった対象を通路優先で再選択する。その結果、手札選択時に潜水者が水路へ戻り、次の一致攻撃の実際の `choice.target` も水路になる。予測窓を開くこと自体は原因ではない。

修正では `SelectHand` 内の重複した対象選びを除き、対象保持と離脱後の選び直しを既存の `RetainPublicTarget` に一本化した。対象不要の行動で相手を選択中でも、`Choice` は合法候補の `target:null` を返すため、不要な対象IDをCoreへ送る変更にはならない。

## コードを読む順序

1. `apps/crossweave-godot/Godot/Application/GameScreen.Exploration.cs` の `TapCard` → `SelectHand`。クリックした手札IDを記憶する。今回変更した日本語コメントに、UIの選択対象と行動のtargetが別である理由を記した。
2. 同ファイルの `RefreshAction` → `RetainPublicTarget`。現在の対象が有効なら保持する。対象が離脱したら、公開された合法候補から通路優先で選び直す。
3. 同ファイルの `Choice`。相手IDに合う合法行動を選び、対象不要の場合は `target:null` の候補へ戻る。画面の選択と実際の要求をここで結び付ける。
4. `apps/crossweave-godot/Core/Application/Expedition.cs` の `Choices`。これは参照のみ。対象IDが必要なのは場と一致する攻撃であり、他の行動はnullを返す。UIがこの規則を再計算して変更するものではない。
5. `apps/crossweave-godot/Godot/Application/UiAutomation.TargetProbe.cs`。手札・相手・予測・詳細にGodotの合成InputEventを送り、選択と送信予定choice、実セーブが変わらないことを検査する。

`GameScreen`、選択対象の保持方針、`Choice` は本作独自の構成であり、Godotが要求する標準構成ではない。GodotのControlへ入力イベントが届き、本作のクリック処理が呼ばれる部分と、C#の文字列・JSONを選ぶ部分を分けて読む。検査中のreflectionは一般の.NET機能で、UI内のprivate選択状態を観測するためだけに使用する。

失敗時にもゲームの確定状態を直接書き換えない。予測と選択は保存命令ではなく、今回の操作試験では開始時と終了時のDTO・セーブバイト一致を確認した。公開view投影の境界試験は `finally` で元viewと選択へ戻す。

## 固定入力と再実行入口（開発担当向け）

既存 `apps/crossweave-godot/Tests/Fixtures/application-oracle.json.br` の natural 記録の期待差分を先頭から復元する。設置はstep 1、身構はstep 2、回復はstep 11。手札、相手、数値、規則は変えず、既存 `GenerateReviewFixtures` と同じschema／engine_versionの接続名だけをC#表記へ変換する。通常セーブは使わない。

生成スクリプトはNode.js標準機能のみを使用する検査用入口であり、製品の新しい実行依存ではない。生成物を2重に管理せず、元oracleと生成器を正本とする。今回、生成器の再出力3件が実際の試験入力とバイト一致した。

```sh
node apps/crossweave-godot/UiProbe/generate-target-fixtures.mjs /absolute/target-fixtures
# 既存固定SDK/Godotで本編をビルドした後、各入力を一意の隔離slotで確認する。
Godot --headless --path apps/crossweave-godot/Godot -- \
  --ui-check=target-retention --ui-slot=target-place-unique-run \
  --ui-output=/absolute/target-result --ui-fixture=/absolute/target-fixtures/place.json
```

`guard.json`、`heal.json` も同じ入口で、出力先とslotを分けて実行する。実行ファイル名 `Godot` は固定C#版の実際のパスに置き換える。利用者へSDK導入・ビルドを依頼する手順ではない。

| 修正後の設置 | 非通路と通路の選択、対象不要札、予測札詳細、予測、攻撃へ復帰 | 33チェック成功 |
| 修正後の身構 | 一致する身構札・設置札を経由する往復 | 29チェック成功 |
| 修正後の回復 | 一致する回復札・身構札を経由する往復 | 25チェック成功 |

合計87チェック。そのうち6件は、3入力ごとの主体離脱／候補ゼロを公開viewだけで投影した境界検査であり、ゲーム中に主体を撃破して通過した実戦結果ではない。全入力で操作によるセーブ変更なし。対象不要行動の `choice.target` はnullを維持し、戻した攻撃は選択したE1またはV0を維持した。

環境は固定Godot C#4.7.2・.NET SDK10.0.401、Linux、headless、実Mainノードと合成InputEvent。ビルドは警告0・エラー0。画面の実描画、物理マウス、Windows 11実機、DPI・音・GPU性能、人の面白さ評価、正式UI受入はこの検査の合格に含めない。

証拠は同階層の `target-retention/manifest.json`、各 `*-result.json`、`*-steps.json`。manifestは対象保持単独のソースhashであり、攻撃修正との統合版hashではない。統合後に最終ソースで再検査し、その証拠を別記録にする。
