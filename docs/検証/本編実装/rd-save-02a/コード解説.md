# RD-SAVE-02A コードを読む入口

今回できるのは「本編の一操作を実ファイルへ確定し、別プロセスで続きから再開する」こと。Godot画面は未接続。対象コードは `e6b3b7446626f99131396e10bfbfdbd5990d8694`。[検証README](README.md)に確認環境と結果を記録する。

## 役割と読む順序

| 順 | ファイル・主要な処理 | 何を担当するか |
|---:|---|---|
| 1 | [Infrastructure/Application/FileGameSession.cs](../../../../apps/crossweave-godot/Infrastructure/Application/FileGameSession.cs) のCreateNew・Open・Execute・Dispose | アプリ側の入口。起動時に保存所有権とCore本体を作り、終了まで保持する。一つの窓・画面ごとに保存を開き直す構成ではない |
| 2 | [Core/Application/GameApplication.cs](../../../../apps/crossweave-godot/Core/Application/GameApplication.cs) のExecute | 既存本編が候補を計算する箇所。現在のdocumentのコピーで進め、保存前に所持や残高の原本を書き換えない |
| 3 | [Infrastructure/Application/ApplicationFileStore.cs](../../../../apps/crossweave-godot/Infrastructure/Application/ApplicationFileStore.cs) のTryCommit・Write・Reconcile | .NETのファイルI/O、排他、置換、結果照合を実装。trueを返して初めてCoreがdocumentを交換する |
| 4 | [Infrastructure/Application/SaveFileCodec.cs](../../../../apps/crossweave-godot/Infrastructure/Application/SaveFileCodec.cs) のEncode・Decode | 版付き外枠、payloadのhash、ApplicationDtoの復元検査。ファイル形式とゲーム内容の版は別の責務 |
| 5 | [SaveProbe/Program.cs](../../../../apps/crossweave-godot/SaveProbe/Program.cs) と [Tests/SaveTests.cs](../../../../apps/crossweave-godot/Tests/SaveTests.cs) | 実際の別プロセスを作り、どこで止め、何と比べるか。テスト内の故障注入と本物の強制終了を区別して読む |

Coreは「ゲーム上の操作が正しいか」と確定状態を管理する。Infrastructureは「その確定をどこへどう記録するか」を担当する。Godotは後続で画面・入力・起動終了・OS保存パスを接続する。Testsはこれらの期待結果を確認する。同じsolutionに置く分け方は本作の設計で、Godotが必須にしているクラス構成ではない。

`ApplicationDto`はCoreが持つ保存用データの写し。`IApplicationCommitBoundary`は「候補を永続確定できたか」をCoreへ伝えるC#のinterfaceである。Godotのシグナルやノードの仕組みではない。保存先のPathやFileStreamをCoreへ置かないので、以前のメモリー本編も、画面に依存しない試験も継続できる。

## 「出発」を一つ追う

画面側はInspectのrevisionとview_tokenを使ってGameCommandを作る。`Type="depart"`、Payloadは`{"case_id":"SCN-001"}`。RequestIdはこの操作に固有の値。FileGameSession.Executeから既存GameApplication.Executeへ渡される。

Coreは要求履歴と現在版を確認し、現在の状態のコピーに、探索run・持参した実個体・手札・乱数・場面等を設定する。revisionと要求履歴も同じコピーへ追加する。この時点では現在の所有状態はまだ古いままである。

`boundary.TryCommit(currentRevision, candidateDto)`から保存部へ進む。保存部は、書込み所有権を保持していることと、現ファイルが以前読んだ状態のままであることを確かめる。候補をtmpへ書き、フラッシュし、読戻す。完成したtmpで現保存を置換し、旧保存をbackupへ残す。

最後に現保存を読んで候補と一致することを確認する。trueがCoreへ返ると、Coreは初めて `document = next` としてメモリー上の原本を交換する。以後返されるViewは確定後の状態である。表示だけ先に成功させる順序を避けるため、この順番を採用した。

プロセスを終了するとFileGameSession.Disposeが所有権を解放する。次のプロセスはOpenでファイルの版・hash・本編整合性を検査し、ApplicationDtoをGameApplication.Restoreへ渡す。乱数seedで探索を作り直すのではなく、全MT語と現在位置、札の所在、要求履歴を復元するので、同じ次操作の結果も一致する。

## 失敗時に何を守るか

| 状況 | 実装上の分岐 | 試験で確かめること |
|---|---|---|
| tmpへの書込み不能・容量相当の例外 | Write→Reconcileで旧完全保存を確認しfalse | 旧メモリー・旧ファイルが同じ。同じ要求を再試行できる |
| 書込み中／置換前に強制終了 | 次プロセスが現保存をOpen。残ったtmpは採用しない | 以前の完全保存が再開される。実プロセスをKillし、finallyが通らない状況を作る |
| 置換後、応答を返す前に中断 | 現保存には新revisionと要求履歴が存在 | 再送はreplayed。追加の支払い・帰還精算がない |
| 置換結果も読めない | ApplicationCommitUncertainException→CoreのcommitBlocked | 旧viewにはstale=true、全操作不可。Reload成功後の実物を使って再送 |
| 二重起動 | 固定の`.lock`をFileShare.Noneで開けず拒否 | 別プロセスが保存に触れられない。所有プロセスをKillすると次が取得できる |
| 破損／未来版 | Openは失敗。自動新規作成しない | 元バイトが保持される。backup復旧は明示操作、破損原本も別名で保存 |

成否不明を普通のfalseへ変えると、ファイルでは支払済みなのに画面が未払いと判断し、新IDで再購入させる危険がある。このため既存bool境界へ専用例外だけを追加した。外側のsessionを閉じて再度Openするか、所有権を維持してReloadし、保存された要求履歴で結果を確定する。

`FileShare.None`はファイルを開くOSハンドルの共有条件。`lock(gate)`は同一プロセス内のスレッドを順番に通すC#の機能であり、別プロセスを止めるものではない。本実装は両方を役割に応じて使う。Disposeも同じgateを取るため、保存中に終了要求が来ても、その同期処理が終わるまで所有権を解放しない。

## 実際に動かす

固定SDKは10.0.401、runtime10.0.12。リポジトリの `apps/crossweave-godot/` で実行する。

```sh
python SaveProbe/verify.py
```

この入口は固定SDKの取得・hash照合、locked restore、Testsのbuild、保存試験と既存42試験、TRXと検証manifestの保存を行う。Godotや配布ZIPを起動する入口ではない。既に固定SDKを取得済みなら `--no-acquire` で再取得を省略できる。

保存の生成・別プロセス読込みだけを追う場合は、ビルド後に同じCLIを2回実行する。引数の保存先と出力先は自分で用意した試験用絶対パスへ置き換える。

```text
dotnet SaveProbe/bin/Debug/net10.0/Crossweave.SaveProbe.dll create <試験用保存の絶対パス> <生成結果JSONの絶対パス> learning-example
dotnet SaveProbe/bin/Debug/net10.0/Crossweave.SaveProbe.dll snapshot <同じ保存の絶対パス> <読戻し結果JSONの絶対パス>
```

二つの結果のpidは異なり、dtoとviewは一致する。GUIで操作できることやGodotの通常保存パスの確認ではない。具体的な確認環境・結果・未確認はREADMEを参照する。

## .NET公式資料

- [File.Replace（.NET 10）](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.replace?view=net-10.0)：既存ファイルの置換とbackup。既存backupは直前の現保存で置き換わる。
- [FileStream.Flush（.NET 10）](https://learn.microsoft.com/en-us/dotnet/api/system.io.filestream.flush?view=net-10.0)：書込みバッファを送り出す処理。
- [FileShare（.NET 10）](https://learn.microsoft.com/en-us/dotnet/api/system.io.fileshare?view=net-10.0)：他のopenとの共有条件。

これらのAPIの使用だけで、OS全体の停電耐性・すべてのファイルシステム・Godot終了処理が自動的に完成するわけではない。今回の故障点と環境を固定した試験結果と区別する。
