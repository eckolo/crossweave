# RD-SAVE-02A 保存形式とGodot側への接続契約

本編保存部は純C#／.NET。Godot画面、通常入口、終了要求の接続は02B。Core56caf205のDTOを継承し、既存のメモリー起動も維持する。

## 形式と保持対象

外側はUTF-8 JSON、kind=`crossweave.application.save`、fileVersion=1、writtenUtc、payloadSha256、payload。payloadはApplicationDto v1（FormatVersion/RuleSetId/ContentSetId/State）をそのまま格納する。対応は規則`CW-M1-rules-0.5`／内容`CW-M1-SCN001-0.2`。外枠版とDTO版は独立。SHA256はpayloadの実JSONバイトの破損検出で、改ざん防止ではない。

State全体を一単位で保存する。所持実個体・編成・心得・残高端数・ロック・候補・帰還台帳・知識・案件・既読、run・nextRun・探索進行・手札／山／場／回収・主体／防御／予約・全MT系列、revision・view_nonce・要求履歴、明示保存した未払いdraftを保持。復元でseedから引き直さず、取得予定を確定個体へ変更しない。

初回形式の固定例は `Tests/Fixtures/save-file-v1.json`。実装したCreateNewが実際に書いた保存で、架空の旧M1版ではない。既存対応v1は無変換で読める。未来のfile/DTO/content版は書込みせず拒否する。今回は前の本編ファイル形式が存在しないため形式移行はなし。旧JS保存の製品importも対象外。将来形式変更時は元版の実保存からの変換・失敗保全を別途実装する。

読込み上限64MiB・JSON深さ128。上限超過は原本を保持して診断。履歴・領収・知識を無条件に切り捨てないため、長期量の設計は後続。ローカルWindows/Linuxファイルシステムと同じ絶対パスを用いる協調プロセスが今回の対象。ネットワークドライブ、複数の別名／ハードリンクから同じ文書を扱う運用、OS全体の停電は未確認。

## APIと寿命

入口は `Infrastructure/Application/FileGameSession.cs`。一つの起動が一つのインスタンスを所有し、画面へGameApplication本体や保存DTOの可変参照を渡さない。

| API | 呼出し条件・結果 |
|---|---|
| Diagnose(absolutePath) | 読取りのみ。Primary/Backupのready・missing・破損・非対応・I/O失敗、残ったtmpを返す。診断だけでは排他取得しない |
| CreateNew(absolutePath, campaignId?) | 現保存・backup・未確定tmpがない時だけ作成。初期状態をファイル確定してから返す。読込み失敗の代替として呼ばない |
| Open(absolutePath) | `.lock`の排他取得→現保存の版・hash・Core整合検査→復元。missing／破損時に自動新規作成しない |
| Inspect / PreviewPreparation / PreviewAction / QuoteConversion | 従来の公開情報・予測。予測は保存しない。viewは独立コピー |
| Execute(GameCommand) | 同期の候補計算・ファイル確定・メモリー交換。一つの操作とそれに伴う自動処理をまとめる |
| RequiresReload / LastSaveFailure | 成否不明で停止中か、直近の保存失敗理由を読む |
| Reload() | 所有権を保ち現保存を再検証。本体を実物から再構築する。成功するまで通常操作を再開しない |
| RecoverBackup(absolutePath) | 所有者を閉じてから行う明示復旧。壊れた原本を`.damaged-*`へ保全し、`.bak`から戻して新しいsessionを返す。最大一操作の巻戻しを説明する |
| ArchiveIncompleteCreation(absolutePath) | 初回作成中断でtmpだけ残った場合の明示処置。tmpを`.abandoned`へ保全し、新規作成を可能にする |
| Dispose() | 進行中Executeの終了を待ち、所有権を解放する。別の保存を追加で走らせる処理ではない |

開始APIは失敗時に例外。SaveException.Codeを診断に用い、FileNotFoundException・UnauthorizedAccessException等のOS例外も起動失敗として扱う。場所を黙って変えたり、読めない文書を上書きしたりしない。通常パスの解決は02BがGodotのProjectSettings.GlobalizePathで行い、`user://saves/local/m1.json`の絶対OSパスを渡す。今回のCLI／Testsは専用一時領域だけを使う。

## 確定結果と失敗

| Execute.Status | 意味と画面側の扱い |
|---|---|
| committed | 保存先で候補を読戻した後にメモリー交換済み。View全体を採用して確定表示 |
| replayed | 同ID同内容の要求は既に適用済み。保存を書き直さず現在Viewを返す |
| rejected | 不正操作・古いrevision/token、または確実に未確定の保存失敗。保存失敗はcommit_boundary_failed、旧完全保存・旧メモリーを保持。同じ要求IDで再試行可能 |
| indeterminate | 置換前後の成否を保存先から判定できない。旧viewはstale=trueで全操作不可。購入／帰還の成功・失敗を断定しない |
| blocked | indeterminate後の通常操作。再読込みが成功するまで処理しない |

同一操作の通信／UI再送は同じRequestId・Type・Payloadを使う。復元後もrequest_logが残るため、置換後に応答できなかった要求はreplayedになる。新しい内容は新ID。未確定結果のまま別IDで同じ購入を行わせない。ExportDtoも成否不明中は拒否する。

IApplicationCommitBoundaryの既存bool契約は維持。追加したApplicationCommitUncertainExceptionだけは「未確定ではなく成否不明」を意味し、Coreを停止させる。既存のfalse／通常例外は引き続き未永続化。境界未指定のメモリー本編と旧試験の意味は変更しない。

## ファイル処理の順序

1. 同じ`.lock`をFileShare.Noneで保持する。ロックファイルを削除しない。JSON本体を置換しても書込み所有者は変わらない。
2. 前回読んだ現保存の全バイトとrevisionを検査。ロックに従わない外部変更があれば操作停止。
3. 同じフォルダの固有tmpへ候補を書き、Flush(true)、再読込み・検証する。
4. 初回は上書きなしMove。通常はReplaceで現保存を置換し、直前の完全保存を`.bak`に残す。
5. 現保存が候補と一致すれば成功。例外が起きても一致なら成功、旧完全保存と一致なら確実な失敗。どちらとも照合できなければ成否不明として停止。

復旧は自動で行わない。正常な現保存の巻戻し、未来版を古いbackupで上書きする操作は拒否。中断で残るtmpは次回起動で自動昇格しない。復旧元backupは壊れた原本で上書きしない。Flush・ReplaceはOS電源断やストレージ故障までの保証ではない。

02Bは、保存中の入力抑制、失敗／停止状態の表示、再読込み・backup復旧の確認導線、終了要求でのDispose待機を接続する。Windows CI成功を、Godot通常入口・物理入力・配布更新の合格へ置き換えない。
