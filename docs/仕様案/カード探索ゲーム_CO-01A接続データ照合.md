## 3. 3札を同じ定義で通す

| 内容ID／基礎ID | 主効果 power/hit/evasion/crit_gain | 場 power/hit | 期限 | 設置／一致 |
|---|---|---|---|---|
| CRD01／nt_flow（A攻撃） | 3/70/0/25 | 0/30 | 2 | 10/10 |
| CRD02／nt_pressure（B攻撃） | 4/50/0/25 | 6/0 | 2 | 8/12 |
| CRD03／nt_stop（D防御） | 3/0/20/20 | 2/20 | 2 | 10/10 |

内部A/B/DはSCN試行入力のままで、正式な属性語の全体対応を決めない。f/l/gの改名ではない。新3札を既存13基礎と合わせた16種のカタログへ追加し、無料初期集合は10種のまま、新3札の初期解放・所持は0とする。

修飾は既存AOの種類・family排他・最大3・life/power合法性を継承する。攻撃2札はheavy/light/precise/echoing/dull/frail、防御札はlight/sturdy/frailを入口許容し、組合せは既存検証で絞る。新効果・新修飾は追加しない。AO1のblueprint形とkeyを維持し、保存外枠のcontent/card registry版へ結び付ける。負の修飾だけの束は合法性の確認対象には入るが、非空の取得候補は少なくとも一つ有益な修飾を要求する。

移植では、基礎＋修飾の完全性能を解決してから情報署名・実札へ渡す。既存`I.signature`は両間隔も含む。カードの修飾による間隔差を一度加え、その後に心得の割引と既存の下限を適用する。`nt_pressure`を未知typeの10/10へ落とすこと、旧`stats`のdefault/overrideで`nt_stop`の攪乱20・機転20を上書きすることを防ぐ。実runtimeでの注入・`Game.cost`・復元検査はD02/D03に残る。今回確認したのはコピー上のAO compileと情報署名までである。

## 4. 報酬・候補・所持を分ける

実台帳キー案は`JSON.stringify(['CW-M1-reward-1',run,reward_id,source_event_id])`。各行に案件・mode・target_set・ACT・構成版・内容版・旧engineキーを保持する。旧A/V0等を使う演算アダプターは、現在のtarget_setでRWへ解決する。再訪を水門復旧の報酬として記録しない。

| RW／対象 | M1の中身 | 保護と取得候補の階層 |
|---|---|---|
| RW01／ACT01 | 100 units＋素材Mを1個＋nt_flow解放対象 | 自身を含む既得分を保護。I |
| RW02／ACT02 | 100 units＋nt_pressure解放対象 | 撃破時は未保護。T1先行の生存退場は0。I |
| RW03／ACT03 | 200 units＋nt_stop解放対象 | 有効clearで全保持。I |
| RW04／ACT04 | RW01の内容を継承 | 自身を含む既得分を保護。I |
| RW05／ACT05 | RW03の内容を継承 | 再訪clearで全保持。I |

素材の型は`M`、数量は1。「M1」という別素材を登録しない。用途・加工・売却価値は未接続。RWや初攻略を直接所持個体へ変えない。特に既存ARの`generatedRewards`がunlockから個体を追加する挙動は、このSCN入力では使用しない。新3札は実候補の購入だけで恒久個体へ進む。

保持した解放の和集合を反映した**後**に、その帰還の実候補を作る。Iは2〜4候補、修飾数重み6:4:0:0、card/passive重み1:1、札の基礎は解放集合、心得PS01〜04のA重み2:4:1:1。価格は400 units、ordinary帯、1候補表につき購入1回を試行に使う。II/IIIの既存表も入力に収めるが、このSCNの全5成果はIなので到達しない。

候補表のIDはrun＋内容版から一度生成し、候補ID・context・価格・band・購入領収を保存する。次の保持済み有効報酬を持つ帰還で更新し、未購入の旧候補も置換する。緊急脱出・保持成果なしの撤退では、以前の候補表を購入済み状態ごと維持する。閲覧・見送り・購入・変換・取り直し・出発・再開・帰還確認では再抽選しない。

初期や旧候補もない非適格帰還は候補0。新規適格帰還でも候補プールが有効に0なら、空表を領収とともに記録して`status:none`にする。現在のM1入力では心得候補があるため、適格帰還の空プールは通常到達しない。壊れた登録や版不一致を空候補へ隠さず拒否する。どの場合も架空の候補・無償個体で補わない。

購入は`ack_return`後のhomeで、現候補・現view・未購入表・未使用残額・明示planを確認して確定する。返還可能額を現在の資金へ足さない。D01例の未使用300＋既払200は、明示取消後500、400購入後100。ordinary個体の変換50 unitsは別操作で、実支払の全額返還に変換率を適用しない。機械方策が見送った候補も購入条件を満たせば選べる。

任意敵を残した初踏破は300 units・M1個、任意敵も倒せば400 units・M1個となる入力である。前者は未使用資金だけでは400購入に届かず、後者も全3種類の候補出現や3個購入を保証しない。初踏破で所持を自動追加せず、再訪で得た資源を何へ使うか選べるようにする試行条件であり、取得テンポが適切だと評価した結果ではない。

## 5. UIへ影響する差分

`CW-M1-view-1`、公開操作名、BD形plan、エラーの`{code,field,details}`、`display_data`だけを描く境界は維持する。内部のtarget/registry/台帳版はアダプター内で解決する。**互換拡張案は`continue_scene`の任意payload 2項目だけ**とする。

| 項目 | 追加する意味／互換性 |
|---|---|
| `advance?: boolean` | 既定trueは従来の`{scene_id}`と同じ。falseは表示の記録だけで時刻・ドロー・場面停止・報酬を進めない |
| `displayed_text_ids?: string[]` | 現scene・現viewで実際に開いた適格な本文IDだけを記録。trueで省略した場合は現在の必須本文、falseで省略なら空。任意詳細を一括既読にしない |
| false時の段階 | exploring/returnに加え、homeの現在の依頼場面でも表示記録だけ許す。trueは従来のexploring/returnの現在pauseが必要 |
| 必要な理由 | 純粋なinspectではDETAIL06を開いた事実・CL05・既読を永続化できない。表示の記録を報酬・進行と切り離すため |
| 影響先 | UI S05依頼、S15探索、S18詳細、S16/S24帰還。CO-U01のS06〜S12の準備操作名・planは変更しない。本文未接続段階ではCL05を未観測のまま扱える |
| 状態 | 設計案を保存。UI担当の受領・対応確認は未実施。CO-01最終照合へ渡す |

必須本文の公開は、その場面を返す更新が保存成功した時の公開データを指す。人が読んだ・理解したことの証拠にはしない。任意詳細の利用可能性だけではCL05を立てず、明示された表示記録を検証する。無効ID・別scene・古いview等は既存の構造化拒否で全状態を維持する。通常の再閲覧はinspectで可能で、再精算しない。

returnで準備比較は可能だが、購入・変換・次出発は不可。`return_receipt.new_unlocks`、`home.candidates`、`home.owned`、`capabilities`を別の意味で使う。保存失敗時は以前の確定viewと下書きを保ち、失敗した購入・解決・帰還を成功表示しない。今の予約から後続全手順を保証する予測や、旧BEの3局面を全行動対応として扱う変更もない。

## 6. 保存・確認範囲・次の受渡し

`CW-M1-save-1`の外枠を継承し、案件必須項目・run領収・公開場面履歴・出発時案件状態・候補版の型と整合条件を入力に記した。案件状態の欠落を初回に補完しない。旧PT-NT・研究snapshot・UI-Fの保存は自動移行しない。正常な新形式は終端と精算済みreturnを一括保存するため、通常openでcollectを補完しない。IndexedDB一括確定とJSON輸出入の案はD01を継承し、実装・ブラウザーでの永続確認は後続である。

静的照合では、出典blob・本文の一致、ST9・MODE3・ACT5・基礎16・本文等48・RW5・END8・ACH5の対応、初期配分、修飾72種のAO検証と情報署名、終了条件24組、S01を基に明示した成果台帳6例の算術を確認した。ID/type/場面条件の検査を含む。実際の候補抽選・探索手順・controller・保存装置を走らせた結果ではない。戦闘0、候補抽選0、旧AU〜BF/BD/BE/PT-NTの再実行0。新runtime・実保存・画面接続・人評価は未確認。

原本の文章訂正を求める新たな事項はない。入力の`compatibility_notes`に、任意詳細の永続化、W1/W2と過去原因の区別、素材表記、ARの自動個体化の除外、再訪の知識IDを設計側の接続差分として残した。S01原本は維持する。

今回の提出を受け、とりまとめCO-01がUI CO-U01の最終成果と公開payload拡張・入力版・保存環境を照合する。D02/D03ではカタログ注入、単一controller、案件と精算の一括確定、候補・購入・次出発を実装し、U02が画面へ接続する。そこで初めて、選んだ札組で再挑戦する理由、再訪の目的と反復の感触、購入と習得を選ぶ理由を人に確かめる。数値や入力照合だけで面白さを確定しない。BF後のA保護到達比較はCO-D05に保持する。

**CO-01Aは保存・読戻し・提出でこの単位を終了し、稼働枠を解放する。CO-01全体の完了やD02/D03の開始へ自動で進まない。**
