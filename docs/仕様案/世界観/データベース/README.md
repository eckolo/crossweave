## 案と正式仕様の区別

個別ファイルの `status` は全件「案」から始める。新しい名称、世界の来歴、札の効果を自動採用しない。既存の[世界観候補](../世界観候補.md)のA〜Eや[背景断片](../背景断片.md)は別資料として保持し、今回の件数には数えていない。

| `scope` | 意味 |
|---|---|
| 描写案 | 景色・人物・事情・物語上の接続。追加の進行機能や自動分岐の実装を約束しない |
| 既存接続案 | 現行の数量や共有ルールに接続しやすい候補。効果値・強さ・具体的な属性割当は未採用 |
| 新効果案 | 新しい条件判定、対象指定、発動時点などが必要な候補。効果の採否を設計側で検討する |

札は不思議の働きから具体的な道具になる。名前に「傘」「槌」等を必ず入れる必要はない。属性候補の流動・重圧・変容・境界は働き方の軸であり、夢や遺構などの由来とは区別する。索引の `origins` は背景の整理用で、ゲーム中の札が持つ由来情報とは別。

一致による主効果、双方が使う場、捨て場からの回収、由来と消滅の時点、有限な消費札は現行設計に従う。場の強化を自分専用にせず、対象別の行動名で攻撃・進む・壊す・探す等を表す。隠蔽と機転・一閃は現行処理を維持し、新しい足止め時間や会心確率を語から追加しない。

参照した設計は[基本設計0.52・D48〜D52](../../../確定仕様/カード探索ゲーム_基本設計.md)。修飾・複数取得・低効率変換・同種心得の限定的な同時利用を踏まえ、[心得の装備方式](../../カード探索ゲーム_パッシブ装備.md)の比較中の方式、装備枠、費用、交換率をここでは選択していない。

## 見直し・追加の手順

1. 分類の索引から個別ファイルを開き、「検討メモ」に良い点、気になる点、差し替えたい箇所を追記する。名前だけの採用と効果までの採用を区別する。
2. `status` を「案／検討中／採用／見送り／統合」から選ぶ。採用の根拠や統合先を本文へ残す。見送りでもIDを消して別案へ使い回さない。
3. 新規案は[テンプレート](TEMPLATE.md)を分類ディレクトリへコピーし、未使用の `WB-分類-連番` を付ける。名称変更時もIDは維持する。分類を変える場合もIDを安易に振り直さず、索引側の分類定義と移行方法を検討する。
4. 先頭のメタデータを更新する。値はJSON表記の文字列・配列とし、`related` には既存の安定IDを入れる。本文中の生成マーカーで囲まれた関連案は手で編集しない。
5. 索引更新を実行する。分類索引、テーマ・由来・関連索引、件数一覧、JSON、個別案の関連リンクが再生成される。具体像・接続案・検討メモは保持される。

リポジトリのルートから実行する。

```bash
python docs/仕様案/世界観/データベース/索引更新.py
python docs/仕様案/世界観/データベース/索引更新.py --check
```

Python標準ライブラリだけで動く。検査対象はIDの重複、必須項目、分類、参照先、相対リンク、生成物との一致。文章の魅力やゲームバランスの妥当性を自動判定するものではない。
