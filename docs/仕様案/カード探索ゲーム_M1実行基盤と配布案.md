# crossweave — M1実行基盤と配布案

版：0.8／2026-09-27（日本時間）／CO-M1R R1〜R4。担当：実行基盤・配布設計 `20260926-runtime-delivery`。

**ユーザー判断を受け、当面はGodotを採用して進める。これまでのC#優先を継続し、Godot 4系 .NET版＋C#、Windows 11 x64向けデスクトップアプリとして具体化する。限定M1は実行一式のZIP、将来はSteam配布へ継続。端末内ファイルへ永続化する。**

Godotの採否は今回の判断待ちから外す。正確なエンジン・SDK・TFM・C#・export templates・拡張の版、実装、性能・配布合格は後続で確定する。以下はGodot採用方針に沿った利用手順・実装計画であり、アプリ完成報告ではない。0.1〜0.7の推薦順位は比較履歴として保全し、現行選定に重ねて適用しない。

## 1. 選定と成立条件

GodotのUI・文字・2D描画・入力等の基礎と、シーンを視覚的に確認・調整できる制作環境を利用する。一般的な採用の広がりも判断材料になる。一方、独自UIの構造や演出の所有者、C#とノードの寿命・通知、テスト実行環境の区別は設計する必要がある。ユーザーの比較後のGodot選択を採用方針として記録し、個別の選択理由を推測して追加しない。

ゲーム側の主要言語はC#とする構成。Godotから独立したCoreにゲーム状態・命令・計算を置き、Godot側はノード・入力・描画・音・資源とCoreの接続を担当する。GDScriptの併用を必須にしない。独自の見た目や演出を既製のプリセットへ合わせることを完了条件にせず、Containerの配置と独自アニメーション等が同じ値を競って書かないよう境界を定める。

一つのリポジトリー・solution・普段使うC# IDEを入口とする。Coreの通常.NET試験とGodot実行が必要な画面試験を分類。Rider等の連携やgdUnit4Netは利用候補で、選んだ版の組合せを後続で確かめる。シーン・資源・project設定も版管理・レビュー対象とし、C#コードだけを見て動作確認済みとしない。[接続構造資料](../作業資料/実行基盤・配布/CO-M1R_接続構造とテスト管理.md)

### 同意された目標

| 項目 | 対象・目標 |
|---|---|
| 基準PC | Windows 11 x64、低消費電力4コア級CPU、8GB RAM、SSD、内蔵GPU。機種・GPU・ドライバーは計測前に固定 |
| 表示・入力 | 内部1920×1080、16:9、主画面の縦スクロールなし、マウス中心。ドラッグ・演出60fps、クリックの視覚応答100ms以内 |
| メモリー | アプリ関連プロセス合計500MB程度以内を常用目標。ピーク・GPUメモリー・長時間増加も別記 |
| 起動 | 初画面と操作可能時点を別測定。起動画面・読込み段階・失敗時案内で体験を補える場合、5秒超を一律不合格にしない。無表示待機・固まった表示を許す意味ではない |
| 配布 | 開発環境不要、通常権限、必要ファイル同梱、更新で保存保持。圧縮・展開・更新容量、必要な一時空き領域も記録 |
| 範囲 | 「夜潮の排水路」の準備→探索→帰還→取得・編成変更→再出発と終了再開。試作はメモリー保持可だが、M1・最終アプリは永続化必須 |

上記は開発目標で、最低動作保証や測定済みのSteam掲載値ではない。rendererはCompatibilityを最初の確認候補とし、必要な独自演出と内蔵GPUで確かめる。Godot安定版.NET・同版templates、.NET10／C#14を初期の適合確認候補にするが、SDK導入だけで組合せの成功を宣言しない。0.5の作業量比率も未実測の仮モデルで、1.5倍の上限保証ではない。

| 表示確認 | FHD基準・16:9。OS倍率100/125/150%、日本語の読める最小寸法、見た目とクリック領域を実物で確認 |
| 初期配布 | 本人向け限定ZIP。大型生成物の実際の登録先は既存外部成果物運用へ合わせて後続で固定。今回生成・アップロード・共有はしない |
| 将来のSteam | 同じアプリのRelease出力をSteamの配布単位へ登録。実績・Cloud・overlayは必要なものを別途接続。Deck・ゲームパッド・他OSを自動で含めない |
| 更新 | M1は旧版を終了し新版ZIPを別フォルダーへ全展開。アプリ専用の保存領域を継続。Steam提供後はSteam更新を主経路にする |

| 順 | 利用者の操作 | アプリの動作・確認点 |
|---|---|---|
| 1 入手 | 版付きZIPと短い案内を受け取る | 対応OS・版・既知の制約・保存場所と更新方法を確認できる |
| 2 起動 | ZIPを全展開しexeを開く | 起動画面→必要資源の読込み→開始画面。失敗時は理由と次の操作を示す |
| 3 初回 | 「はじめから」を選ぶ | 通常初期状態を生成・保存。試験用資金／fixtureを注入しない。既存保存があれば上書きの影響を明示 |
| 4 準備 | 「夜潮の排水路」を確認し、取得・編成を検討→確認→確定 | 未確定と確定を分け、支払い・所持・編成の保存成功後に確定表示 |
| 5 一巡 | 出発→本文・手札・対象・場を操作→踏破／撤退／緊急脱出→帰還結果 | 採用規則と合意済みUIの意味を実装。結果再表示で二重精算しない |
| 6 再探索 | 所持・残高を確認し、取得または編成変更を確定→再出発 | 確定した編成を使用。仮の価格・残高を配布都合で変更しない |
| 7 終了 | 探索中は「中断」して開始画面へ、拠点では変更を確定して閉じる | 中断を撤退へ変えない。保存結果を待って終了。未確定編集があれば失う内容を示し、終了／編集継続を選ぶ |
| 8 再開 | exeを開き「続きから」 | 最後の確定状態・同runへ復帰。配り直し・再抽選・二重付与なし |
| 9 更新 | 旧版を閉じ、新版を展開して起動 | 別領域の保存を読込み、形式移行前に元データを保全 |

初回のOS警告・署名は配布物で確認し、警告無効化を標準手順にしない。ここで定める体験は後続実装の受入条件案であり、操作可能なGodotアプリが既に存在することを示さない。

## 4. R3 — 保存・終了再開・更新

### 保存先と文書

Godotの`user://`を使う。`application/config/use_custom_user_dir=true`、`application/config/custom_user_dir_name="crossweave"`を設定する案により、アプリ表示名や配布フォルダー名から保存領域を独立させる。通常版は`user://saves/local/m1.json`、Windows実体は`%APPDATA%/crossweave/saves/local/m1.json`。[G4]

.NETのファイル処理を使う場合は、Godot側で`ProjectSettings.GlobalizePath`によりOSパスを解決して保存部へ渡す。CoreにはGodot型・パス解決を持ち込まない。保存部は書込み先を一元管理し、取得・作成失敗時にアプリ展開先へ黙って退避しない。通常保存・検査用保存・ログ／設定を区分し、試験が通常セーブを壊さないようにする。

保存形式は版付きゲーム状態文書（JSON候補）。所持・残高・編成・候補・知識・案件状態・探索run・乱数状態・手札／山／場／回収山・帰還精算を同一確定単位に含める。ID・数値・列挙・乱数方式と版を明記し、表示ノードや途中のアニメーションを保存原本にしない。

旧`CW-M1-save-2`のJS内部構造や試作保存全件の自動移行は初期M1の前提にしない案。保存例は保全する。旧データ持越しが必要になった場合に対象を定めて明示importを設計する。**M1配布開始後の保存保持・更新互換は必須**。配布場所の変更とセーブ場所の変更を結び付けない。

### 保存時点・失敗・終了

- 新規開始、取得／編成の確定、探索の一手と自動処理が揃った境界、帰還精算で保存する。確定表示は保存成功後。未確定編集・予測・詳細表示を支払い済みとして保存しない。
- revision・処理済み操作を単一の書込み経路で管理し、重複クリック・再送・再表示で二重決済・二重報酬を起こさない。
- 同じ保存領域の書込み所有者は一つ。OS／ファイルロック等を設計・確認し、Godotの採用だけで単一起動・原子的保存が完成したと扱わない。
- 一時ファイルへの書込み→flush／検査→置換、直前の完全保存の保全を候補にする。標準APIやrenameだけで停電耐性を保証しない。書込み失敗・中断・破損・二重起動を実物で検査する。
- 終了は進行中の保存結果を待つ。強制終了後は最後の完全な確定状態へ復帰し、未保存操作の成功を保証しない。読み込めない保存を空データとして初期化しない。
- 更新時は元保存を保全して形式移行し、失敗時の復旧・未対応形式・旧版起動時の扱いを定める。展開先を変えた更新でも継続できることを確認。

Steam段階ではSteamID等による保存区分と既存local保存の移行を別途決める。Cloudは確定ファイル指定のAuto-Cloudを初期候補とし、一時ファイルや端末固有設定を除外する。API接続・overlay・Cloud・アカウント切替は別段階の確認で、GodotSteam等の拡張・C#呼出し・対応版を採用済みとはしない。既存Steam調査の未確認を保全し、限定M1の完了条件へSteam全機能を追加しない。

## 5. R4 — 後続・担当・依存

[後続実施計画0.8](../作業資料/実行基盤・配布/CO-M1R_後続実施計画.md)に具体的な担当案・編集境界を示した。

**Godot採用方針の受領→RD-ENV-02（版と作成／実機経路）→RD-PROOF-02（代表場面）→D04B（本体・UIの新実装と統合）→RD-SAVE-02（正式保存・終了・更新）→RD-PACK-02（配布物）→D04（実操作・保存再開）→P02（試遊）→CO-02（M1受入）**の順を提案する。保存契約の設計はD04Bの初期から行い、画面完成後まで放置しない。

D04Bはアプリケーション実装・統合の責務。既存共通本体の管理担当がゲームバランス検討だったことを理由に、新アプリ全体を同Workへ割り当てない。規則・経済・丸め・乱数・精算等の意味に具体的な疑義がある場合だけ原本担当へ照会する。D04E/Aのブラウザー固有作業は保留を維持し、目的をGodotの作成・ファイル保存・終了再開・書込み所有者の確認へ置き換える案。
