# crossweave — M1実行基盤と配布案

版：0.7／2026-09-27（日本時間）／CO-M1R R1〜R4。担当：実行基盤・配布設計 `20260926-runtime-delivery`。

**現行推奨：MonoGame＋C#（DesktopGL、.NET10／C#14を初期確認候補）、Windows 11 x64向けネイティブアプリ。限定M1はZIP配布、将来はSteam配布へ継続し、端末内ファイルへ保存する。方式の正式採用・実装・性能確認は未了。**

0.7では[用途と普及度](../作業資料/実行基盤・配布/CO-M1R_用途と普及度の比較.md)を比較。一般的な採用の広がりではGodotが優勢で、両方に商用／Steam事例がある。現在のC#・独自構造・テスト把握の優先条件からMonoGame推奨を維持するが、一般的な普及度で上回るという判断ではない。Godot全体の検出件数をC#利用率に置き換えず、MonoGameの外部ツール統合の負担も評価する。

0.6では、作業量1.5倍程度の許容と、C#コード・テスト・IDEから構造を把握しやすいことを重視する条件により、推奨をMonoGameへ変更した。[接続構造とテスト管理](../作業資料/実行基盤・配布/CO-M1R_接続構造とテスト管理.md)を現行判断とする。GodotのC#は同じプロセス内のAPI連携であり、外部通信ではない。GodotでもIDE・テストを集約可能だが、シーン／エンジン側の構造は残る。MonoGameでもネイティブ依存・実機検査は残る。1.5倍を保証上限にしない。以下0.5以前は判断の履歴。

0.5では[AI支援時の作業量予測](../作業資料/実行基盤・配布/CO-M1R_AI支援時の作業量予測.md)を追加。AI支援後の限定M1総作業をGodot=100と置き、MonoGame＋補助120〜150、自作多め140〜190を未検証の計画枠とする。人の有効作業量の相対値であり、確定工数・日数・統計的区間ではない。Godot側の適合調整で差が消える場合も含め、後続の代表作業で校正する。推奨・採用状態は変更しない。

0.4では[GodotとMonoGameの多角比較](../作業資料/実行基盤・配布/CO-M1R_GodotとMonoGameの多角比較.md)を追補。推奨は維持し、文字・定型UIの基礎を利用する利点と、画面・入力・描画構造を自分で管理する利点を区別した。MonoGame＋UI補助も比較対象とし、性能優劣は未判定。GodotはCompatibility、MonoGameはDesktopGLをそれぞれ最初の確認候補とする設計案。

0.3ではユーザーのC#への習熟・好みと、独自UI／演出を大きく自作する可能性を受領。推奨言語をC#へ変更し、MonoGame＋C#を主要対抗候補へ上げた。[C#対応と独自UIの詳細](../作業資料/実行基盤・配布/CO-M1R_CSharp対応と独自UI.md)を参照。方式の正式採用とは区別する。

0.1のElectron推奨は、既存本体・UIを再利用する前提での結論だった。ユーザーが既存コードを試作として全面作り直してよいと明示したため、その加点を外して推奨を変更した。起動体験・合意した性能目標・配布容易性を追加して評価した。[再比較と一次資料](../作業資料/実行基盤・配布/CO-M1R_性能・配布条件での再比較.md)と上記0.3の追加検討を選定根拠とする。[0.1の履歴](https://github.com/eckolo/crossweave/blob/f6c7dfd536ea603d65f9a1d66f152b9c8895c86b/docs/仕様案/カード探索ゲーム_M1実行基盤と配布案.md)は保全されている。

## 1. 選定の結論と条件

MonoGameは独自UIの構造・入力配送・演出状態をC#中心に設計し、通常の.NET solution・テストから把握しやすくできる。C#への習熟、独自UI、追加作業の許容、管理容易性の優先を合わせて推奨する。Godotの文字・UI・制作支援を借りる利益は残り、主要対抗とする。MonoGameでは不足する機能を限定して自作または補助ライブラリーで用意し、確認・保守も担当する。Unity、Defold、GameMaker、Tauri、Electron、NW.js、URL配信も前版で再比較した。MonoGameがGodotより高速・省メモリーだという実測はない。

言語案はC#。Coreは描画から独立した通常のC#に置き、MonoGame側は起動・入力収集・描画・音・資源と接続を担当する。.NET10／C#14とDesktopGLを初期確認候補とし、SDK・MonoGame・Content builder・フォント／UI補助の版を固定して確かめる。全UIの完全自作や汎用エンジン制作を前提にしない。補助を増やせば構造の理解・版管理の負担も増える。ランタイム・GC・GPU負荷は未測定。既存JSのAPIやDOM/CSSを必須構造にせず、採用済みルール・了承済み操作意図と固定した試験目的を入力とする。

### 同意された開発目標と未確認

| 項目 | 目標・扱い |
|---|---|
| 基準PC | Windows 11 x64、低消費電力の4コア級CPU、8GB RAM、SSD、内蔵GPU。具体機種・ドライバーは測定前に固定 |
| 表示・入力 | 内部1920×1080、16:9。ドラッグ・演出60fps、クリックの視覚応答100ms以内。マウス中心の既存操作意図を継承 |
| 常用メモリー | アプリ関連プロセス合計500MB程度以内を目標。ピーク・GPUメモリー・長時間増加・Steam等との同時起動も記録 |
| 起動 | 初画面と操作可能になるまでを別計測。起動画面・現在段階・失敗時案内で体験を補える場合、5秒を超えても一律不合格にしない。無表示の長時間待機や固まった表示を許容する意味ではない |
| 配布 | 開発環境不要、通常権限、必要ファイル同梱、更新でセーブ保持。容量は圧縮・展開・更新・一時空き領域を別計測 |
| 未確認 | 全項目未測定。これは最低動作保証・Steamストア掲載用確定値ではない。MonoGame版・backend・補助・素材量を固定したRelease版で確認する |

現在のWorkはLinuxで、dotnet／MonoGame／Godotを導入・実行していない。WindowsのGPU・マウス・DPI・Steam実機確認には別の実行経路が必要。Linuxで生成やheadless検査が可能な製品機能と、このWorkで確認済みであることを混同しない。

方式採用後の最初の後続作業は、小さなMonoGameサンプルで独自カード配置・日本語・ホバー拡大・短ホールドドラッグ・詳細窓・予測矢印・演出中の再入力、起動表示・保存終了再開・配布と、同じsolution／IDEからコードとテストを追えることを確かめる案。実物で条件が合わなければ原因を分析し、必要な候補だけ再比較する。全候補を同時に実装しない。

| 8 再開 | exeを開き「続きから」 | 最後の確定状態・同run・進行へ復帰。配り直し・再抽選・二重付与なし |
| 9 更新 | 旧版を閉じ、新版を展開して「続きから」 | 保存を別領域から読込み、必要な形式移行前には元データを保全 |

## 4. R3 — 保存・終了再開・更新

### 保存先と形式

.NETの`Environment.GetFolderPath(Environment.SpecialFolder.ApplicationData)`を基点として、固定したアプリ専用領域へ`Path.Combine`等でパスを組み立てる案。通常版のWindows保存先案は`%APPDATA%/crossweave/saves/local/m1.json`。アプリ表示名・展開フォルダー・実行時作業ディレクトリーに依存させず、保存先の取得／作成失敗を黙って別の場所へ逃がさない。Steam版はSteamID等による利用者区分を別階層へ設ける案とし、既存local保存の移行を無断で行わない。[接続構造とテスト管理D1、再比較S3]

保存はバージョン付きのゲーム状態文書（JSON候補）とし、表示ノードや一時アニメーションをそのまま保存しない。所持・残高・編成・候補・知識・案件状態・探索run・乱数・手札／山／場／回収山・帰還精算の状態を同一確定単位に含める。ID・整数値・列挙値・乱数の表現と版を明示する。

旧`CW-M1-save-2`のJS構造を新実装の必須内部形式とはしない。旧試作保存の全自動移行は初期M1の必須にしない案とし、持越し対象が必要になれば明示importを別に定義する。**M1配布開始後の保存保持・更新互換は必須**。旧保存例は仕様照合資料として保全する。

### 保存する時点と失敗

- 新規開始、取得／編成等の確定、探索の一手と自動処理が揃った境界、帰還精算で保存する。確定表示は保存成功後。予測・詳細表示・未確定編集を購入済みとして保存しない。
- 単一書込み経路でrevision／処理済み操作を管理し、重複操作や再送で二重決済を起こさない。旧JSのStore APIやIPCを必須にはしないが、同じ安全性を受入条件にする。
- 同じ保存領域の書込み所有者を一つにする。フレームワークの採用だけで単一起動・原子的保存が完成すると扱わず、OS／ファイルロック等を後続で設計・検証する。
- 一時ファイル→flush／検査→置換、直前の完全保存の保全を候補にする。名前変更や標準ファイルAPI単独で停電耐性を保証しない。保存中断・書込み拒否・破損を実物で確認する。
- 終了時は未完了保存の結果を待つ。強制終了後は最後の完全な確定状態へ戻し、成功していない操作は保証しない。読み込めない保存を空データとして初期化しない。
- 更新前の保存を保全し、新形式への移行・未対応形式・旧版へ戻した場合を定義する。M1以降の新版で保持されるものを検査する。

Steam Cloudはまずファイル指定のAuto-Cloudを候補にする。同期対象は確定セーブに限定し、一時ファイル・キャッシュ・端末固有設定は除く。起動時同期、終了前の確定保存、2台間、オフライン、アカウント切替、競合を確認する。実績やSteam API連携をM1の全機能へ直結させず、接続部分を分離する。必要なC#用Steam接続ライブラリーは別途版・保守元・配布条件を確認する。GodotSteamの確認待ちをMonoGame案の前提にしない。

## 5. R4 — 後続と判断

[後続実施計画0.7](../作業資料/実行基盤・配布/CO-M1R_後続実施計画.md)へ責務・編集境界・依存を整理した。MonoGame採否→作成／実機経路→代表サンプルで性能・配布確認→本体・UI新実装→永続化／終了→配布→技術確認→人の試遊→M1受入の順を提案する。

D04Bは既存UIファイルの機械的受領だけでなく、新しいアプリ全体の実装・統合の責務へ再設定する。ゲームバランス検討に本体再実装・UI統合・配布を一律に割り当てない。元担当には規則・経済・丸め・移行の意味が必要な具体点だけを渡す。

今回の依頼対象は方式・推奨・後続計画と文書保存まで。MonoGame採用は未決で、SDK導入・実装・CI・公開・素材制作へ自動続行しない。次の判断案はMonoGameで代表サンプルの確認へ進めること。得るものはC#中心の構造・テスト管理と独自UI制御で、追加のUI基礎・確認・保守を引き受ける。工数倍率・性能は未保証。日本語・UI基礎や制作支援の負担が大きい場合はGodotへ再評価する。
