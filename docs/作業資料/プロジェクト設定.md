## 差し替え用の全文

```text
【正本・参照先】
GitHubリポジトリ eckolo/crossweave を、設計文書・コード・軽量資料の正本保管先とする。特定ブランチを恒久的な最終正本とは定めず、作業先・同期元・統合先はWorkごとに管理する。ブランチへの保存・統合と、仕様の正式採用は別である。

初期案内（2026-09-09の設計ひな形作成段階）は dev_design_tmp_assembly の README.md と docs/作業資料/Work分担.md。これは現段階の集約先を見つける入口であり、全Workの更新先を固定する指定ではない。明示された引継ぎや後継の案内を優先し、既定ブランチ・名前・更新日時だけで正本や作業先を推測しない。

【Work・chat開始時の必須設定】
各Work・chatでプロジェクトの実作業を始める前に、作業目的とWorkID、および次の4項目を必ず定める。
1. 作業ブランチ：通常の編集・コミット・Push先。
2. 必須同期元ブランチ：変更を取り込んで追随すべき前提。不要なら理由付きで「なし」。
3. 成果の統合先：成果を戻すブランチと統合担当。統合しない作業は理由付きで「なし」。
4. 共通文書の担当：対象ファイルまたは節ごとの更新担当Work・担当ブランチ、自Workの直接更新範囲。担当外は変更案を自Work側に保存し、既存担当へ渡す。

ユーザー指定、既存Work設定・引継ぎ、現段階の分担、作業内容の順に確認し、足りない項目はAIが既存の権限・担当を侵害しない範囲で自動決定する。ブランチ名や形式的な登録のためだけに確認待ちにしない。引継ぎでは設定を継承して最新状態を確認し、別の並行作業なら分離する。共通文書の既存担当を一方的に変更しない。

設定は開始時に短く提示し、自Workの作業ブランチの docs/作業資料/Work/<WorkID>.md へ保存する。登録のための読み取り・ブランチ作成・設定保存は先行してよいが、4項目を定めずに本体の編集・検証を始めない。読み取りだけの相談でも4項目と「更新なし」を明示し、そのためだけのブランチ新設・登録コミットは不要。保存作業へ移る前に正式登録する。

Work分担.mdを登録索引として、WorkID・作業ブランチ・設定ファイルの所在・役割を案内する。登録先は当該段階の集約ブランチを明示する。自Workの登録情報だけの更新は通常の運用作業として行ってよいが、他Workの割当変更や成果の逆方向統合は含まない。他Workの設定を取り込んでも自Workの設定と取り違えない。

【ブランチの自動命名・作成】
新しい独立作業では、原則 <種別>/<内容>-<YYYYMMDD> をAIが自動命名する。種別は design・verify・playtest・impl・ops 等、内容は短い英小文字のkebab-case、日付は作成日の日本時間とする。既存名・同名競合・Gitの命名制約を確認し、競合時は -02 等を付ける。同じ名前があるだけで他Workのブランチを再利用しない。

派生作業は、確認した依頼元・同期元の最新コミットから作成する。命名・通常の作業ブランチ作成・自Workへの保存は個別確認なしに実施してよい。ただし同一作業の引継ぎは既存ブランチを再利用し、チャット新設だけを理由に増やさない。既存ブランチの自動改名や、作業途中の無断切替は行わない。

【同期・検証・統合】
作業単位の開始時に、自Workと必須同期元の最新HEADを確認し、未保存変更を保全したうえで未取り込み差分を取り込む。取り込み後のREADME・基本設計・要検討事項・関連検証資料を読む。単なる取得や参照を統合完了とせず、確認したHEAD・取り込み済みコミットを記録する。

成果反映前にも自Workと同期元を再確認する。変化があれば差分と影響を確認し、必要な統合・再検証を行う。ファイル保存のたびに無条件マージせず、まとまった作業単位で行う。検証・試遊は実際に用いるコミット・入力・条件を固定して記録し、進行中の試験を同期に合わせて勝手に差し替えない。

必須同期元は原則0〜1本、複数なら理由と順序を記す。循環した必須同期や、自Work自身を同期元に指定することは避ける。参考に読むだけのブランチは参照先として区別する。同期元への逆方向統合は自動許可されず、成果は指定した統合担当が許可範囲内で確認・統合する。

【保存・競合・権限】
通常の更新・日本語の簡潔なコミット・自Workの作業ブランチへのPushは逐一確認不要。担当範囲の変更を意味のある単位にまとめ、他Workやユーザーの変更を保全する。古いファイル全体で上書きしない。公開済み履歴を書き換えない更新を用い、競合や並行更新で拒否されたら再取得・再統合する。保存後のGitHub上のコミットと内容を確認してから完了を報告する。

形式的に解消できる競合は処理を進める。取り込み方向、既存担当、仕様意図に実質的な選択が残る場合だけ、影響する更新を止め、具体的な選択肢を示す。独立した安全な作業は続行する。強制Push、履歴改変、master/main等への統合、公開範囲変更は別途確認する。統合先への指定だけでこの確認を免除しない。

【GitHubとDropbox】
通常文書、継続編集するコード・入力、小規模な結果はGitHub。READMEと docs/検証/外部成果物.md が指定する大型成果物だけはDropboxの gist/crossweave を正本とし、正確なパスは一覧に従う。同じファイルを両方で独立更新しない。旧Dropbox文書は保全用コピーとし、Dropbox連携でローカルの .git を書き換えない。旧作業ツリーの整理では移行記録を参照し、未保全の差分を破棄しない。

外部成果物は元ファイルを保全し、利用ツールの権限・確認条件に従って更新する。一覧に版・対応条件を記録し、複数Workで同じ固定名ZIPを同時更新しない。

【仕様区分・検討の継続】
採用済み仕様、未採用案、検証用仮条件、過去記録を区別する。仕様は docs/確定仕様/、案は docs/仕様案/、経緯・進捗は docs/作業資料/、試験は docs/検証/ で管理する。文書名は原則固定し、版は文書内で管理する。採用時には案・要検討事項・参照先も整合させる。古い会話や記録だけで解決済みの判断を蒸し返さない。

正式仕様や目指す遊び方の変更・仮条件の正式採用にはユーザー判断を要する。許容された効果の方向だけで具体的な札・数値まで確定しない。試行仮設定は目的・条件・維持前提・結果・限界を記録して自律的に検証する。最重要の評価軸は「これで面白いかどうか」であり、数値や合法手数だけで面白さを実証した扱いにしない。

試遊待ちと、試遊なしに進められる検討・検証を分離する。依頼に関係する検討・検証・記録・保存は、ユーザーの採用判断・意図確認が必要になるまで継続する。通常保存や仮設定の許可待ちだけで停止しない。必要な判断には停止理由と選択肢・根拠を示す。

設定文は docs/作業資料/プロジェクト設定.md で管理する。文書への反映とChatGPT設定画面への適用は別として報告する。開始時の手順はAIが作業を始める際に行うもので、チャット作成イベントによる自動起動や常時監視を前提にしない。
```

## 改訂の根拠と範囲

ユーザーの補足：dev_design_tmp_assembly は設計ひな形作成の作業ブランチであり、現段階の成果が結果的に集約されているだけ。恒久的な最終正本ではない。

今回の要求：Work・chatの開始時に、作業先・必須同期元・統合先・共通文書担当を必ず定める。ブランチ名も作業内容から自動で決める。既存作業の引継ぎと新しい独立作業を区別し、命名確認だけで止まらない手順として具体化した。

通常の登録情報更新は運用作業であり、ゲーム仕様の採用権限やmaster等への統合権限を追加するものではない。共通文書の担当を奪ったり、同期しただけで進行中の試遊条件を変えたりしない。

開始設定の書式・現段階の分担は[Work分担](Work分担.md#work-start)、今回の作業設定と確認範囲は[作業記録](Work/20260909-work-routing.md)を参照。
