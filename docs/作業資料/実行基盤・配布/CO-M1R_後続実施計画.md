## 3. C#・Godot・テストを把握する構成案

一つの`apps/crossweave-godot/`配下のsolutionを入口にし、次の責務を置く。これはパス案であり、今回ディレクトリーやコードを作成しない。

| 領域案 | 内容・境界 |
|---|---|
| `Core/` | 純C#のゲーム状態・命令・計算・必要な表示状態。Node/Resource等のGodot型を参照しない |
| `Infrastructure/` | ファイル保存・形式移行・ログ。保存先は起動側で解決して渡す。描画に依存しない |
| `Godot/` | `project.godot`、C#ノード、シーン、資源、入力、描画、音、起動時組立て。ゲーム状態の原本をUIへ重複保持しない |
| `Tests/` | Core単体、ファイル連携、Godot統合を区分。同じsolution/IDEから実行できる構成を確認 |
| `packaging/` | Release export手順、manifest、案内。認証情報を通常設定へ混ぜない |

アプリ担当がCore／画面と状態契約、基盤担当が保存・起動・配布を所有する案。同じ担当が順番に実装してよい。実ファイルが決まったら割当表で境界を固定する。

- Godotのシーン・資源・設定をC#と一緒にレビュー。配置、当たり判定、演出の同一プロパティに複数の所有者を作らない。
- Coreは通常の.NET試験。Nodeやシーンを動かす試験はGodot runtimeが必要と明示。gdUnit4Net等はadapterとの版適合を確認して採用する。単体試験だけで実入力・描画・OS保存を代用しない。
- 普段使うIDEを入口にまとめる。Rider等の連携は候補で、IDE購入や乗換えを今回の完了条件にしない。Godotエディターはシーン・資源の制作確認に使用する。
- 札追加、文章変更、窓寸法、演出順の変更時に追うファイルと人の作業時間を記録。0.5の相対工数を実測で校正する。AI生成量を検証・保守の完了量と同一視しない。

## 5. ゲーム仕様の判断が必要な具体点

原本に従った実装・同等性確認はアプリ担当の責務。次の意味が不明、または変更が必要な場合だけ、再現入力・現仕様・候補・影響をゲームバランス検討へ渡す。

1. 数値の丸め、同時解決順、乱数・配札・時刻の扱いが言語差で変わる場合。
2. 取得・変換・帰還による残高、個体、候補寿命、知識、喪失が変わる場合。
3. 再開境界の変更で巻戻し・再抽選・二重精算・中断時の撤退扱いが生じる場合。
4. 必要になった旧保存移行でゲーム上の意味が失われる場合。

パス、保存キュー、UIイベント重複、ノード寿命、export依存等はアプリ／基盤で扱う。原本担当への情報提供依頼や同時稼働を、通常の調査・資料化の開始条件にしない。

## 6. 受渡し・配布

新規アプリ領域・統合枝・担当ファイルは、とりまとめが後続着手時に本案から確定する。各Workは計画全体→共通仕様・本体の必須同期を行い、固定成果を順次受領する。今回の1Work条件を無断で拡大しない。

大型ZIPは既存の外部成果物運用に従い、登録済み領域の版別新規パス（例`releases/m1/<版>/crossweave-m1-<版>-win-x64.zip`）へ置く案。現時点の生成・登録・アップロード・共有は0。GitHubにはコード・軽量資料・manifestを保存する。

受渡しにはソースSHA、エンジン.NET／SDK／templates／renderer／拡張版、生成手順、配布hash・内容一覧、基準PC、性能の測定法と結果、保存形式・互換、通常開始とfixtureの区別、未確認一覧を含める。利用者には入手・起動・中断・終了・再開・更新の短い案内を渡す。

Godot採用の方向はユーザーが判断済み。とりまとめはCO-M1Rを成果受領後に完了へ更新し、D04E/A・D04B・P02等の依存と割当を再設定する。本書保存は、とりまとめの受領や後続着手を意味しない。
