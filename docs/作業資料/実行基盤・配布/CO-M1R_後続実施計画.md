# CO-M1R 後続実施計画

版0.1／2026-09-26。**全て後続割当案・未着手。** 推奨A（Electron／Windows／ファイル保存）採用時の順序。[方式案](../../仕様案/カード探索ゲーム_M1実行基盤と配布案.md)を入力とし、とりまとめが正式な担当・統合先・依存へ反映する。今回はCO-M1Rの1Workだけで終了する。

## 責務の分類と編集境界

| 担当案 | 責務・理由 | 編集境界・受渡し |
|---|---|---|
| アプリケーション統合・実装（新しい独立Work案） | 完成した本体とUIを一つの起動物へ接続し、使用版と依存を固定する。D04Bはこの責務 | 新しい作業枝`impl/m1-application-<開始日>`を技術最新HEADから作成する案。選択受領したUI差分、アプリ入口／組立・統合記録を担当。元UIに新しい独自版を併設しない |
| 実行基盤・配布（本Workの後続タスクとして継続する案） | 対象OSのホスト・保存媒体・終了／更新・パッケージ・配布物を一体で保証する。方式案と責務が連続するため継続が自然 | 後続で明示割当された新規`apps/desktop/`等のホスト・preload・FileStore、package/lock、配布生成、専用確認。アプリ統合枝へ、統合担当が必要差分を受領。今回の設計枝へ無断で実装を開始しない |
| 実機確認（実行基盤・配布の担当機能＋必要な実機操作者） | 起動物・OS・保存・更新の実在を確認。保存実装者が準備できる技術確認と、対象PCでの表示・入力を区別 | 専用`docs/検証/実行基盤/m1-desktop/`等へ版・入力・結果。利用者の通常保存を検査で上書きしない |
| UI改善（具体的な問題があるときだけ既存Workへ） | 了承済み画面の表示・操作と専用部品の原本管理 | `docs/検証/UI/readability/`の修正。統合担当は再現・期待結果を渡す。終了通知等も共通UI原本の変更が必要なら小さい依頼に分ける |

| とりまとめ（既存） | 採用判断の記録、後続割当と統合先、優先度、CO-02受入 | 計画フォルダー原本だけ。統合コード・環境整備・保存実装を集中させない |

上記は必要な仕事の区分であり、7Workを起動する指示ではない。連続した成果は一担当で順番に扱える。反対に、新規／既存という区分より編集境界・目的を優先する。

**成果統合先の提案**：M1の実行一式は新しいアプリ統合枝を当面の候補とする。共通本体の原本は`dev_design_tmp_assembly`、UI原本はUI枝のまま。原本の担当を移転しない。従来の「設計枝へUIを統合」は未実施の計画なので、とりまとめが本提案と比較して受領先を確定してから実施する。masterへの統合は含まない。

同期は全後続Workで計画全体を先に取り込み、必要な技術前提を後にする。アプリ統合担当と基盤担当を相互の必須同期元にはしない。アプリ統合担当は基盤の固定成果を受領し、基盤担当は固定された統合入力を使う。専門成果の取り込み後に最新の計画コピーを再照合する。

負担は現構成からの推定であり人日見積りではない。特に4は文書保存の原子性とWindows上の例外処理、6は実機確保に不確実性がある。1で実行経路、2で対象差分が確定した時点で後続担当が見積りを更新する。

## 配布保存と受渡し

配布ZIPは大型生成物となるため、既存方針に合わせDropboxの`/久乃銑泉/gist/crossweave/`配下を第一候補とする。**新規パス案**は`releases/m1/<版>/crossweave-m1-<版>-win-x64.zip`。現時点では存在・登録・upload・共有を行っていない。

RD-PACK-01で実サイズ・ハッシュ・対応コミットを揃え、`docs/検証/外部成果物.md`原本担当へ追加案を渡す。登録と保存先の確定後にuploadし、本人がダウンロードできる入口を提示する。共有先を増やす必要がある場合は対象を指定して扱い、恒久的な公開URLを推測しない。GitHubにはコード・軽量資料・manifestを保存する。二重の正本や同じ固定名ZIPの上書き競合を作らない。GitHub Releasesやストアへ切り替える場合は、その配布経路の採用と公開範囲を別途定める。

作成・確認担当への受渡しには、ソースSHA、UI受領manifest、生成コマンド、package lock、ZIP hash、保存形式・互換対象、通常開始と検証fixtureの区別、未確認一覧を含める。利用者にはZIPと短い起動・更新・再開案内を渡す。ビルド手順を遊ぶ人の操作にしない。

## ゲームバランス検討へ分離する具体点

現時点で新しいルール判断は必要と判定していない。次の問題が実際に起きたときだけ、具体例・期待値・影響を付けて既存原本担当へ渡す。

1. 同じ保存を開いてもmode／案件状態や乱数・手札が変わる場合、その変更が既存規則違反かを確認する。保存媒体のパスやアクセス権問題は基盤で扱う。
2. 取得・変換・帰還の二重適用、残高・所持・候補に意味上の矛盾が出た場合、既存経済契約と照合する。IPC応答喪失だけなら基盤・接続の修正対象。
3. save1／旧draft移行で失われる項目がある場合、互換の意味を原本担当へ渡す。UI名目で旧習得費の返還や自動購入を追加しない。
4. 自然初回の残高で高額候補を買えない等、既存仮値に依存する試遊上の制約は記録する。接続を成立させるために報酬・価格を水増しせず、既存の適切な保存例を別試験で使う。

「中断すると撤退扱いにする」「一手前へ任意に戻す」「配布更新時に候補・探索を再抽選する」等は方式設計の裁量で追加しない。正式ルール変更が必要ならユーザー判断へ上げる。

## とりまとめが反映する事項

- CO-M1RはR1〜R4提出済み・方式判断待ちとして受領し、M1完成と区別する。
- 採用時に対象OS・入力・配布形態と後続担当・アプリ統合先を設定する。現在の原本担当は維持。
- CO-D04Bの責務をアプリケーション統合として具体化し、D04E/Aの保留・置換・縮小を上表で更新する。
- Windows作成／実行の未確保を外部条件として管理し、未確認を成功扱いにしない。今回の成果提出の阻害とはしない。
- 既存仮データ・固定試験・未公開ビジュアルの保全を維持。今回の後にどのWorkを稼働するかは次の割当で定める。
