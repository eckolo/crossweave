# CO-M1R — GodotとMonoGameの用途・普及度

版0.7／2026-09-27（日本時間）。WorkID `20260926-runtime-delivery`。ユーザーの「一般的に用いられている方向性や用途・シェア」の追加質問への調査。方式の正式採用・実装・性能測定ではない。

## 1. 結論

**一般的な採用の広がりと近年の勢いではGodotが優勢。MonoGameはC#のコードを中心に独自の構造を作る用途で実績のある、利用規模の小さい選択肢。** 両者とも商用制作に使われ、MonoGameを試作専用・既に廃れた基盤と扱う根拠はない。

公開機能・事例・普及指標からの整理であって、開発者の用途を網羅的に測定した結果ではない。Godotが大きいことと、crossweaveの独自UI・テスト管理に適することは別の評価軸。0.6のMonoGame＋C#推奨は維持するが、普及・制作支援・参加者を増やす際の標準化ではGodotの利点を明示する。正式採用は未決。

## 2. 方向性と用途

| 観点 | Godot | MonoGame |
|---|---|---|
| 提供するもの | エディター、ノード・シーン、UI、2D／3D等を統合したゲームエンジン | 描画・入力・音・Content等を提供する.NETフレームワーク。必要な制作環境を組み合わせる |
| 制作の中心 | シーン・資源を組み、コードで挙動を作る。エディターによる配置・調整を活用 | C#コードを中心にゲーム構造・画面構造を作り、補助や独自ツールを選ぶ |
| 想定しやすい制作形態 | 個人・小規模チーム、ゲームジャム、2Dや3Dのインディー制作。コード以外の編集も分担したい場合 | C#経験者を中心とする個人・チーム。構造を所有したい、独自ゲーム基盤を育てたい、XNA系資産・知識を使いたい場合 |
| 公開事例で目立つ用途 | 2Dアクション、カード／ローグライト、RPG、パズル、3Dホラー、制作ツール | 2Dアクション、プラットフォーマー、生活シミュレーション等の商用インディー。自作エンジン／ツールの下地 |
| 3Dへの展開 | シーン編集、モデルの取込み、ライティング等の統合環境を利用できる | 3D描画APIはあるが、同等の制作環境を標準で一式受け取るわけではない |
| 言語・情報 | GDScriptとC#等を含むエコシステム。Godot全体の利用数をC#の利用数へ置換できない | フレームワーク・公式資料・サンプルの中心がC#。母数は小さいがC#のまま参照しやすい |

根拠はGodot Features、MonoGame公式入門・ドキュメント、両者の公開事例。[G1、M1、M2、G2] MonoGameにもContent用のツールや外部エディターはある。「ゲーム全体の統合エディターを必須にしない」と「一切エディターがない」を混同しない。

ジャンルだけでは選べない。カードゲームは両方で作れるし、アクションだからMonoGame専用という制約もない。ユーザーが自分でプログラミングする範囲と、視覚編集・文字・UI基礎を任せる範囲で適合が変わる。

## 3. 採用事例の読み方

| 基盤 | 公開例 | この比較で言えること |
|---|---|---|
| Godot | Slay the Spire 2、Brotato、Dome Keeper、Cassette Beasts、Buckshot Roulette | カード／2Dだけでなく複数ジャンルの公開例がある。公式Showcaseの掲載を確認 [G2] |
| MonoGame | Stardew Valley、Streets of Rage 4、Celesteでの利用 | 公式ドキュメントが採用例として紹介。商用完成品の制作・移植に使われる [M1、M2] |

本作に近いカードゲームの例として、Slay the Spire 2の開発元Mega CritはGodot採用をFAQで明示し、Steam Early AccessでのWindows／macOS／Linux提供を説明している。[G3] これはGodotがカードゲームや独自画面の商用制作に使える具体例であり、本作の仕様・性能が検証済みという意味ではない。今回参照したFAQはC#利用率の根拠にはならない。

Celesteについて開発者のツール紹介を読むと、C#＋XNAに加え、クロスプラットフォーム向けにFNA／MonoGameを使用し、その上に改造したMonocle、別途フォント・音・レベル編集のツールを組み合わせている。[M3] 「有名作がMonoGameを使った」だけから、全機種・全版がMonoGame単体で完成していると説明しない。この事例は、コード中心の制作でも外部ツールを選ぶ責務が残ることをよく示す。

## 4. Steamでの検出件数

2026-09-27 JSTに取得したSteamDB TechnologiesのEngine一覧は次の通り。[S1]

| 技術分類 | 同じ一覧におけるゲーム検出件数 |
|---|---:|
| Unity | 66,424 |
| Unreal | 20,782 |
| Godot | 5,063 |
| MonoGame | 475 |

Godot／MonoGameの検出件数比は約10.7倍。ただし**世界の開発者シェア・Steam販売本数・売上・成功率・C#限定の利用率ではない**。全エンジンの件数を合算して市場シェアの分母にもしていない。

SteamDBは配布ファイルの名称から自動判定し、全作品を把握できず、検出漏れ・誤分類もあると明記する。検出に必要なファイル一覧を取得できる範囲にも制約がある。集計一覧はゲームのみだが、個別技術ページには他のapp種別も表示される。個別ページの表示上限「100 products」を総数と扱わない。[S1]

XNAとFNAはMonoGameとは別分類であり、重複・版・対象機種を確認せずMonoGameへ加算しない。同じ作品が歴史的に複数の技術を使う場合もある。取得値は変動する参考値として観測日付きで保持する。

## 5. 開発者調査・成長

GDC 2026の公式公開要約は、調査全体で2,300人超の業界関係者を対象にし、開発者の主要エンジンとしてUnreal42%、Unity30%を示す。Godotについては**新しいインディー開発者の層で11%**と記載する。[S2] 対象集団が異なるため、Godot全体11%とも、Steam件数の比率と同じ尺度とも扱わない。公開要約でMonoGameの同条件の比率は確認できず、0%としない。

Godotの2026-05-06付公式記事は、Steamのリリース数やゲームジャムでの利用増加を報告している。ただし元データは概ね2026年2月までで、エンジン自体から利用追跡情報を取っておらず、各指標の集め方にも限界がある。[S3] ダウンロード数・SNS人数・開発者数・作品数を足して「ユーザー数」を作らない。

MonoGameは公式サイトに2026-09-16の新テンプレートのフィードバック募集、2026年のSpotlightによる作品・ライブラリー紹介等があり、開発・コミュニティ活動が続いていることを確認した。[M4、M5] Godotより小さいという規模の観測を、そのまま保守停止・将来安泰のいずれの証拠にも変えない。

## 6. crossweaveへの影響

| 評価軸 | 今回の判断 |
|---|---|
| 一般的な採用の広がり・近年の勢い | Godotを加点。Steam件数とGDCの観測から判断 |
| 新しく参加する人と制作手順を共有する容易さ | シーン・エディター等の共通の仕組みを利用するGodotに利点。ただし採用人数・日本語情報量の比較は未測定 |
| C#の資料をそのまま使うこと | MonoGameに利点。Godot全体の規模差がC#向け情報にもそのまま当てはまるとは確認できない |
| 独自の画面構造とテストをコードから追うこと | 0.6の理由でMonoGameを加点。必要なUI補助の選定・自作・保守は引き受ける |
| 商用／Steam実績 | 両方に実績あり。一方だけが商用可能という差ではない |
| 本作の性能・配布・工数 | 件数・有名作から判定しない。従来の代表サンプルと実機確認が必要 |

**一般論での採用のしやすさならGodot、本作でC#中心の構造の把握を優先する現在の条件ならMonoGame推奨を維持**する。これは少数派を積極的に選ぶ理由を説明する判断であり、MonoGameが一般的にGodotを上回るという主張ではない。

前回の管理容易性を過大評価しない。MonoGameでUI・文字・音・画面編集の補助を多数接続すると、エディターや設定を追う負担が戻る。後続RD-ENV-02で必要な補助の版・保守・資料・C#からの制御範囲を確認し、RD-PROOF-02では作成だけでなく変更・調査時に触る箇所を記録する。これらは前回計画の具体化で、今回は実装しない。

## 7. 状態と一次資料

公式の機能説明・当事者の採用例・SteamDBの同一集計・GDC公式要約まで確認。世界全体／日本国内／Godot C#限定の正確なシェア、MonoGameの同条件アンケート比率、売上シェア、相談の応答速度、AI支援の精度差は未確認。利用規模から本作の性能・1.5倍の工数上限を保証しない。

今回の範囲は資料化・自枝保存・読戻し・引継ぎのみ。UI統合、永続化、CI、サイト公開、Steam登録、素材制作、SDK導入、他Work稼働は行わない。既存原本・仮データ・固定試験を保全する。
