## 新しい会話で行う順序

1. **設定と現在地を確認する。** 同じWorkID・枝・担当範囲を継承。設計公開HEAD、旧作業コピー、最新計画を読む。最新設計枝に追補が既に提出されていれば、実blobと差分を確認して重複適用・保存を避ける。旧会話と同時に編集しない。
2. **最新同期で上書きする前に未公開成果を保全・復元する。** 旧コピーが残る場合も元の差分は保持し、新しい隔離コピーへ移す。旧コピーが使えなくても、このpatchとmanifestで復元できる。未保存変更のある場所をresetしない。
3. **基点7c2a43dの清潔な隔離コピーで復元を照合する。** patchのSHA-256を確認し、`git apply --index --check <staged.patchの絶対パス>`、続けて `git apply --index <同パス>`。38パスのmode/blobと `git write-tree` をmanifestと照合する。最新枝が進んでいる場合はまず基点で復元し、その後の差分を通常の方法で調整する。復元済みの旧コピーへpatchを二重適用しない。
4. **必須計画同期と引継ぎ記録を行う。** `ops/project-coordination-20260913` の `docs/作業資料/とりまとめ/` を再帰的に全件、同パス・同blobで同期。計画枝全体はマージしない。自Work設定と計画同期JSONに、新しい会話への移行・受領した最新HEAD・全path/blob・今回の限定範囲を記録する。同期後は計画ファイル等が変わるため、復元直後のtreeと異なるのが正常。過去の `conditions.json`・`artifact-check.json` の固定計画14件を新計画へ書き換えない。
5. **提出に必要な差分だけ確認する。** 下記を読んで、復元したコードが `code-06.json` の固定版と同じことを確認。コード・入力が同じなら26件・12件や旧自然進行・旧比較を再走しない。差異・実際の不備が見つかった範囲だけ修正・追加確認し、元の失敗／修正記録も保持する。
6. **通常保存とGitHub読戻しを完了する。** 設計枝への通常コミット・非強制Push、commitの親／tree・公開HEAD・主要本文／blobを確認。成果SHAと未確認範囲を自Work・引継ぎ記録へ残し、その記録も保存・読戻しする。同期した保全patchの存在と実際のruntime提出は区別する。
