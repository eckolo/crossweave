## 3. 受け渡しの単位と置き場

**1タスク＝レビューして戻せる成果1単位、原則1ブランチ・1PR・1Codex会話。** 一手ごとの細切れ依頼にはせず、関連する実装・検証・説明をまとめる。同じタスクの修正は同じ会話を使い、会話上限等では報告ファイルから同じタスクを引き継ぐ。長い親タスクは、独立して受入可能な範囲に分ける。

| 情報 | 保存先・更新担当 |
|---|---|
| 目標・全体優先度・依存・現在の枠 | 既存 `Work別実施計画.md`／とりまとめ |
| 依頼内容・対象範囲・完了条件 | `docs/作業資料/とりまとめ/着手指示/<TaskID>_内容.md`／とりまとめ |
| 作業開始設定・実行中の状態 | `docs/作業資料/Work/<実行WorkID>.md`／実行担当 |
| 受領した計画全件の照合 | `docs/作業資料/計画同期/<実行WorkID>.json`／実行担当 |
| 実装と検証、未確認・次の操作 | `docs/作業資料/実装報告/<TaskID>.md`／実行担当 |
| コード差分と受領・統合 | 作業ブランチと、そのタスクのPR／実行担当・指定統合担当 |

依頼書は[テンプレート](タスク依頼書テンプレート.md)を使う。計画フォルダはとりまとめ所有のままなので、Codexはそこに完了コメントを書き足さない。実行状態は自Work記録・報告を更新し、とりまとめが次回受領時に計画へ反映する。計画側の状態には確認SHAを付け、常時リアルタイムの監視結果と誤認させない。

初期は既存のMarkdown管理とPRで十分。GitHub Issues／Projectsは、未着手件数・不具合・検索需要が増えた時の一覧画面として追加する候補。使う場合もIssueに依頼本文を複製せずTaskID・依頼書の固定SHAリンク・担当・PRを結ぶ。今回Issue・Project・自動配送は作成していない。

## 4. 一件の具体的な運用

1. **とりまとめが依頼書を用意する。** 目的、必要な成果、実行先、論理WorkID、作業枝、同期元と取り込み範囲、統合先・担当、変更可能パス、採用済み仕様、未決範囲、検証・終了条件を記入。依頼書の版と計画元SHA、技術基点を固定し、空き枠と依存を満たすものだけ「着手可」にする。
2. **ユーザーがVS Codeで開始する。** 対象リポジトリを開き、Codexへ短い開始文とTaskID・指示ファイルを渡す。GitHub上の最新依頼書は `fetch` 後の固定refから最初に読み、古いローカルコピーを開始根拠にしない。初回未導入なら下記の準備タスクから始める。
3. **Codexが開始状態を固定する。** 変更中ファイルを保全し、割当と所有範囲を確認。清潔な作業フォルダ／worktreeを作り、計画全体を実同期→技術前提を取り込み→計画全blob再照合の順で準備する。4項目と受領版を自Work記録へ保存してから実装する。
4. **Codexが一単位を実装・検証する。** 内部関数分割や通常の不具合修正は進める。未決のゲーム規則に当たったら、その判断を要する箇所だけ保留し、選択肢・推奨・影響を報告。独立部分は仕上げる。ユーザーが採用済みの規則を再承認待ちにしない。
5. **Codexが成果を提出する。** 最新計画・技術差分を再確認し、通常コミット、担当枝への非強制Push、公開SHA・内容の照合、報告を保存。必要な権限とGitHub認証がある場合は指定baseへのPRを作る。PR作成機能が使えなければPush済み枝とbaseを返し、GitHub画面から作成できる状態まで整える。既に許可された通常保存のために毎回確認を求めない。
6. **担当が受領し、とりまとめが更新する。** 仕様適合、差分、実施済み検証、未確認を確認し、指定された統合担当が受領・統合する。Codexの自己申告だけでユーザー受入やM1完成にしない。統合SHAと残件を計画へ戻す。

人が毎回行う連絡は、原則「開始文をCodexへ渡す」「PRまたは成果SHAをとりまとめへ知らせる」の2回。Work側はそこから報告を読む。画面の微修正ごとに探索を最初から試し直す必要はなく、直接場面入口で関連変更をまとめて提示する。自動連携を前提とせず、必要になった時に別の運用タスクで追加する。

## 5. 枝・WorkID・並列数

実装を切り出す場合の作業枝は `impl/<task-id>-<内容>-<YYYYMMDD>` を候補とし、初回発行時に一意な実行WorkIDを付ける。ChatGPTに新しいWork会話を作る必要はなく、Codex会話が実行窓口になる。専門Workは仕様・原本・受領の責任を維持し、依頼書で委任したパスだけCodexが変更する。既存WorkIDを二人の書き手に重複使用しない。

一方、既存作業を丸ごとCodexへ交代する場合は引継ぎとして同じWorkID・枝を継承できる。その場合は旧担当の編集を区切り、保存・未保存差分と次の操作を固定する。今回はこの交代は実施しない。

| 対象 | 分岐元／返却先の案 | 注意 |
|---|---|---|
| 共通runtime・保存・開発共通環境 | 設計の受領済み最新基点／`dev_design_tmp_assembly` | masterを作業基点にしない。設計が同じ処理を改修中なら同時に依頼しない |
| UI専用描画・部品 | UI枝へ必要な設計成果と最新計画を同期した基点／`ui/readability-20260910` | UI側で受領後、設計が差分を選択統合。旧PR #1全体の再マージを自動実行しない |
| 検証専用コード・記録 | 検証対象を含む担当枝／依頼書で指定 | 固定セーブ・旧試験結果を上書きせず、新結果の保存先を分ける |

**最大2WorkはCodexを含む全実行担当で数える。** Workが1つ稼働中ならCodexは最大1つ。設計とCodexが同じファイルを編集する構成は避ける。追加の会話・CLI・サブエージェントを数に含めず増やさない。本とりまとめの検討も現在の1枠で、候補タスクを並べることは着手指示ではない。

初期はCodex用の専用cloneを一つ用意し、同時に一つのタスク枝を開く形でよい。並行実装を始める場合だけ作業フォルダを分け、各フォルダを別のVS Codeウィンドウで開く。Codexがworktreeを作成しても、VS Codeの表示先が自動で切り替わる前提にはせず、必要なフォルダを案内する。

新しいフォルダで同じファイルを編集しても衝突の解決にはならない。フォルダ分離は未保存差分の混入を防ぐもの。実装対象・統合順は依頼書で分ける。Git worktreeを使う場合は、同じブランチを別の作業場所で同時checkoutせず、タスク枝を作る。ローカルの起動URL・ポート・保存枠もタスクごとに区別する。

## 6. 状態と受入の区別

| 状態 | 更新・判定 | 進める条件 |
|---|---|---|
| 候補 | とりまとめ | 移管候補。まだ実行しない |
| 着手可 | とりまとめ | 前提・担当・範囲・基点・検証条件を記入済み、枠を確保 |
| 実行中 | 実行担当の記録 | 受領版・枝・開始SHAを保存。枠を使用 |
| 判断待ち | 実行担当 | 未決と影響を提示。独立部分を保存し、待ちだけなら枠を解放 |
| 提出済み | 実行担当 | 公開コミット・報告・検証・PRまたは返却枝を確認。枠を解放 |
| 統合済み | 指定統合担当 | 受領・取り込んだSHAを記録。人の評価は別 |
| 受入済み | 各完了条件の担当 | 必要な技術検証と、必要な人の確認を満たす。残件付きなら明記 |

実装した／テストを実行した／実ブラウザーで動いた／ユーザーが操作を了承した、の4つを分ける。不要な全件再試験を恒例にせず、変更リスクに対応する検証を指定する。既存結果の再利用ならコード・入力・適用範囲の一致を記録する。

中断時は自Work記録・実装報告へ、公開SHA、未保存差分の保全先、実行済み検証、失敗内容、未決、次の一手を残す。ローカルにしかない成果はWork側から取得できないので、可能な範囲をタスク枝へ保存してから引き継ぐ。PC内の絶対パスだけを唯一の引継ぎ先にしない。

## 8. 初期導入で整える仕組み

- GitHubの認証はChatGPTログインと別に、ローカルGitからfetch／Pushできることを確認する。PRはVS CodeのGitHub機能、GitHub画面、利用可能なら `gh` のいずれでもよく、特定の追加拡張を必須にしない。
- 現リポジトリはES Modules主体で、ゲーム起動自体にバンドラーを必須としない。ルートpackage.json・統一検査入口・AGENTS.mdは確認版にはない。DOM検査用の `docs/検証/UI/readability/package.json` はjsdom 30.0.1を指定する一方、D02Rの記録は26.1.0。ここを最新化の名目で無条件に揃えず、必要な固定版と実行記録を整える。
- 新しい依頼書からの計画同期・受領JSON・結果報告を、初回は既存手順で確実に通す。繰り返しが負担なら、担当の次タスクとして全path/blob照合スクリプトと最小のCIを足す。初回から自動タスク配信サービスや複雑なボードを作る必要はない。
- PRの判定を自動化する場合も、スナップショットした計画SHA・入力・コードを検証する。無関係な計画更新だけで古い試験条件を上書きしたり、全旧比較を回したりしない。同期と影響確認は開始時・成果反映前に行う。
- 操作はローカルで許可された環境の範囲で実行する。権限・ネットワーク・ツールの制限があれば止まった操作と代替可能な残作業を報告する。VS Codeなら必ずブラウザー自動検証・Push・PR作成までできると保証しない。
