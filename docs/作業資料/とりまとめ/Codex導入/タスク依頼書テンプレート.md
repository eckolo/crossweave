# Codexタスク依頼書の書式

版：0.5／2026-10-08（日本時間）。担当：開発計画とりまとめ。
発行先は本枝のdocs/作業資料/とりまとめ/着手指示/。未記入箇所はとりまとめが実際の割当時に埋める。テンプレート自体は着手指示ではない。
共通本文は[共通運用規則](共通運用規則.md)、現在の適用作業は[CO-CX01](../着手指示/CO-CX01_Codex共通規則の適用.md)。個別依頼の読取り専用・停止条件は一般の通常保存許可より厳しい範囲で維持する。

2026-10-08引き継ぎ補足：取得障害後も、同じGitHubプラグイン／対象で仕様に沿った読み取りAPI切替・一覧照合・ページ送りは逐一の承認不要。ブラウザー、診断の更新API、別サービス／認証・資料／固定入力、必要確認・完了条件の省略は含めない。Cloudの個別停止は維持。元の規定を残した[共通規則1.1](共通運用規則.md)と[照合・受渡し記録](C1照合と受渡し_20261008.md)を適用する。旧記載の「別経路」の粒度はこの補足と照合し、すべてのAPI試行を新たな迂回策へ数えない。

## 依頼の識別と開始設定

| 項目 | 記入する内容 |
|---|---|
| TaskID／親タスク・指示版 | 意味ある成果の単位、候補／着手可／依存待ち／提出済み、版・発行日 |
| 目的・必要成果 | 利用者または開発上の問題、変更後の動作、今回完了するコード・資料・検証 |
| 正式WorkID・担当 | 指定された既存WorkID／Work名。新設が必要なら目的・責任・原本の一貫性を説明。同一作業の会話／実行場所交代は既存IDを継承 |
| 実行窓口・会話 | Codex Cloud／ローカル／VS Code等の実在する窓口。新しい会話と正式Work新設を区別。既存窓口が同じコードへ同時に書かない条件 |
| 作業ブランチ | 通常の編集・保存・Push先、受領した正式設定。同一作業のためだけの別枝／改名／PRを作らない |
| 必須同期元 | 最新計画の範囲実同期→既定技術同期→計画一致再照合。各元枝、範囲、順序、複数の理由 |
| 成果の統合先・担当 | 枝と担当、または統合不要の理由。PRが本当に必要な別単位ならbaseも記す。成果保存と正式採用を分ける |
| 共通文書・コード担当 | 原本の既存担当、今回委任するpath／節、読取り専用対象。担当外は自Work側の変更案 |
| 依存・並行条件 | 必要な提出SHA／契約、同時編集を調整する具体対象。今回の件数指定と解除条件を記す。過去の一時上限を恒久化しない |
| 調査版・実装版・試験固定版 | 最新HEADの参考確認と、実際に使う40桁source／入力／条件を別記。進行中試験を無断で差替えない |
| 計画受領 | 元コミット、全対象path/blob、実ファイルコピーと計画同期JSON。参照だけ／fetchだけでは実同期にならない |
| 指示の受領 | AGENTS／override／nested／global／参照原本と最新個別指示の出所・版・有効範囲、全文受領／取得不能、容量と実読込の確認範囲 |

## 実際のcheckoutと権限の照合

開始時に以下の期待値と観測値を別に書く。正式Workとクライアントの画面・環境・folder・work枝を同一視しない。

| 対象 | 期待値 | 開始時の観測値・確認手段 |
|---|---|---|
| repo／path | 正式repoと許可された作業場所 | 実repo／絶対path。秘密値を出力しない |
| Work／枝／HEAD | 指定ID・枝・基点 | 実枝・HEAD・refs・未保存ファイル／index。保全の範囲 |
| 必要source／入力 | 固定コミット・全対象path/blob・fixtureのhash | ローカル存在・実ファイル一致・不足。指定sourceの取得可否を区別 |
| 書込み範囲 | product・scratch・保存枠・Git・環境設定ごとの許可 | 実権限と未確認。HOME／CODEX_HOME・通常saveを勝手に転用しない |
| 通信 | 個別指示の許可集合と停止条件 | 現在の有効状態・観測版・試行回数／結果。許可集合からenforcedを推定しない |
| 固定環境 | OS／CPU・Godot・.NET／TFM・native・font・描画条件 | 実版／hash・存在・不足。既存の別版やfontで無断代用しない |

枝／source不一致や必要前提不成立があれば、依存する実装・取得・準備・検査を止める。無断のbranch作成・切替・改名・reset／force・全枝マージで一致に見せない。適用状態の観測手段がなければ、存在しないメニュー／APIを発明せず不足を報告する。実在する人操作または具体的な迂回策の判断まで分ける。

依頼書自身の最終コミットを同じ本文へ再帰的に埋めない。発行後の開始文で具体SHAを渡し、実行担当の受領JSON・報告へ実取得版を記録する。

## 必読の入力・実施範囲

README・現行共通規則・自Work設定・最新計画と依頼書、今回必要な採用仕様と技術契約、再利用結果のcode／input／適用限界を指定する。全過去会話を一律に読ませず、現行・未採用・試行・履歴を分ける。

実現する振る舞い、編集可能path、通常save・公開情報・UI・失敗時状態の重要境界を具体化する。許可された通常の実装判断は担当へ任せる。既了承の暗色UIを変えるなら差異を未承認として扱い、未合意の表示方式や全UI再承認を先に追加しない。

新規・変更コードと同じタスク内で、丁寧な日本語コメント、読む順、処理の流れ、設計理由、失敗時の状態を教材へ記録する。Godot固有／C#・.NET／本作独自設計を区別する。

## 必要な検証と人の担当

| 確認 | 固定入力・実在する実行方法 | 終了条件・残す限界 |
|---|---|---|
| 変更した処理 | 実コマンド・code版・依存版 | 具体期待値／不変条件、未実施理由 |
| 保存・公開境界 | 許可された隔離保存枠、合法入力 | 通常save保全、未知情報なし、revision・再送の意味 |
| 必要な描画／入力 | 指定viewport・font・描画環境・同状態対 | 合意原本と使用先対応。CI／合成入力成功を実機へ拡張しない |
| 人の判断 | 人タスクID、開始資料、短い操作、求める回答 | 人が今できる条件と待機条件。採用・実機・試遊を区別 |
| 成果保存 | 自枝通常保存・非force Push、GitHub読戻し | 実コミット・本文／blob・親／tree／HEAD、保存と受領を区別 |

今回の変更に必要な検査を実行し、無関係な既成功試験を標準で反復しない。使えない便宜的コマンド・正常終了だけ・実行0件を合格にしない。Windows CI、Linux／LLVMpipe、利用者Windows 11実機、面白さの人判断は別項目。

## 手順不成立・判断と停止

プロジェクト共通規則の「手順不成立時の報告と迂回策の事前承認」を全文で適用する。対象・元の手段・停止点・確認済み／未確認・実施済み・停止中を報告する。別手段／経路／対象／条件、確認省略、代替資料／成果、範囲／終了条件変更は、理由・対象範囲・影響を示して明示承認前に接続・取得・準備・試行しない。

停止依存を別名の独立作業で達成しようとせず、元の手順と許可範囲内の保全・状況整理・無関係な既承認作業だけを続ける。既回答の採用判断、形式的命名、通常の担当内保存を再質問しない。

## 提出と開始文

全依頼の必須成果に「とりまとめへの報告プロンプト」を含める。自Work引継ぎへ保存し、最終応答のコード枠で具体値を埋めた全文を提示する。[完了報告と引継ぎ規則1.6](../完了報告と引継ぎ規則.md)の第10節を使う。リンクやSHAだけで代用せず、未完了で区切る場合も未完了報告文を出す。読取り専用は既存の証拠保存方式／応答を使う。Cloud適用はGit保存・直接全文受領・有効AGENTS読込をそれぞれ根拠とともに分ける。

自Workの既存記録と適切な既存成果フォルダーへ、TaskID／指示版・受領全文／出所・計画同期・技術基点・実枝／HEAD・code成果SHA、主要変更と理由、実検査条件と結果、失敗／未確認、残件の担当と具体再開入力、未保存差分の保全を保存する。必要性がない別報告ファイル・別枝・PRを形式のために作らない。

今回依頼の完了／未完了、実装完了、提出、とりまとめ受領、UI適合、実機、人試遊、正式採用を別に報告する。最終HEADは最後の応答とGitHub履歴で示す。人が開始文を送付したことと、AIの全文受領／着手は別。

```text
eckolo/crossweaveの<TaskID>を、<正式Work名・WorkID>／<指定枝>の同一作業として継続してください。
今回の指示は<固定40桁SHAと依頼書path／版>、実装基点は<固定SHA>、実行窓口は<選択済み窓口>です。
共通規則の全文と最新個別指示を受領し、期待されるrepo・正式Work・枝・source・権限と実checkout／観測値を別に示し、設定4項目・保全・指定同期を確認してください。
今回の<具体範囲・必要成果・終了条件>まで進め、担当内の通常保存・GitHub読戻し後に実成果SHA・検査・未確認・次担当／再開条件を返してください。
不成立や停止条件へ依存する部分は止め、具体報告と必要な判断を提示してください。別手段の準備／試行は明示承認前に行わず、既実施範囲を再作成しません。
```

読取り専用Cloudへの開始文には編集・保存を追加しない。規則を取得できない現Cloudには[全文付き直接指示](Cloud継続指示.md)を用い、Git取得と実同期の代わりにはしない。停止中会話の自動起動・監視・他人への自動送信は行わない。

# Codexタスク依頼書の書式

案0.2／2026-09-20。発行先は計画枝の `docs/作業資料/とりまとめ/着手指示/`。下記の未記入箇所は、とりまとめが実際の割当時に埋める。テンプレート自体は着手指示ではない。

## 依頼の識別・開始条件

| 項目 | 記入する内容 |
|---|---|
| TaskID／親タスク | CO-...／既存のCO-U02・CO-D03等 |
| 状態／指示版 | 候補・着手可・提出済み等／版・発行日 |
| 依頼先 | VS Code Codex。受領する専門Work名も記す |
| 新しい会話の要否 | ChatGPT Workの新設有無と、Codex会話の新規／継続／引継ぎを区別。理由を1行 |
| 目的・必要な成果物 | プレイヤー／開発上の問題、変更後の動作、コード・資料・検証の成果 |
| 実行WorkID | 今回の独立実装単位のID。既存作業の交代なら継承元を明記 |
| 作業ブランチ | 今回の編集・保存・Push先。作成元と競合時の命名も記す |
| 必須同期元 | 計画→技術前提の順。各枝・実同期範囲・必要理由 |
| 成果の統合先・担当 | PRのbaseと受領・統合担当。作業者の自己マージ可否は既存権限に合わせる |
| 共通文書・コードの担当 | 原本担当、今回委任するパス／節、保護対象 |
| 依存・並行条件 | 必要な提出SHA／契約、並行できる担当、同時編集を調整する具体的な対象。一時的な件数指定がある場合だけ適用範囲と終了条件。固定の2担当上限は置かない |
| 調査基点／実装基点 | 調査時のSHAと、着手時に受領・固定する実際のSHAを別記 |
| 計画の受領 | 最新計画元の40桁SHAと全path/blobの受領JSON。依頼書自身のblob／版も記録 |

依頼書自身のコミットSHAを同じファイルに埋めて無限に更新しない。発行後の開始プロンプトで参照SHAを渡し、実行担当の受領JSON・報告に実際の取得版を記録する。

## 必読の入力

- README・プロジェクト設定・自Work設定・最新計画と依頼書。
- 今回に必要な確定仕様の節と技術契約。全過去記録を一律に読み直させない。
- 過去結果を再利用する場合は、そのコード・入力・適用範囲。
- 採用済み／未決／仮値の一覧。古い案を実装根拠にしない。

## 実施範囲と受入条件

1. 実現する振る舞いを列挙する。
2. 読取り可能範囲と編集可能パスを区別する。
3. 保存互換・非公開情報・UI表示・失敗時の扱いなど、今回の重要な境界を記す。
4. 複数の選択が許される通常の実装判断は担当へ任せる。
5. 対象外・後続へ残すものは、実際に混同が起こり得るものだけ列挙する。

## 検証

| 確認 | 実行方法・入力 | 合格条件 | 未実施なら残す理由 |
|---|---|---|---|
| 変更した処理 | 実在するコマンドまたは今回作る検査入口 | 具体的な期待値／不変条件 |  |
| 保存・公開境界 | 固定入力・別保存枠 | 既存状態保全、未知情報なし等 |  |
| UI／ブラウザー（必要時） | 起動URL・場面・画面幅・ブラウザー | 可視範囲・操作・永続保存 |  |
| ユーザー確認（必要時） | 直接場面入口、比較する差分 | 今回求める判断だけ |  |

既存結果の上書きや全旧試験の再走を標準にしない。環境差・変更のリスクに応じ、今回必要な検査を記入する。実際に使えないコマンドを便宜的に `npm test` 等と書かない。

## 判断が必要な場合

不足する採用条件、推奨・代案、各影響、回答まで独立して終えられる範囲をまとめる。形式的な命名・通常保存のために確認を増やさない。既回答の仕様は再質問しない。

## 提出

自Work記録と `docs/作業資料/実装報告/<TaskID>.md` に以下を残す。

- 状態、TaskID、指示版、計画・技術基点、作業ブランチ、PR、コード成果SHA。
- 必要な振る舞いが何までできたか、主要な変更と理由。
- 検査コマンド、環境版、入力・保存先、結果、未実施・未確認。
- 他担当の接続箇所、必要なユーザー判断、既知の制約。
- 未保存差分の有無と保全先、次の具体操作、稼働枠の解放。

コードSHAを報告へ記し、その報告を後続の通常コミットへ含める。最終提出HEADはPR／最終返信で示す。同じファイルに自分自身の最終SHAを延々追記しない。

## 開始プロンプトの型

```text
crossweaveの<TaskID>を実施してください。実行先はVS Code Codexです。
最新の ops/project-coordination-20260913 を取得し、固定したrefから
<依頼書のパス>を読んでください。
状態が着手可であること、依存・担当・作業枠を確認し、指定の同期と開始設定を済ませて実装・必要な検証・通常保存・成果提出まで進めてください。
判断が必要な部分は選択肢と影響を整理し、独立部分を仕上げてください。
成果SHA、PRまたは返却枝、実装報告のパス、未確認事項を返し、今回単位を終了してください。
```

実行担当への送信はユーザーが行う。依頼書を保存しただけでCodexが起動した／受領したとは記録しない。
