## 何が未確認で、なぜ従来手順をそのまま使わないか

- 9月15日のD02先行版 `68da4ff0` はPython静的サーバーをループバックの8000番で起動し、同一originからES Modulesと確認ページを配信する手順。通常の同じPCでの開発には成立する。8000はそこで指定したポートにすぎない。
- D02の `browser-check.json`（`d44ffa5b`）から既に `ERR_BLOCKED_BY_CLIENT`。D04Aの `environment.json`（設計 `4ad410b3`）もページ実行前の拒否で、実保存0件。サーバーとCloud Chromeが接続可能な同じ環境にあるという証拠はない。
- OpenAI公式はWeb／モバイルのCloud Browserを対応する公開・未ログインサイト向けとし、localhost用途には別の組込みブラウザーを案内する。この説明と観測から、今回のCloud Browserをローカルサーバーの既定接続先としない。エラー内部のポリシー名や物理的なネットワーク構成を特定できた、とは扱わない。
- 「全てのlocalhost手順が成功し得ない」「環境の許可を一つ変えれば直る」とは結論しない。単なる環境待ちから、担当が実行経路を確立するタスクへ変更する。

## 再開時に範囲を見直すE1〜E3

| ID | 実施内容・完了条件 |
|---|---|
| E1 経路と固定条件 | 最新計画・自枝・既存D04Aのコード／入力を照合。既存Actionsとワークフロー変更権限・実行可否・ブラウザー依存の導入条件を確認。サーバーとブラウザーの実行場所、origin、起動コマンド、使用SHA、OS・ブラウザー完全版を記録。8000固定は不要だが一回の検証内でoriginを維持 |
| E2 到達と実行 | 既存D04Aの `d04a-prepare.mjs`・`harness.html`・`runner.mjs` を再利用。固定依存で実Chromiumを起動し、同じrunnerのHTTP配信・ページとモジュールの読込み・native APIの利用・既存検査の実保存→実再読込まで確認。新たなゲーム用検査画面を作り直さない |
| E3 証拠とD04Aへの継続 | 実行ID／URL・使用SHA・入力hash・環境・標準出力・失敗時のconsole/pageerror・結果JSONを保存。環境成立後は同じ条件でD04A A2〜A4へ継続する。E2で取得した保存／再読込結果を再利用し、同じ確認を別タスク名で二重実施しない |

実装の目安：専用の小さなPlaywright実行部と限定workflowを設計枝へ追加する。必要な依存を版固定し、通常の実行権限・既存の読み取り権限を用いる。新しい認証情報・公開サービス・製品用バックエンドは必要ない。既存Node専用CIの成功を実保存合格へ読み替えない。

CI側の2タブは、**同じブラウザー保存領域を共有するbrowser context内の、独立した2つのPage** として開く。独立contextでDBを分離したり、同じdocumentにcontrollerを2つ作るだけで代用しない。再読込は実navigationを行い、既存runnerのdocument ID・保存hash・最終statusを証拠にする。headlessの実Chromiumはブラウザーの実IndexedDBを使うが、手動入力・見た目・面白さの確認を兼ねない。

期待値を実装と別に作り直さず、既存D04Aの既知入力・判定と `passed_limited_browser_checks` を使用する。ボタン実行・ページ再読込・peer待機・最終再読込・結果JSON保存を最小の自動操作でつなぐ。APIを利用できない・ブラウザーが起動しない・入力準備が失敗した場合は検査成功にせず、具体的な阻害段階を残す。ブラウザー利用制限や承認拒否を別経路で突破しない。

Actionsが使えない場合も、方式の比較だけでユーザーへ丸投げしない。使用SHA・依存・起動／停止・最初に開くURL・操作順・結果の返却先まで揃え、ユーザーに残る最小の操作とその理由を示す。未導入のCodex・ローカルWorkが使えると仮定しない。
