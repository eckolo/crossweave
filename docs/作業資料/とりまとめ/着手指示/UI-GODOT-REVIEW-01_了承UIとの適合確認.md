## 今回の実施と成果

1. **合意案の基準固定**：画面・状態・部品と、了承根拠／原本SHA・path/blob／後継／画像を対応づける。M1の準備・取得編成、探索、札・主体・順序、詳細／予測、共通案内、本文・帰還・記録を対象にする。未採用全画面や新規素材には広げない。
2. **外観の全対象照合**：同じFHD・倍率・等価状態で、寸法・余白・文字組・色・枠・画像／アイコン・重なり・窓／スクロールバー・選択／ホバー／無効等を原本の実表示と比較。全体画像と拡大・寸法値を残す。初回23適合の外観、描画部品の違いとして除外した差、取得不能PNG3件も今回の網羅性の中で扱う。未取得／未描画を適合へ転記しない。
3. **機能の再確認**：R01〜R07とU01を修正ソース・実画像・入力結果に対応づけて再判定。無関係な既確認機能や全旧スイートは一律やり直さない。U01の自然FHDはoverflow=0、送り証拠は同じ実ノードの限定寸法という条件を保持する。
4. **残る2ケース**：R01-filler期限切れ消滅とR04-unlimited明示nullのguardは実描画未確認。原本・既存公開契約を調べ、合法状態の入口と必要証拠、または今回適用外の具体根拠を記す。取得できないだけで合格にしない。規則／数値／通常セーブを変更して再現を捏造しない。本編が必要証拠を追加する担当で、UIはその受入条件を渡す。
5. **差異台帳と実装受渡し**：各差異ID、期待値、現値／画像、影響、修正箇所・担当、確認手順を記録。「一致／不一致／未確認／個別承認済み例外／根拠付き対象外」を区別。共通部品の寸法・スタイル・状態を本編が使える基準にし、代表画面から段階的に合わせる修正順を示す。再デザインや実装者の推測による近似は指示しない。
6. **保存**：README・適合確認・review.json・とりまとめ引継ぎを更新し、visual-baseline.md/json・visual-diff.md/json等の基準／台帳・比較画像を同フォルダーに保存。旧判定・固定画像・失敗は保全する。自枝への通常保存・Push・GitHub本文読戻し後に提出。

新しいゲームコードは今回の担当外。調査用コードを追加する場合は範囲・日本語コメント・読む順と失敗時を説明する。実行環境の制限は独立してできる比較を終えて具体的な未確認として残す。利用者にGodot／SDK導入・ビルド・差異の全列挙は求めず、拒否済みlocalhost経路を再試行しない。

## 完了・配布判定と受渡し

今回レビュー依頼の完了条件は、M1対象一覧と基準・項目別判定・具体差異／未確認・担当別の必要成果・固定SHAを保存し、再現修正へ渡せること。**要修正を残したレビュー完了と、UI適合を分ける。** 必要資料が作れない場合は依頼内未完了と再開条件を明記する。

配布可は、合意案からの未承認差異・判定に必要な未確認が0件、7指摘／U01の必要な機能確認が解消し、対象SHAと証拠が一致した後。既了承の細部再現を「仕上げ」で免除しない。利用者の実機・DPI等はCO-D04Cへ別欄で残す。合意案を変更せざるを得ない場合だけ、実画像・試行結果・代案を添えユーザーの個別判断事項をとりまとめへ返す。未承認のまま適合扱いにしない。
