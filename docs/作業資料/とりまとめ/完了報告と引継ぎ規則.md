# 各Workの完了報告と、とりまとめへの引継ぎ

版：1.3／2026-09-29。ユーザーの「任されたタスクが完了したら、とりまとめへの引継ぎを作成する」という指示に基づく共通規則。1.1でコードをGodot学習教材にするためのコメント・解説条件を追加。1.2で資料の入口とルート相対パス、1.3で次のWorkへ渡すプロンプトの本文提示と、ディレクトリ単位の受渡し方針を追加。

**各Workは、今回任された依頼全体を終えたら、とりまとめ向け引継ぎを作成・保存し、最終応答で提示する。** 最初の項目や内部の一区切りが終わっただけの場合は、依頼全体の完了と表示しない。今後の各担当指示へ適用し、既存Workも最新計画の必須同期で受領する。

## 1. 最初に「今回の依頼全体」を決める

- 最新の担当指示とユーザーの追加指示から、今回の依頼ID・対象タスク・必要成果・完了条件を自Work設定へ短く記録する。たとえばUIは今回の `CO-U02-B`、ビジュアルは `CO-V01＋CO-V02の背景2点`。Workの全将来タスクやM1全体とは分ける。
- ユーザーが実装・検査・保存まで任せた場合、同期・調査・初回実装だけを独立した終了条件へ変更しない。同じ依頼内の残作業を、未依頼の「次の候補」へ移さない。
- 内部の手順を分割することと、ユーザーに任された範囲を狭めることは別。担当範囲内で判断不要の残作業がある限り継続する。進捗報告を挟むことはできる。

## 2. 状態を二つの欄で明示する

| 欄 | 書く内容 |
|---|---|
| 今回の依頼全体 | **完了／未完了**。部分完了を「完了」としない |
| 現在の状態 | **進行中／判断待ち／外部条件待ち／中断／完了・とりまとめへ引継ぎ** |

「保存できた」「検査が通った」「今回単位終了」だけで結論にしない。依頼の各成果について、完了・未了・今回範囲外と根拠を並べる。保存が必要な成果は、指定先への保存・必要な読戻し・引継ぎ文作成までが完了条件。

判断待ち・外部条件待ちでは、残件、止めている理由、再開に必要な入力と担当、ユーザーの判断／作業の有無を明記する。独立してできる残作業は先に進める。会話上限等で中断する場合も途中引継ぎを残し、未保存差分と正確な再開地点を保全する。

## 3. 引継ぎの保存先と内容

原則として、自Work枝の **`docs/作業資料/Work/<WorkID>.md` に「とりまとめへの引継ぎ」節**を設ける。冒頭に最新の依頼状態と当該節への導線を置き、過去の状態と取り違えないようにする。既存の報告書・検査記録への参照を使い、同じ説明や全履歴を複製しない。長い資料を分ける場合も、自Work設定から最新版が一意にたどれるようにする。

```text
とりまとめへの引継ぎ
Work名／WorkID／作業ブランチ：
今回の依頼ID・対象範囲：
今回の依頼全体：完了／未完了
現在の状態：進行中／判断待ち／外部条件待ち／中断／完了・とりまとめへ引継ぎ
依頼内容の内訳：各成果の完了・未了・今回範囲外と、その根拠
保存先：成果コミット・ファイル。未公開／未保存の有無と保全先
確認済み：実際の版・環境・確認範囲。未確認も区別
コード作業の学習用解説：保存先・対象コード版・最初に読むファイル／クラス／メソッド
残る依頼内タスク：なし、または具体的な残件と再開条件
ユーザーの判断・作業：不要、または必要な判断・操作と理由
後続への入力：受け取るWork、成果・API・素材・条件・参照版
次の候補：今回範囲外の候補だけ。着手済みとはしない
```

後続Workの受領・統合・ユーザー受入は、担当側の成果提出とは別に記録する。たとえばD03の設計完了とUI接続完了、背景納品とその画像の正式採用、Node検査と実ブラウザー保存は分ける。

## 4. 最終応答と次の作業

- 最終応答の先頭を **「今回の依頼全体は完了です」** または **「今回の依頼全体は未完了です。残件は…」** とする。その後に保存済み成果、ユーザーに必要なこと、後続への入力、とりまとめ向け引継ぎの参照先を簡潔に示す。
- 完了した場合は、その依頼の範囲で終了する。未依頼の次タスクや別担当の仕事を自動開始しない。とりまとめが引継ぎを確認し、後続の優先度・依存・担当指示を更新する。
- 引継ぎ文の作成・保存・提示を原則とし、別会話への自動送信・起動・常時監視は前提にしない。とりまとめの受領を確認していない場合は「引継ぎ作成済み・受領未確認」と書く。
- とりまとめも、担当完了・成果受領・統合・ユーザー受入を区別して計画へ反映する。既に同等の完了報告がある過去成果へ、形式を揃えるだけの再実装・再検査・再報告依頼は出さない。

本規則は固定の並列数上限を設けない。担当の編集範囲と依存関係を維持し、3Work以上でも依頼単位と引渡し先を明示する。

## 5. コードを学習教材として読むためのコメントと解説

2026-09-28 18:04のユーザー指示を反映する。ユーザーはGodot未経験で、今回作成するゲームコードを教材として学びたい。**今後コードを作成・変更するタスクでは、丁寧なコード内コメントと、実コードに対応する解説を必要成果に含める。RD-SAVE-02Aから継続して適用する。** 実装担当の通常作業として行い、同時に別Workを稼働させる条件にはしない。

### コード内で説明すること

- 日本語を基本とし、主要クラス・公開APIの役割、入力・戻り値、呼出し条件、状態やファイルを変える範囲を説明する。C#の公開APIは必要に応じてXMLドキュメントコメントを使う。
- 処理の意味が読み取りにくい箇所は、何をしているかと、なぜこの順序・構造・APIを選んだかを併記する。状態の所有者、失敗時に残す状態、重複操作・非同期処理・寿命の扱い、守るべき条件を重点にする。
- Godotのシーン・ノード・シグナル・呼出しのタイミング・リソース等に関係する箇所は、関連する用語と実際の接続先を初出で説明する。Godotが要求する仕組み、一般のC#／.NET機能、このプロジェクトで選んだ設計を区別する。
- 自明な代入等への逐語的なコメントで埋めず、初めて読む人が処理を追うために必要な粒度にする。仮処理・制約・未接続部分は事実どおり記し、コードを変えたら対応するコメントも直す。

### 適切な区切りで提示・保存する解説

実装のまとまりができた時に、何が動くようになり、どのコードがどの役割を持つかを会話で短く説明する。毎行・毎編集の長い講義にはせず、依頼内の作業を進めながら説明する。完了時は要点と読む入口を提示し、詳しい解説は担当の検証・受渡し資料へ保存する。

| 解説の項目 | 必要な内容 |
|---|---|
| このコードでできること | ゲームのどの動作を実現したか。実装済み・今回触れていない範囲・仮処理を区別 |
| 読む順序 | 実在する入口ファイル、主要クラス／メソッド、呼出し元と呼出し先を示す。資料・ソースの場所はリポジトリルート相対パスを併記し、アプリREADME等の一つの入口からたどれるようにする。対象版を固定し、行番号だけに依存しない |
| 一つの処理を追う | 入力→処理→状態変更→保存／表示など、その実装で完結する代表的な一経路を説明。必要な短い実コードの抜粋や図を対応付ける |
| Godotとの関係 | Godot固有の仕組みと純C#／.NET部分を区別。本作独自のクラス名・設計方針をGodotの標準用語・必須構成として教えない |
| 設計理由 | なぜ分離したか、なぜこの順序か、どの不具合を防いでいるかを実装と結び付ける。主要な選択だけを扱う |
| 動かして確かめる入口 | 使用版・必要な環境・実行手順・期待される結果、対応する既存テスト。担当が確認できた範囲と未確認を明記する |

Godot APIの仕様説明には採用版に対応する公式資料を必要箇所で添える。一般論だけの教材や未実装コードを実装済みとして示さず、説明と実コードの対応を確認する。

適用対象は新規・変更箇所と、その流れを理解するために必要な既存コード。完了済みCore等のタスクを未完了へ戻したり、全コードへの一括コメント追加・学習用の機能追加・構造変更を自動で行ったりしない。既存処理は読解案内から参照し、許可された編集範囲内で必要なコメントを補う。

**完了条件には、実装・検証に加えて、対象箇所のコメント整備、実コードと対応する解説の保存、読戻し、ユーザーへの要点提示を含める。** ユーザーの理解確認や学習の完了は承認待ちにしない。とりまとめは方針と受渡しの確認を担当し、実装担当に代わってコードへ注釈しない。

## 6. 次のWorkへ渡す指示の提示

2026-09-30 20:47指示：とりまとめが次タスクを整理するときは、保存した指示書へのリンクに加え、**そのままコピーして担当Workへ貼り付けられる依頼全文を応答本文に提示する。** 依頼先・新規／継続、対象リポジトリ・WorkID・作業枝、同期元、対象指示書、今回の実施範囲・終了条件を含める。概要だけで利用者に依頼文を組み立てさせず、指示書と本文を一致させる。これは別Workへの自動送信許可ではない。

## 7. 本人向け成果の受渡し形式

同指示：必要なものが1ディレクトリ内に揃っていればよく、単にまとめる目的のZIP化は必須にしない。必要な圧縮は利用者側で行う。実行物は依存・資源・案内とともに一つの配下へ集約し、必要な内部階層を保つ。コードと通常資料のGitHub管理を継続する。

共有先で利用できる一式・正確な版・一覧・起動案内は必要。ZIPの生成・取得・全量hash確認を、本人向け受渡しや実機確認の完了条件に追加しない。過去の未実施は成功ではなく要件変更として記録する。特有の技術要件で圧縮が必要な場合は実際の目的・形式・影響を示し、一般的な納品のためだけに導入しない。
