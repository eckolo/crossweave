# 各Workの完了報告と、とりまとめへの引継ぎ

版：1.0／2026-09-20。ユーザーの「任されたタスクが完了したら、とりまとめへの引継ぎを作成する」という指示に基づく共通規則。

**各Workは、今回任された依頼全体を終えたら、とりまとめ向け引継ぎを作成・保存し、最終応答で提示する。** 最初の項目や内部の一区切りが終わっただけの場合は、依頼全体の完了と表示しない。今後の各担当指示へ適用し、既存Workも最新計画の必須同期で受領する。

## 1. 最初に「今回の依頼全体」を決める

- 最新の担当指示とユーザーの追加指示から、今回の依頼ID・対象タスク・必要成果・完了条件を自Work設定へ短く記録する。たとえばUIは今回の `CO-U02-B`、ビジュアルは `CO-V01＋CO-V02の背景2点`。Workの全将来タスクやM1全体とは分ける。
- ユーザーが実装・検査・保存まで任せた場合、同期・調査・初回実装だけを独立した終了条件へ変更しない。同じ依頼内の残作業を、未依頼の「次の候補」へ移さない。
- 内部の手順を分割することと、ユーザーに任された範囲を狭めることは別。担当範囲内で判断不要の残作業がある限り継続する。進捗報告を挟むことはできる。

## 2. 状態を二つの欄で明示する

| 欄 | 書く内容 |
|---|---|
| 今回の依頼全体 | **完了／未完了**。部分完了を「完了」としない |
| 現在の状態 | **進行中／判断待ち／外部条件待ち／中断／完了・とりまとめへ引継ぎ** |

「保存できた」「検査が通った」「今回単位終了」だけで結論にしない。依頼の各成果について、完了・未了・今回範囲外と根拠を並べる。保存が必要な成果は、指定先への保存・必要な読戻し・引継ぎ文作成までが完了条件。

判断待ち・外部条件待ちでは、残件、止めている理由、再開に必要な入力と担当、ユーザーの判断／作業の有無を明記する。独立してできる残作業は先に進める。会話上限等で中断する場合も途中引継ぎを残し、未保存差分と正確な再開地点を保全する。

## 3. 引継ぎの保存先と内容

原則として、自Work枝の **`docs/作業資料/Work/<WorkID>.md` に「とりまとめへの引継ぎ」節**を設ける。冒頭に最新の依頼状態と当該節への導線を置き、過去の状態と取り違えないようにする。既存の報告書・検査記録への参照を使い、同じ説明や全履歴を複製しない。長い資料を分ける場合も、自Work設定から最新版が一意にたどれるようにする。

```text
とりまとめへの引継ぎ
Work名／WorkID／作業ブランチ：
今回の依頼ID・対象範囲：
今回の依頼全体：完了／未完了
現在の状態：進行中／判断待ち／外部条件待ち／中断／完了・とりまとめへ引継ぎ
依頼内容の内訳：各成果の完了・未了・今回範囲外と、その根拠
保存先：成果コミット・ファイル。未公開／未保存の有無と保全先
確認済み：実際の版・環境・確認範囲。未確認も区別
残る依頼内タスク：なし、または具体的な残件と再開条件
ユーザーの判断・作業：不要、または必要な判断・操作と理由
後続への入力：受け取るWork、成果・API・素材・条件・参照版
次の候補：今回範囲外の候補だけ。着手済みとはしない
```

後続Workの受領・統合・ユーザー受入は、担当側の成果提出とは別に記録する。たとえばD03の設計完了とUI接続完了、背景納品とその画像の正式採用、Node検査と実ブラウザー保存は分ける。

## 4. 最終応答と次の作業

- 最終応答の先頭を **「今回の依頼全体は完了です」** または **「今回の依頼全体は未完了です。残件は…」** とする。その後に保存済み成果、ユーザーに必要なこと、後続への入力、とりまとめ向け引継ぎの参照先を簡潔に示す。
- 完了した場合は、その依頼の範囲で終了する。未依頼の次タスクや別担当の仕事を自動開始しない。とりまとめが引継ぎを確認し、後続の優先度・依存・担当指示を更新する。
- 引継ぎ文の作成・保存・提示を原則とし、別会話への自動送信・起動・常時監視は前提にしない。とりまとめの受領を確認していない場合は「引継ぎ作成済み・受領未確認」と書く。
- とりまとめも、担当完了・成果受領・統合・ユーザー受入を区別して計画へ反映する。既に同等の完了報告がある過去成果へ、形式を揃えるだけの再実装・再検査・再報告依頼は出さない。

本規則は固定の並列数上限を設けない。担当の編集範囲と依存関係を維持し、3Work以上でも依頼単位と引渡し先を明示する。
