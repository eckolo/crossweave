# crossweave — とりまとめ計画の必須同期

版：1.4／2026-09-15（日本時間）。ユーザーの「各Workの必須同期元にこのWorkの成果を必ず含ませる」という追加依頼に基づく運用規則。正式なゲーム仕様とは別の運用である。

## 1. 同期元と順序

計画の担当Workは `20260913-project-coordination`、現在の作業ブランチは `ops/project-coordination-20260913`。後継へ移る時は、プロジェクト設定・登録索引・各Work設定を合わせて更新する。ブランチ名を恒久的な最終正本とは定めない。

| 対象Work | 必須同期元と順序 | 複数またはなしの理由 |
|---|---|---|
| とりまとめ自身 | なし。自ブランチの最新HEADは取り込む | 計画を依存の上流に置き循環を避ける。設計・各専門Workの最新成果は計画更新時に必ず参考確認するが、定常のマージ元にはしない |
| 設計集約 `20260909-design-assembly` | ①とりまとめの計画範囲 | 自身が設計集約なので別の設計同期元は不要 |
| 運用 `20260909-work-routing` | ①とりまとめの計画範囲 | 作業先が設計集約と同じ。運用上の優先度・連携前提を受け取る |
| 試遊・UI・世界観・シナリオ・ビジュアル | ①とりまとめの計画範囲 → ②`dev_design_tmp_assembly`の既存の同期範囲 | 優先度・依存計画と採用仕様・共通実装の二系統が必要。計画を先に読み、現在の目標を把握してから技術前提を取り込む |
| 今後の新規Work | とりまとめを必ず含め、必要な技術同期元を続ける | 不要な技術同期元は追加しない。計画を抜く例外は通常の自動判断では設けない |

とりまとめ→設計→専門Workという依存で、専門Workは計画も直接取得する。設計集約への取り込み待ちで計画が古くなることを避ける。専門Work側から設計へ成果を渡す既存の統合担当は維持する。

## 2. 計画の同期範囲

必須取り込みの対象は、とりまとめブランチの **`docs/作業資料/とりまとめ/` 全体（配下のフォルダを含む）**。初回5文書、`着手指示/`の担当別プロンプトに加え、現在は`CO-01_実装基準.md`も含む。前回の固定ファイル一覧に限定せず、取得した最新ツリーの全対象を照合する。

この範囲を自Workブランチの同じパスへ保存する。参照リンクを置くだけ、fetchするだけ、古い受領記録を残すだけでは同期完了にしない。受け取ったファイルはとりまとめ担当の同期コピーであり、各Workで独立に優先度を書き換えない。変更希望・完了報告は自Workの既存記録へ置き、とりまとめが計画へ反映する。

着手指示には、提出を確認した過去の割当も履歴として含む。ファイルが存在することだけを今回の着手指定にせず、ファイル冒頭の状態と最新Work別実施計画の「今の着手対象」を確認する。過去指示の同期は、そのタスクの再実施要求ではない。

**範囲限定の同期は、元ブランチ全体のマージではない。** とりまとめの分岐元に含まれる古いゲームコード・専門文書・別Work設定まで取り込まない。同期記録には元コミットと対象パス・blobを記し、元コミット全体を統合済み、祖先としてマージ済みとは記録しない。技術前提の取り込みは別途、設計集約から従来の方法で実施する。

計画が設計集約経由で既に同一内容になっている場合も、最新のとりまとめHEADで対象全体を照合し、同一なら追加コピー不要と記録する。二番目の設計同期で古い計画が戻った場合は、最後に最新の計画範囲を再照合・復元する。各Work固有の設計判断を機械的に破棄して整合させない。

## 3. 作業開始・再開時

1. 自Work・とりまとめ・必要な技術同期元の最新HEADを取得し、未保存変更を保全する。固定された試遊のコミット・入力は変更しない。
2. 最新とりまとめHEADを固定し、計画フォルダ全体のツリー・ファイルを読む。前回の受領記録と比較する。
3. 変更・追加された計画ファイルを自ブランチへ反映し、元のblobまたは内容ハッシュと照合する。削除・移設があれば、独自の未保全差分がないことを確認して計画側の移行指示に従う。
4. 自Workのマイルストーン・優先タスク・前提・受け渡し条件・最大2Workの着手枠を読み、自Work設定に受領版と対応タスクを記録する。全タスクの優先度表に載っていることだけで今回の着手割当とせず、Work別実施計画の現在の対象・入替条件に従う。
5. 技術同期元がある場合は最新差分を従来の手順で取り込み、README・基本設計・要検討事項・必要な検証資料を読む。最後に計画が最新受領版と一致するか再照合する。
6. 計画・技術前提が揃った範囲から本体の編集・新しい検証を始める。取得不能や実質的な競合がある場合はその影響範囲を止め、無関係な安全な作業と復旧を続ける。古い計画のまま新しい優先度を推定して進めない。

進行中の試験は元条件を固定して完了・中断を記録し、計画更新は次の試験や作業単位へ適用する。同期のために試験中の入力やセーブを差し替えない。

## 4. 成果反映前

とりまとめHEADと技術同期元を再取得する。計画の対象内容が変わった場合は取り込み直し、今回の成果の目的・統合先・優先度への影響を確認する。対象内容が同一なら、その最新HEADを確認した事実と同一内容を記録する。毎ファイル保存ごとの無条件マージは不要。

内容の不一致がなくなってから、自Workの担当差分と計画コピー・同期記録を通常保存する。GitHub上のコミットと対象内容を読み戻す。他Workの完了や仕様採用を、同期した事実だけで追加しない。

## 5. 受領記録

自Work設定へ人が読む要約を記し、照合情報を **`docs/作業資料/計画同期/<WorkID>.json`** に保存する。このフォルダは計画の配布対象外なので、各Workの受領記録を互いに上書きしない。

```json
{
  "work_id": "担当WorkID",
  "source_work_id": "20260913-project-coordination",
  "source_branch": "ops/project-coordination-20260913",
  "source_commit": "取得した最新の40桁SHA",
  "scope": "docs/作業資料/とりまとめ/",
  "mode": "scoped-file-sync",
  "files": {"対象ファイルの相対パス": "元のGit blob SHA"},
  "plan_version": "0.5",
  "task_ids": ["今回参照するCOタスクID"],
  "technical_source": "別途確認する設計同期元、または不要の理由",
  "status": "ファイル同期済み。着手・完了は別記録"
}
```

`source_commit`を書くだけでなく、対象全ファイルが一致していることを確認する。GitHub APIを使う場合も同じく、最新refと固定コミットのツリー／本文を取得して差分だけを書き込み、反映先のblobを照合する。ブランチ全体のマージをしたように親コミットを追加しない。

初回導入では、ユーザーが明示した範囲としてとりまとめWorkが各Work設定・計画コピー・受領記録を更新する。これは専門担当による計画の読了・着手を代行した記録ではない。各担当は次回開始時に最新計画を再確認し、既存の技術同期の未取り込み分も処理する。

## 6. 実施上の限界と反映先

本規則はGitHub上のプロジェクト設定・Work分担・各Work設定へ反映する。ChatGPTの設定画面への自動適用、停止中の会話の起動、常時監視、全コミットを技術的に拒否するCIを追加するものではない。各Workの開始時・成果反映前の必須手順として運用し、未同期の成果は取り込み前に同期・影響確認を行う。

2026-09-13に、ユーザーからChatGPTプロジェクト設定へ反映済みとの報告を受領した。これはユーザーの適用報告であり、本Workが設定画面を読み戻した記録ではない。計画の更新は同期元ブランチへ保存し、受領側の次回再開・成果反映前の同期で取り込む。受領済み・着手済みとは先取りしない。
