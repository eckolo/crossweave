## 1. とりまとめWorkが管轄すること

- ゲーム作成までのマイルストーン、優先度、依存関係、達成を判断する証拠を管理する。
- 現在の目標に必要な仕事へ各Workのタスクを並べ替え、成果物・担当・受け渡し条件を具体化する。
- 仕様決定、機能実装、画面への接続、人による評価のどこで止まっているかを区別する。
- 新しい課題が出たら、現在の目標に必要か、後の段階でよいか、独立して深める候補かを判定する。
- ユーザー判断が必要なときは、既存の判断を再質問せず、未決部分の具体案・推奨理由・影響をまとめる。

各分野の原本と共通エンジンは既存担当が更新する。とりまとめは各Workの実行順を設定するが、専門担当の採用判断・原記録・実装の所有権を引き取らない。追加のユーザー指示に基づき、全Workは本ブランチの計画成果を必須同期する。設計・コードの既存同期も維持し、[計画同期手順](計画同期手順.md)で対象範囲と順序を定める。

## 4. 今回の目標M1の範囲

初回題材は既に試遊依頼のあるSCN-001／夜潮の排水路を使う。未解決の再挑戦と解決後の再訪を区別し、後者は既存の「管理用連絡路の確認」案から最小の内容を具体化する。新しい全編シナリオや地図システムの採用を前提にしない。

| 段階 | M1で必要なこと | 既存材料・追加が必要なこと |
|---|---|---|
| 準備 | 探索先・既知情報と、札／心得の取得可能・所持・編成を確認し変更できる | 了承済み統一画面へ実状態を接続。初期／後日入手の操作を共通化し、確認用編成で出発成功にしない |
| 探索 | 正式探索UIを継承し、環境への進展、任意の相手、借り札、進退を判断できる | PT-NT-001の一往復を固定参照。共通演算へ接続する差分を記録 |
| 帰還 | 踏破・撤退・緊急脱出の持帰り／喪失、知識、解放、所持を区別する | 再表示や再読込で成果を二重加算しない。本文閲覧で回復・報酬を増やさない |
| 成長・取得 | 取得予定の追加・取り外し・取消・編成を未決済で確認し、一括確定する。正式取得した心得を追加の種類習得なしで編成できる | CO-D03Rで旧D03との差分、数量・個体・価格・変換・ロック・候補・旧保存移行を整合。取得前取消は返金と分ける。UI案の固定金額を採用値にしない |
| 次の探索 | 帰還後の変更が次の出発へ反映され、恒久成果・知識・案件状態が残る | 新しい出発の手札・場と、前回の恒久成果を区別。新規ゲームの初期化を流用しない |
| 中断と再開 | 探索の途中中断から再開する。拠点の札組・心得は確定時に自動保存し、次回は保存済み状態を開く | ユーザーの0.11訂正を優先。未確定編集の中断保存を新たな必須操作にせず、旧版の保存済み案は保全する。実IndexedDBでの確認は未了 |

実行は小さく分ける。**途中到達A**は帰還成果・習得・編成変更を次へ持ち越す接続確認、**途中到達B**は取得個体・修飾・購入・変換までを同じ状態へ接続したM1候補。Aは早く触れる中間版として提示できるが、Bを終える前にM1全体を完成扱いにしない。価格等の理由で自然な初回に使えない機能は、別の固定検証状態で機能を確認し、初回へ報酬を水増ししない。

M1の受入では、正常な一巡に加え、保護前後の撤退、緊急脱出、実行不可の準備、帰還と購入等の再適用、保存再開を確認する。人には「帰還後に何を変え、それが次の探索でどう役立ったか」「途中で対象や進退を選び直す理由が分かったか」を主に確かめる。技術的な接続合格と、人の理解・面白さの評価を別欄で残す。

## 5. 優先度と作業の調整

| 優先度 | 意味 | 今回の扱い |
|---|---|---|
| P0 | M1の接続・進行・保存を止める、または複数Workの前提になる | 共通状態と実適用の条件、案件状態・再訪データ、成長UIと本体接続を先行 |
| P1 | M1の判断・識別を成立させる、またはM2の評価に直結する | 必要な用語と短文、実表示用素材、現在の試遊観察、判断負担や反復への対処 |
| P2 | 後段の完成に必要だがM1を止めない | 別探索先の本格展開、全30単位の残りUI、全編の進行・素材・仕上げ |
| P3 | 直近の完成条件から独立した比較・設定候補 | 世界観の広い案出し、未使用素材や演出の追加比較。必要となれば昇格 |

着手枠を割り当てられたWorkは、指定されたP0/P1成果を一つ受け渡せる単位で仕上げる。前提待ちの場合は、同じ割当範囲で独立して進められる部分を完成させる。待ちしか残らなければ保存して枠を空ける。新しいWorkや別タスクへ自動的に広げず、次の割当へ引き継ぐ。

設定の深掘り・広い案出しも後続タスクとして維持し、現在の目標への必要性・前提の充足・確認負荷で着手順を決める。並列数自体を目標にせず、1Workでも3Work以上でも、独立して進められる成果の組合せを選ぶ。新案を必須機能へ自動昇格させない。

## 6. 受け渡しと計画の更新

本計画はユーザーが委任した優先度設定として保存する。**計画登録／担当の受領／着手／成果提出／接続済み／確認済み**を分ける。今回、他の会話やWorkを起動したり、担当が受領したことにしたりしない。

各Workは開始・再開時と成果反映前に、計画同期手順に従って最新の計画成果を自ブランチへ取り込み、自分の行を確認する。次の情報を自Workの既存記録に残す。とりまとめは次の作業単位でその記録を読み、実施計画を更新する。常時監視やユーザーによる所感の毎回の転記を前提にしない。

1. 対象タスクID、着手または待ちの状態、満たしていない依存。
2. 成果コミットとファイル、使った仕様・コード・入力の版。
3. 完了した範囲、仮置き、試験と人の所感、未確認事項。
4. 次の担当が接続できる入力・出力と、既存成果への影響。

追加タスクは必ず「どのマイルストーンに必要か／何を解除するか／誰が受け取るか」を付ける。内容・素材を整える場合は、仮入力による最小の障害解消か、正式採用を目指す対象への投資かを示し、対象・根拠・終了条件を絞る。目標に影響しない深掘りは後段へ置く。進行不能や重大な解釈違いが見つかった場合は優先度を変更し、理由を記録する。仕様の正式採用は引き続きユーザー判断とし、タスクの着手・保存とは分ける。
