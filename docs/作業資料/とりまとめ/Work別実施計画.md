## 3. 実施順と引き渡す単位

### 枠の運用

- 最大2Workには、とりまとめ・運用・臨時レビューを行うWorkも含める。現在の計画作成を終えてから最初の2Workを開始する。人が既存試遊を遊ぶ行為自体はWorkの実作業に数えず、試遊Workが記録・分析を行う時には1枠を割り当てる。
- 指定した成果を保存・確認・報告したWorkは今回の単位を終了し、枠を空ける。続けて別タスクへ進む場合は次の割当を確認する。前提待ちだけが残った場合も、内容・不足入力を保存して枠を空ける。
- 今回の2Workも、もう一方の完了を待たずに成果を提出できる。UIは提出済みCO-D01を境界として操作を具体化し、設計は提出済みCO-S01と接続条件の対応を揃える。CO-01Aが未提出でもUIの提出を止めず、最終適合をCO-01へ残す。
- CO-01Aは既存CO-01の設計側の先行分であり、新しいゲーム機能ではない。D01とS01が相互未照合で提出されたため、UI待ちにせず実装前の不足を解消する。CO-01全体・CO-D02/D03の依存は維持する。2枠を埋めるためだけに別の深掘りを始めない。
- 現在稼働中の別会話は自動確認・停止していない。実際の開始時は、既に動いているWorkの終了・中断の区切りと合わせて総数を2以下にする。

### M1までの順序

日付の約束ではなく、成果が揃った時に進む順序。後段の担当への指示は、その時点の最新会話・原本・不足に合わせて具体化する。

世界観・ビジュアル・現在の試遊CO-P01・運用は、今の2Workへ追加して常時並行させない。M1を止める具体的な不足が出たら、終了または保存して中断した枠へ割り当てる。2Workが稼働中にとりまとめが実質的な受入・再計画を行う場合も、先に1枠を空ける。

### 受け渡し時に守る境界

CO-D01の提出で、AU系統を接続元にする案、単一CampaignController、公開view、操作・拒否・保存の契約例が揃った。新runtimeは未実装。CO-S01は3モードと具体ID・札・成果を提出したが、両者は相互の最終成果を未照合である。CO-01Aでは既存の記述を繰り返さず、対応が未定の入力を決め、根拠・試行版・残るUI接点を保存する。

UI-F-001 v0.1の「解放札を次の無料準備へ追加する」表示例は、継続本体のAUに基づく「解放→候補→購入した個体→持込」と異なる。CO-U01では解放だけを持込可能にしない。UIはCO-D01の公開viewと明示操作を用い、正式探索UIの画面を全体から作り直さない。実行・保存の本体接続はCO-U02へ残す。

実装選択と差替え可能な試行値は担当が記録して進められる。全数値や全画面の正式採用をCO-01の前提にしない。CO-01Aで契約変更が必要になった場合は理由・影響項目・変更案を明記し、先行中のUIを受領済み・修正済みにせずCO-01で確認する。

実装統合は設計集約Workが担当する。専用UI部品・シナリオ・画像は各担当ブランチへ保存し、設計が指定成果を受け取る。試遊Workに独自のプロフィールや経済を増設させない。途中到達Aは早い確認用として提示し、未接続の取得・変換を完成済みにはしない。数値比較用の機械方策をプレイヤーの推奨選択へ流用しない。

CO-D04では正常な探索に加え、保護前後の撤退・緊急脱出・失敗する準備操作・帰還や取得の二重適用・拠点／探索中の保存再開を確認する。BEは限定3局面の表示資料として使う。PT-NT-001と過去の比較結果を保全し、新しい接続版には別の固定試験IDを用いる。人への確認は全ルートの再走や既回答の取り直しを一律に要求しない。
