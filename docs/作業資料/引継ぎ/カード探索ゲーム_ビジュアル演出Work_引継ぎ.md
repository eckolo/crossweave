## 依頼

GitHub `eckolo/crossweave` の「ビジュアル・演出設計」を担当する新しい独立Workを開始してほしい。採用済みの世界観を基に、どんな絵・空間・動きとして体験させるかを比較し、ユーザーと具体化する。

最初は方向の異なる2〜3案を、同じ題材で比較できる形にする。文章の方針だけで終えず、小さな視覚見本や連続する場面の見本へ進めてほしい。通常の調査・仮案・保存は自律的に進め、画風などの正式採用は比較材料を揃えてユーザーの判断として記録する。

## 引き継ぐ世界と表現の意味

- 不思議が一見見えない日常の町を拠点に、その裏からつながる数多の異界を旅し、日常へ帰る。旅先には住人の暮らしと来歴がある。
- 主人公の職業は **辿り屋**。異変の筋道を辿り、奥でしか得られない事実や行えない対応へ到達する。未知を探索できる専門性そのものが仕事になる。
- 怪異・夢・物語・魔法・遺構などから、不思議の概念や働きを取り込み、**具体的な道具にして札の形で持ち運べる**。由来は例示で、閉じた分類ではない。
- 「札を畳む／開く」という所作、材質、道具展開の詳細は案。複数の表現を比較してよい。「札」という語だけで和風の護符や和紙へ固定しない。
- 「ひと息の休息」という水筒、「綻び縫い」という針があってよい。道具の形と呼び名を分け、種類名を必須にしない。具体物も由来と作用に照らして評価する。
- 中心は探索と突破。数量は **突破・探査・身構・攪乱・機転**、状態は **隠蔽**、会心相当の事象は **一閃**。一閃は現行正式名だが、斬撃の演出に限定する意味ではない。
- 探査は有効な箇所・機会を捉え、突破は進展を生む。身構は押しとどめ、攪乱は避ける・惑わす・隠れる働き。隠蔽のリセットで、既に得た知識まで忘れたようには描かない。
- HP相当の表示名は主体ごとの設定で、未設定時は **余力**。道なら **道のり**、障害物なら **耐久**が例。道のりは進むと減る残量。行動名も対象側に持たせ、攻撃・進む・壊す・探すなどを使う。表示名と行動名は独立している。
- 属性は不思議の由来より、働きの性質を軸にする。流動・重圧・変容・境界という現行語を確認し、四種類が永久の上限、内部A〜Dとの対応が名称だけで決まる、と推定しない。

## 初回の成果

### A. 表現方向の比較

2〜3方向それぞれについて、絵の密度、材質、光と色、空間の奥行き、主人公の見せ方、不思議の現れ方を具体化する。単なる色違いにせず、同じ場面で何を感じるかの違いを示す。個人開発で素材を追加・修正し続けられる作り方も比較軸に含める。

題材の第一候補は「日常の小さな仕事場」「乾いた深海（WB-LOC-002）」「遠雷の鋳造所（WB-LOC-006）」。異なる性質を比較するための例であり、採用済みの舞台や必須の三地点ではない。初回は各方向の小さな見本を作り、広げる前に違いを評価できる量へ留める。

### B. 札と道具、行動の見本

既存DBから性質の異なる札を少数選び、名称・不思議の由来・具体的な道具の形を添えた見本を作る。携行中／使うとき／使った後の関係を比較する。

探査・突破・一閃を、敵だけでなく道や障害物でも表す短い場面案を作る。音は必要なら方向を添える。長さ・反復時の負担・どの対象へ作用したかの読み取りを評価し、演出だけで新しい追加行動や計算規則を採用しない。

### C. UIへ渡す表現条件

背景の密度、対象の輪郭、選択状態、札と道具の対応、属性の識別など、UIと共存する条件を整理する。UI側は背景による場所感と情報の削減を重視している。配置・操作・予測情報の設計は既存UI Workが担当するので、必要な変更は接続案として記録する。

初回成果には、各案の魅力・弱点・制作上の見通し、推奨案と理由、世界観側の回答が必要な点を添える。未決定部分は仮置きの範囲を示して比較を続け、全設定の完成を待たない。

## Work設定と保存先

開始時に同じ仕事の登録・明示的な後継がないか確認する。同一作業の引き継ぎなら既存WorkIDとブランチを継承する。新規なら、確認した設計集約の最新HEADから `design/visual-direction-YYYYMMDD` を作成し、WorkIDを `YYYYMMDD-visual-direction` とする。日付は実際の開始日の日本時間。同名の別作業とは枝番等で区別する。

| 項目 | 割当 |
|---|---|
| 作業ブランチ | 上記のビジュアル・演出専用ブランチ |
| 必須同期元 | `dev_design_tmp_assembly` の1本。開始時と成果反映前に確認・必要な取込みを記録する |
| 最新版を照合する参考先 | 世界観 `design/worldbuilding-20260910` と UI `ui/readability-20260910`。開始時・成果反映前に担当資料を照合し、確認SHA・文書版・影響を記録する。ブランチ全体の必須マージは増やさない |
| 成果の統合先・担当 | `dev_design_tmp_assembly`／設計Work `20260909-design-assembly` |
| 直接更新範囲 | 新設する `docs/仕様案/ビジュアル・演出/`、`docs/作業資料/ビジュアル・演出/`、必要時の `docs/検証/ビジュアル・演出/`、自Work設定。既存の同名成果があれば担当を確認する |
| 共通文書担当 | 世界観正本・正式用語・世界観DBは世界観Work。共通設計・演算・統合は設計本筋。配置・操作・UI実装はUI Work。試遊原記録と共通運用は既存担当 |
| 設定と登録 | 実際の分岐SHA・確認HEAD等を `docs/作業資料/Work/<WorkID>.md` へ保存し、現段階の集約先 `Work分担.md` に自Workの索引行を登録する |

入口README、比較資料、見本・制作元、参照版、判断記録を分けて索引可能にする。通常文書・小規模成果はリポジトリの保存規則に従い、大型成果物は最新の外部成果物運用を確認する。

成果と採用判断は自Workに保存し、対象コミット・ファイル・受渡し先・未決定点を記録する。世界観の共通原則へ波及する提案は世界観Workへ、UI接続条件はUI Workへ渡せる資料にする。別Workが自動で起動したり会話を共有したりする前提を置かない。
