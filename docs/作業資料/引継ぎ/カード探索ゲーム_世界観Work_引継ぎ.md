# カード探索ゲーム — 世界観Workへの引継ぎ

作成：2026-09-09 UTC／2026-09-10 日本時間。作成元は設計Work `20260909-design-assembly`、保存先は `dev_design_tmp_assembly`。本書は新しいWorkの開始依頼であり、世界観Workや専用ブランチが既に開始・作成済みという記録ではない。

## 依頼

このゲームの世界観を、試作の表現に引っ張られず、自由な発想で広く検討してほしい。具体的な素材の用途や成長対象を固める前に、世界観の方向性を比較する。まず候補を出し、ユーザーとの対話で育てる。最初から一案へ確定しない。

ユーザーの指示：

> 「素材の使い道」あたりの検討に関しては、そろそろ世界観設定の検討も入れていく必要がありそう
> 現状は試作として剣寄りファンタジーっぽい感じで諸々書いているが、別に世界観設定としてそちらに寄せる必要は無い
> 例えばSFで札として「武装」を扱い巨大遺構を探索する、とか、属性を「魔法属性」と定義づけ魔法一色のゲームにしても良い
> まだ何も決まっていないため、試作の設定には引っ張られず、自由な発想で広く案を出して検討したい
> このあたり何も決まっていないので、「素材の使い道」みたいな具体的な要素を固める前に検討始めた方が良いと思う
> 恐らく別Workに分岐する感じになるか？

SFの武装・巨大遺構、魔法中心の世界は可能性を示す例であり、採用案でも候補の上限でもない。剣中心のファンタジーを候補から禁止する趣旨でもない。現在の札名・素材名・大岩・回復の表現、暫定ゲーム名から世界の方向を逆算しない。原案にも固有名詞はすべて仮案とある。

## 最初に用意する比較

最初の成果は、方向の異なる6〜8案程度の比較と、それぞれの遊びのイメージを短く説明したものとする。数を満たすための名前替えを増やさず、探索する理由、プレイヤーの立場、対象の規模、世界の成り立ち、雰囲気にも幅を持たせる。ユーザーが案を混ぜたり、別方向を指定したりできる形で提示する。

| 比較軸 | 各案で説明すること |
|---|---|
| 体験の魅力 | その世界で何をするのが面白そうか。プレイヤーが抱く期待や感情 |
| 主体と目的 | 誰として、何のために、何を探索するか |
| 札と属性 | 札は武装・術・技術・現象等の何を表すか。属性一致がどう読めるか。これらの例以外も可 |
| 共有する仕組み | 自分・敵・環境の札が場と回収山を共有し、他者由来の札も利用できることをどう表現するか |
| 探索と戦闘 | 同じ仕組みで相手と環境に対処することが、どんな行為として感じられるか |
| 成果と次の準備 | 選択式の成長ポイントと用途限定報酬が、その世界でどんな成果や成長に当たるか |
| 相性と検討点 | 既存の遊びを生かせる点、説明上の無理、仕組み側の見直しを提案したい点 |

最初から詳細な年代史、個々の武器・素材の一覧、レシピ、価格、数値バランスを埋めない。報酬は「回収した技術を次の装備選択へつなぐ」等の役割が分かる粒度で足りる。世界観から面白い遊びの着想が出たら記録し、単なる外見の置換に限定しない。実装の細かい都合だけで早期に候補を落とさず、必要なルール変更は既存仕様と区別して提案する。

## 引き継ぐ遊びの前提と、自由に考える範囲

採用仕様の正本は[基本設計](../../確定仕様/カード探索ゲーム_基本設計.md)。引継ぎ作成時点は0.43・D43。次表は発想のための要約であり、詳細な処理は正本を参照する。

| 引き継ぐ仕組み・目標 | 世界観側で検討できる表現 |
|---|---|
| 属性一致、共有の場・回収山を利用する。プレイヤー・敵・環境が札の仕組みに参加する | 属性の意味、札が何を表すか、なぜ他者由来の札を使えるか。札が世界内に物理的に存在する必要はない |
| 探索と戦闘を同じ仕組みで扱い、状況によって有効な強みを変える | 突破、解読、交渉、調整等も発想の入口になる。ただし行為の変更に伴うルール差は別途提案する |
| 初期構築の個性と、探索中に他者の札が混ざる変化を両立させる | 持参する準備と現地で利用する手段の関係 |
| 攻略で成果を得て、帰還・精算後に準備し、次の探索へ向かう | 探索場所、目的、拠点や帰還の意味、反復する理由 |
| 成長ポイント＋用途が限定された素材・札等を併用する【D43】 | ポイントや報酬の呼称・世界内での意味・成長する対象。具体用途・費用・配分は未決定 |
| 札報酬は初期構築の選択肢の解放。循環中の現物札の持帰りとは別 | 新しい手段を習得・再現・利用可能にする表現。恒久的な札の現物枚数在庫制を推定しない |
| 今回の報酬は保護と精算に従う。死亡時は今回分を失い、以前の持帰り成果は保持する | 成果の確保、撤退、失敗をどう描くか。探索中の保護を、死亡でも残る拠点への送金と同一視しない |
| 見た札の記録を保持し、初回撃破・踏破で対象の初期札構成を知る。知識は死亡・撤退でも残る【D41/D42】 | 観測、経験、解析、研究等による学習と再挑戦 |
| 消費型札は探索ごとに再セット。帰還で全回復し、次は選んだ探索先の入口から出発する | 準備の補充、回復、再出発の描写。恒久的な補充費用を追加採用したと扱わない |

大岩の局所的な攻略検討は、世界全体を岩の破壊中心にする指定ではない。環境HPや攻撃等の処理用語だけで、環境対処を必ず物理破壊と読む必要もない。現行ルールのどこまでを自然に表現できるかは比較するが、すべての処理へ長い設定上の説明を作ることを初回の完成条件にしない。

AF試行の硬質片、溜め打ち、常時軽減、数値・価格・素材とポイントの同時要求は、報酬処理をつなぐための仮例である。世界観候補の既定素材・技能・強化方式ではない。AFの再実行や全試験履歴の通読は、このWork開始の前提にしない。

## 分担と受け渡し

| 作業 | 担当 |
|---|---|
| 世界観候補、比較、ユーザーの反応・採用判断の原記録 | この引継ぎで開始する世界観Work |
| 共通の基本設計・仕様案・要検討事項・統合検討、素材用途を含む仕組みとの接続 | 設計Work `20260909-design-assembly` |
| 人の試遊と原記録、UIの情報整理・操作比較 | 登録済みの各担当Work。現在の固定試験を維持 |

設計Workは世界観の候補と関係する素材・成長対象の具体的な確定を先送りし、世界観に依存しない循環・精算・情報処理等を続ける。世界観Workは方向性の比較から始め、魅力的な候補が出たら必要な素材の役割や成長の意味を設計側へ渡す。世界設定をすべて完成してからしか相談できない段階制にはしない。

世界観による見た目の方針は、後からUI担当とも接続する。現行UI試作の外観を世界観への指定とせず、既存の表示・操作比較を待たせる理由にもしない。

別Work間で会話が自動共有される前提は置かない。採用・候補・未決定・試行例を分けた記録、対象ファイル、結果コミット、設計側への変更提案を保存する。正式な世界観方向の採用はユーザーの判断として記録し、共通仕様への反映は設計担当が行う。

## 新Workの開始手順

1. GitHub `eckolo/crossweave` の `dev_design_tmp_assembly` を入口として、最新の[README](../../../README.md)、[プロジェクト設定](../プロジェクト設定.md)、[Work分担](../Work分担.md)、本書を読む。後継先が明示されていればそちらを優先する。
2. 登録済みの同一世界観Workの明示的な引継ぎがあれば継承する。なければ新規独立作業として、確認した設計集約先の最新HEADから専用ブランチ `design/worldbuilding-YYYYMMDD` を自動作成する。日付は実際の作成日の日本時間。同名競合時は既存Workを流用せず枝番等で分ける。WorkIDも自動採番する。
3. 次表を開始設定として短く提示し、自Workの設定ファイルへ保存する。実際のHEAD・担当範囲を埋めてから本体の候補文書を編集する。集約先のWork分担索引には自Workの行だけを登録する。
4. [要検討事項](../カード探索ゲーム_要検討事項.md)の最新判断と世界観分岐の節、基本設計の関連箇所を読む。必要に応じて[統合検討](../カード探索ゲーム_統合検討.md#worldbuilding-handoff)98章、96章、関連仕様案へ進む。全履歴・全ZIP・数値試験の再計算を開始条件にしない。
5. 幅広い候補を作成して比較を提示し、自Workの作業ブランチへ保存する。仮案の通常保存のために追加確認を求めない。ユーザーが選ぶ前に一案を採用仕様へ昇格させない。

| 開始設定 | 現段階での割当 |
|---|---|
| 作業ブランチ | 上記手順で作成する世界観専用ブランチ |
| 必須同期元 | 現段階の設計集約先 `dev_design_tmp_assembly` の1本。開始時・成果反映前に最新HEADと差分を確認し、必要な取込みを記録する |
| 成果の統合先・担当 | `dev_design_tmp_assembly`、設計Work `20260909-design-assembly`。世界観Workが共通仕様へ逆方向統合しない |
| 直接更新範囲 | `docs/仕様案/世界観/世界観候補.md`、`docs/作業資料/世界観/検討記録.md`、自Workの設定。必要な世界観専用資料は同じ専用ディレクトリへ置く。既存の同名成果があればその担当を確認する |
| 共通文書の担当 | 基本設計・中心仕様案・要検討事項・統合検討・共通試験等は設計Work。README・共通運用規則は既存運用担当。試遊・UIの専用成果はそれぞれの担当を維持 |
| 設定保存先 | 自ブランチの `docs/作業資料/Work/<WorkID>.md`。集約先の索引にその所在を案内する |

運用の詳細は最新のプロジェクト設定を優先する。設計集約先への自Work登録と成果の統合を区別し、他Workの割当・固定試験・共通コードを変更しない。ブランチ名や形式的な登録の許可を聞くためだけに停止しない。
