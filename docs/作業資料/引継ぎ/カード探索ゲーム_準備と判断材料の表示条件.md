## 2. BD：本人が計画し、変わる準備を確かめる

### 2.1 APIと状態の境界

制御側で `inspect(snapshot)` を呼び、現在の未使用資源・習得支払・習得・所持・装備・未順序の札組、実候補、無料札と基礎習得の選択肢を得る。本人の選択を明示計画へまとめ、`preview(snapshot, plan)` でコピー上の結果を得る。いずれも現在の拠点または精算済み帰還の入力を対象とする。

保存済みBD結果からUIへ渡すのは、`fixtures[].display_data` または `boundary_cases[].display_data` だけ。外側の `checkpoint`、`policy_fixture`、履歴上の購入／見送り、照合用 `plan`、`summary`、`checks`、出典・ハッシュを渡さない。APIを直接使う場合も公開戻り値だけを表示側へ渡し、元snapshotやコピー中の保存状態を渡さない。

| 本人が明示する入力 | 扱い |
|---|---|
| `retain_learning`・`cancel_learning` | 現在の既習得を重複なく全て二分する。省略した基礎を自動取消しない |
| `candidate` | 現在の実候補IDまたは `null`。選択・見送りは本人の意思。候補の順位付けや自動選択をしない |
| `purchase_timing` | `before_preparation` は取消→購入→次準備。`after_preparation` は取消→次準備→購入。処理順を表示し、残額の時点を揃える |
| `next_preparation.learn` | 取消後に残る習得へ加える基礎。取消した基礎の再習得も明示し、返還と再支払を分ける |
| `next_preparation.equipment`・`deck` | 今回の装備と札組の全体。無料札は枚数分繰り返せるが、同じ所持札個体を二重に選ばない。既存APIの制限で判定する |

`owned-N`は入力snapshot内の局所handle、`base:…`は既存の無料札・基礎の選択肢、`$purchase`はこの計画で購入するコピー上の個体。画面には名称・修飾・数量を示し、handleや生UIDをプレイヤー向けの名称にしない。新しい実状態を取得したら `inspect` からhandleを作り直す。未購入の `$purchase` を購入前の準備へ入れる計画は拒否する。

比較・取消指定・候補閲覧は元状態、購入履歴、候補の組、保存データを変えない。成功もコピー上の成功であり、`performed_on_copy`を実購入完了と表示しない。実保存へ適用するAPI・処理途中の復元・実行後の再読取は未実装。本データだけで購入完了・保存完了・出発済みを作らない。

### 2.3 検討時の資金と購入直前を分ける

| BDで照合した例 | 候補検討時 | 明示取消後・購入直前 | 購入・習得後 |
|---|---|---|---|
| 0-B／8-Aの返還購入 | 未使用300、習得支払済み200 | PS02取消で200返還。購入直前は未使用500 | 400を購入へ使い未使用100。基礎習得・心得装備なし。以前の所持は維持 |
| 基礎優先 | 追加習得後に候補検討。未使用100、習得支払済み400 | 購入直前も100 | 購入なし。未使用100、習得支払済み400 |
| 0-A／8-Bの方策見送り | 取消・準備前に候補検討。未使用300、習得支払済み200 | 取消なし、購入直前300、購入なし | PS03へ200を払い、未使用100、習得支払済み400 |

この時点名は `candidate_consideration.timing/economy` と `stages.before_purchase` に対応する。既払200を最初から未使用300へ合算して「現在500使える」と表示しない。同じ最終残額100でも失う習得・装備と操作順は異なる。返還量は履歴上の実支払であり、PS02だから常に200返す実装にしない。

BCの自動方策で見送った8-Bの通常・手当 `choice-0` も、人がPS02取消・購入を明示し、無料の手当を購入個体に置き換えれば合法な札組になることをBDで確認した。`requested:null`は今回選ばなかった意味であり、購入禁止や不要品の判定ではない。基礎未習得、容量不足、今の札組に入れない、将来用に保持する、資金不足を一つの「買えない」へまとめない。

### 3.3 説明で維持する規則と公開範囲

- **設置**：主効果は起きず、札は場へ残る。一致時に使用札の主効果と適用される場効果が成立する。場に放つだけで周囲が自動回復する説明にしない。
- **手札期限**：本人の行動後、使わなかった手札だけ残期限が1減る。時刻が1進むたびに減る意味ではない。場札には手札の期限切れがない。
- **循環と消滅**：この3局面で期限0になる通常札は共有の捨て場へ移り、永久喪失ではない。回収・山札補充で誰にどう巡るか、すぐ手札に戻るかは保証しない。消耗品・消滅予定札等の例外を全通常札へ一般化せず、出現元退場時等の既存消滅処理も取り消さない。
- **現在予約**：次の自分の予約は現在時刻＋保存された行動間隔。他主体は公開済みの次回予約だけを使う。同時刻は既存規則のV→P→E、同種は主体ID順。BEが入力として対応する主体はP・V0・V1に限る。
- **予測の限界**：他主体の次札・使用対象・素材消費、後続の再予約や退場後を含む全順序、自分の次手番への到達を保証しない。「先に動く予約がある」と「場札を使うことが確定」は別。共有利用を一方的な損失とも判定しない。

旧方策の選択・理由・順位、私有札、乱数、次札順、実現した未来の行動・回収・再配分、終点・勝敗は表示へ混ぜない。照合の出典・SHA・検証結果は[BD検証記録](../../検証/構築と探索/bd/verification.json)・[BE検証記録](../../検証/構築と探索/be/verification.json)に残し、プレイヤーの選択材料とは分ける。

## 4. 操作・固定試遊と次工程

撤退は既存UIの直接実行を維持する。UI-S24の持帰り予告を必要時に参照できる方針は保つが、BD／BEを理由に毎回の強制確認窓や機械的な推奨を追加しない。S30も全操作へ確認を増やす決定ではなく、実行不可理由と戻れる範囲を具体化する対象とする。

PT-NT-001の専用40ファイルは、依頼・初期札編成→水路・任意の潜水服→港→水門→帰還という一往復。BD／BE、取得個体・修飾、心得習得・装備、購入・変換、次の出発は接続していない。試遊の新規開始による初期化を、成果を引き継ぐ帰還後の再出発へ流用しない。旧PT-Z、正式UI v0.15、PT-NTの入力・セーブ・原記録は各固定版として保つ。

次は既存のUI-PLAN-001に沿って、以下を進める。今回の表示条件の登録のために新たな採用回答は求めない。

1. UI担当は全体構成の案にBDのS08・S09・S11とS06・S07・S10・S18・S30への出入りを重ねる。可変値、空候補、見送り、取消後の装備不可、資金不足を含め、最小表示と任意詳細を具体化する。
2. BEの3局面はそれぞれ別の開始資料として、S15・S18・S20・S21・S28の説明を比較する。選択順位を付けず、現行の画面密度と操作を基準にする。
3. 実準備を保存して次の出発へつなぐ段階では、設計側が実適用の処理境界・候補の鮮度・失敗時の原状態維持・保存復元を別の版で接続する。BDのプレビュー成功をその実装完了と数えない。
4. 操作可能な別版ができたら試験ID・開始条件・元版との差分を付け、本人が失う準備、期限、循環、予約の不確実さを読めるか確認する。現時点の機械照合を人の理解・楽しさ・最適判断の評価へ代用しない。

関連する進退の確認範囲は[既存の試遊条件](カード探索ゲーム_進退と反復の試遊条件.md)を参照する。本書は共通の表示条件の引継ぎであり、各Workへの通知・UI原本への反映・新画面の採用完了を表すものではない。
