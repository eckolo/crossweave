設計Work `20260909-design-assembly` や運用Work `20260909-work-routing` の設定を、自分の試遊Workの設定として継承しないでください。同名ブランチの存在だけでも同一Workとは判断しません。

新しい独立試遊なら、次の設定で具体名を自動決定し、開始時に短く提示してください。これは作成手順であり、本引継ぎだけで試遊Workやブランチを作成済みとは扱いません。

### 2. 同期してから資料を読む

まとまった作業単位の開始時に、自Workと必須同期元の最新HEADを確認し、未保存変更を保全したうえで未取り込み差分を取り込んでください。新規分岐直後は分岐元が取り込み済みの基準ですが、索引登録などで同期元が進んだ場合は本体作業前にその差分も確認・取り込みます。確認したSHAと実際に取り込んだSHAを設定へ記録し、取得・閲覧だけで統合完了としないでください。

取り込み後の自WorkのREADMEから、次の現行資料を確認してください。

- `docs/作業資料/プロジェクト設定.md` と `docs/作業資料/コミット/GitHub移行.md`
- `docs/作業資料/Work分担.md`、自Workの設定、設計Workの設定
- `docs/確定仕様/カード探索ゲーム_基本設計.md` と `docs/仕様案/カード探索ゲーム_仕様案.md`

- 本引継ぎ文と、自Workのブランチに保存された試遊記録

他Workから取り込んだREADMEや設定に書かれた作業先を、そのまま自分の作業先にしないでください。古い仕様文書・履歴中の固定ブランチ指定より、最新のプロジェクト設定と自Workの明示的な割当を優先してください。

成果反映前にも両方のHEADを再確認し、変化があれば影響を調べ、必要な取り込み・関連箇所の再確認をしてください。ファイル保存のたびに無条件マージしたり、参考に読むだけの別Workを必須同期元に増やしたりしないでください。設計側は試遊成果を選んで統合する担当であり、設計側と試遊側を相互の必須同期元にして循環を作りません。

## 設計側の採用更新と、進行中試遊の区別

設計側はD42・基本設計0.42として初回撃破・踏破で初期構成を開示する承認を反映済みです。D40の初訪問の事前案内に続き、D41・基本設計0.41として、開示済みの敵・環境・札構成・報酬候補の知識を死亡・撤退後も保持する方針を採用しました。実際の報酬精算とは区別します。同じ可否は再質問しないでください。現在のPT-Z-001は、以下の固定版・基本設計0.39対応の追加Zを継続します。

次の情報表示の比較に使う準備資料は[統合検討86章・追加AC](../カード探索ゲーム_統合検討.md#information-ac)と試作READMEです。ACは表示用データと再現例であり、操作画面への実装はまだありません。現在の相手の観測、別の相手から得た記録、既知初期構成、自分の現在残数を分けてあります。情報処理の機械照合を、人の理解・面白さの確認済みとは扱わないでください。

別の情報試遊を用意する場合は、初見でも構築・対象選択の理由を持てるか、再構築後も既知構成を現在の相手札と混同せず選び直せるかの二点を候補にします。新しい試験IDと使用版を定め、学習用と評価用の札順を分けてください。保持方式はD41の採用済みの扱いを使います。初期構成の解放条件は[統合検討89〜90章・追加AD](../カード探索ゲーム_統合検討.md#knowledge-ad)で三案を比較し、「観測は都度残し、初回の撃破・踏破で基本構成を開く」案をD42・92章で採用済みです。三案は比較履歴として扱い、新たな接続には`first_resolution`を使ってください。実施時には最新の採用状態を確認してください。既存PT-Z-001へ追加条件を混ぜたり、この準備完了待ちで既存試遊を止めたりしないでください。

追加ADの `knowledge_results.json` には、敵を倒さず環境を踏破したL4からの、次回出発前の三案の情報データがあります。表示用は `departure_samples` です。`diagnostic` と `authored_initial_catalogues` は未公開の全体数を含む内部照合なので、直接プレイヤーへ提示しないでください。未行動の敵との遭遇記録は残りますが、未開示の構成が分かった表示にはしません。ADは操作UIを追加していません。

### 確認したいこと

1. 岩・環境の突破と後続の敵戦で、攻撃／防御の配分に応じた得意不得意が、納得できる構築の取捨選択になるか。それとも有効な選択がなく、待たされていると感じるか。
2. 山札の再構築後も、表示された札の残数・属性・効果から次を考えられるか。持込札と共有循環で得た札に応じて、攻め・防御・設置を選び直せるか。

攻撃6／防御5／回復1、8／3／1、11／0／1の3構成を選べる既存UIを使います。選択後に「この構成で入口から開始」を押した時点で反映されます。進行中の探索を構成変更で差し替えないでください。防御3枚が最適と誘導せず、全3構成の完走も必須にしないでください。

2手だけでは、消費や再構築後を見越す心理を観察できないという所感を受領済みです。通常入口から継続できる試作を使い、到達した場合は初回再構築後・後続の敵戦まで含めて確認してください。一方、退屈で途中中断したことも有効な所感です。所感が一部だけでも記録を先へ進め、全項目への回答を要求しないでください。

### 維持する条件と認識

- 初期HP60、手札3、山札12枚。どの構成も属性A4/B4/C2/D2、同名上限2、回復草1枚を維持します。
- 大岩は自身への回避支援を受けません。自身は回避0・軽減8。回避20は大岩以外の生存主体へ適用され、後続参加者も対象です。大岩退場で支援が終わります。
- 弱攻撃は威力2・命中50です。命中が少しずつ積まれるという肯定的所感を得ており、今回の比較基準を維持します。製品の永久的な採用値ではありません。
- 会心の増加量は使用札を参照します。通常札25、弱札等10、防御20・受け流し40・見切り20という現在の仮設定です。防御時は場の威力補正を防御、場の命中補正を回避へ使います。主体の恒常的な固定会心値へ戻さないでください。
- 回復草は回復16・期限16・回収時消滅。探索内の補給はありません。最初の環境は弱攻撃12枚、後続の敵は防御札も持ち込みます。初期防御0でも共有循環から防御札を得ることがあるため、持込枚数と実際の手段を区別してください。
- 大岩破壊と環境踏破の両方が報酬獲得につながり、保護は環境踏破時に獲得済み分へまとめて適用します。破壊等に細かな追加保護を新設しないでください。
- 自分の全札種の属性・効果・残数を確認できる一覧、属性ごとの場枠、最新順を既定とする履歴と順序切替を維持してください。世界の全属性や相手の非公開札を追加公開する決定はしていません。

### 受領済みの所感を踏まえる

- 相手の札が分からず設置を避け、多少無駄でも一致を優先したことがあります。設置時の場効果が見えること、負の場効果を防御的に使えることは好評でした。設置率を上げること自体を目標にしないでください。
- 敵の直近3行動だけでは山札の判断材料が不足します。既知の敵・環境への経験が役立つ可能性はありますが、札の暗記を前提にしないでください。
- 防御札の偏りによる停滞は負担です。ただし突破向けと敵戦向けで構築の得意不得意を作ること自体は、目指す方向に合います。大岩の回避支援が厄介な地形の個性を持つことも許容されています。全環境の維持／除去を等価にする方針ではありません。
- 防御札には防御量・回避・会心などの個性が求められています。会心が速く積まれ、高防御より高回避の相手が厳しかった所感もあります。現在の試行値だけでバランス解決としないでください。
- 回復1枚は存在感が薄く、非過剰なら使う、過剰かつ期限間近なら設置、という選択に寄っています。旧HP36局面や「消滅が怖くて温存するか」の再回答を求めないでください。追加評価が必要なら、回復総量・防御維持・攻撃機会との関係を別の試験として扱ってください。

引継ぎ準備時点では追加Zの3構成を選ぶ修正版の人評価は未取得でした。再開時は登録された試遊ブランチの最新記録を優先し、受領済みなら再回答を求めないでください。過去の所感とPT-Z-001の結果を分けてください。自動方策の144条件比較は、人の勝率や面白さの証明ではありません。

## 記録・修正・成果の受け渡し

所感と取得できた実経過は、**自Workの試遊専用ブランチ**の `docs/検証/試遊/terrain-build-z/試遊記録.md` へ保存してください。試験ID、基準コミット、UI等の差分コミット、実際に選ばれた構成・到達段階、ユーザーの言葉、観測、解釈、未確認点、次の候補を区別してください。操作ログがなければ未取得とし、一般的な所感から正確な手順・HP・勝敗を推定して書かないでください。

コードの保存とプレイ途中状態の保存は別です。実際に取得できた互換セーブまたは再現可能な選択列がある場合だけ、同じ途中状態から再開したと記録してください。旧Xの回復局面をZの途中セーブとして流用しないでください。

軽微な表示修正や不具合の最小修正は、自Workの試験フォルダへ基準版からの差分と再現手順を保存して進めて構いません。試遊中にHPや手札を操作して狙った感想へ誘導しないでください。仮条件を変えるときは別の試験IDにし、変更目的を記録してください。共通エンジン・基本設計・仕様案・統合検討・要検討事項への取り込みは設計Workの担当です。担当外の文書を直す必要があれば、自Work側に変更案として保存してください。

まとまった結果を保存したら、自Work設定に「統合依頼」として、送り出すブランチとコミット、対象ファイル・試験ID、分かれた基準や取り込み済み同期元SHA、確認範囲、未確認点、統合先と担当を記録してください。設計Workは登録索引をたどって試遊ブランチを取得し、結果と差分を確認して必要な成果を統合します。試遊側が設計集約へ直接成果をPushしたり、同期元へ逆方向にマージしたりしないでください。記録の保存・依頼・設計側での統合完了は別の状態です。

私が正式な採用を明示した場合は、対象と発言を記録し、設計Workで同じ判断をもう一度求めないようにしてください。試行設定や肯定的な感想だけで正式採用と解釈しないでください。

## 権限と継続

通常のファイル更新、日本語の簡潔なコミット、開始設定で定めた自Workの作業ブランチへのPush、記録付きの検証用ステータス設定は許可済みです。各Workは独立した作業コピーを使い、担当差分をまとめて反映してください。並行更新で拒否された場合は最新状態を取得し、既存変更を保全して再統合します。保存後のGitHub上のコミットと内容を照合してから完了としてください。

形式的に解消できる競合は自律的に処理してください。取り込み方向・既存担当・仕様意図に実質的な選択が残る場合は、その更新について具体案と影響を示して判断を求め、独立して進められる作業は継続してください。強制Push・公開済み履歴の書換え・master/mainへの統合・公開範囲の変更は通常権限に含みません。統合先への指定だけで確認が免除されるとは扱わないでください。

結果はGitHubを通じて設計Workが次の作業時に読み込みます。会話の自動同期・別Workの自動起動・未実施の送信を約束しないでください。通常の結果の転記を私に毎回頼む必要はありません。

試遊・所感待ちの間に進められる表示改善や再現準備は継続してください。重い設計比較をここで抱え直さず、明確な設計課題として記録してください。次の試遊候補は、防御札の役割を使い分けられるか、会心・回避への納得感、回復が他の行動と競合する場面です。必要になったものを少数ずつ扱い、すでに受領済みの判断を再質問しないでください。私の判断・操作・所感が必要な場面以外は、実施予告や保存許可待ちだけで止めず進めてください。
