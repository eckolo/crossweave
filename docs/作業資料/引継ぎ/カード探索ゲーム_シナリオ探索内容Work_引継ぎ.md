GitHub `eckolo/crossweave` の「代表案件のシナリオ・探索内容設計」を担当する新しい独立Workを開始してほしい。

採用済みの世界観と現行のゲーム進行を基に、案件を一本、依頼受領から探索・深部到達・帰還・次の準備まで具体化する。プレイヤーが何を見て、どう判断し、どんな気持ちで帰るのかが分かり、設計本筋・UI・ビジュアル担当が利用できる内容資料を作ってほしい。

## 引き継ぐ前提

- 日常の町と、裏道からつながる数多の異界を往復する。旅先には事件以外の暮らしと歴史があり、不思議の起源を一種類へ集約しない。
- 主人公は **辿り屋**。主軸は異変の調査と必要な対応で、奥へ到達する積極的な理由を置く。踏査・取材・回収は副目的にもできる。
- 出発時に分かるのは症状・場所・大まかな見通し。真相や解法、特定の不思議の入手先を最初から知る依頼へ固定しない。具体的な調達は発見後の目的として使える。
- 不思議の概念や働きを具体的な道具にし、札の形で携行できる。元の存在への影響、譲渡、能力の起源、展開の所作等は共通設定の未決定事項。案件固有の仮案を世界全体の法則にしない。
- 主軸は探索と突破。札・場・捨て場の共有、他者由来の札の利用、出現元と消滅、手札期限などは現行設計に従う。借り札の利用を不可能にしたり、供給元の除去を常に正解にしたりする前提を置かない。
- 正式数量名は **突破・探査・身構・攪乱・機転**、状態は **隠蔽**、事象は **一閃**。対象のHP相当表示名は主体別、未設定時は **余力**。道の **道のり**、障害物の **耐久**は例で、道のりは減る残量。行動名も主体ごとに独立設定し、攻撃・進む・壊す・探す等を用いる。
- 一つの世界、一つの探索先、一回の探索、一件の案件、対象の残量0を区別する。A〜Eは比較例でゲーム総量ではない。世界の境目を越えるだけで回復・精算したことにしない。
- 帰還・撤退・死亡、成果と調査記録の保持は本筋の規則に従う。物語上の見せ方は仮案として比較できるが、喪失や再開の処理を文章だけで変更しない。

## 初回成果：一本を通した内容案

### 1. 案件選定と全体の流れ

候補を「奥へ進む必要」「未知を調べる楽しさ」「現地の判断」「帰還後に残るもの」「既存仕様への接続」で比較する。仮選定した案件について、依頼受領→入口→道中の区切り→深部→帰還→次の準備を通して書く。解決後の再訪例も一つ置く。

一本道の会話だけでなく、何が見えて何を選べるかを各場面に示す。進行上の分岐を使う場合は、既存の選択・順序で表せるものか、新機能が必要かを分ける。

### 2. 場面・行動主体・札・心得の対応

| 内容 | 最低限記すもの |
|---|---|
| 場面 | 入る条件、最初に見えるもの、得られる手掛かり、判断、進展、次へ残る状態 |
| 行動主体 | 名称、環境・敵・オブジェクト等の役割、立ち塞がる事情、行動名、残量表示名、残量0で起きること |
| 共存する対象 | 何が並行して残り、何の札・作用を供給するか。除去／残置が後の判断へどう関わるか |
| 札 | 参照WB-IDまたは新規案ID、不思議の由来、具体的な道具の形、名称、探索中の役割、出現元・共有・消滅との対応 |
| 心得 | 何を経験して身につく作法か、既存の効果方向との関係。習得・所持・今回の装備を区別する |
| 成果 | 進行解放、調査記録、習得・取得資源、所持個体などの役割と、確定する時点 |

数値が必要なら固定した本筋条件から参照するか、仮値と出典を明示する。数値・効果・候補数を世界観上の都合で正式決定しない。成立させたい面白い作用が現行仕様で表せなければ、変更提案として残す。

### 3. 実際に読む短い本文

依頼文、到着時の描写、手掛かり、対象の詳細、帰還後の会話を少数ずつ書く。本文・任意詳細・設計者向け説明を分け、設定の説明で毎回の行動を止めない。UIでの配置・開閉操作はUI担当に渡す。

主人公の口調や経歴、事務所の人物が必要なら案件用の仮案と明示する。主人公が固定人物かプレイヤーに委ねる人物かは世界観側の検討事項として残し、差し替え可能にする。

### 4. 接続確認と受け渡し

依頼の症状から手掛かりを辿れるか、危険を冒して奥へ進む理由があるか、得た手段が次の判断へつながるかを通して点検する。敵・道・障害物の違いが名称の置換だけになっていないかも見る。

「既存仕様で接続できる」「既存の未採用案に依存」「新機能の提案」「描写のみ」を区別した対応表と、必要な背景・対象・札・演出の一覧を作る。資料上の確認と、実装・試遊・面白さの確認を分けて報告する。初回は本筋コードへの実装や全編シナリオを完成条件にしない。

## Work設定と保存先

開始時に同じ仕事の登録・明示的な後継がないか確認する。同一作業の引き継ぎなら既存WorkIDとブランチを継承する。新規なら、確認した設計集約の最新HEADから `design/scenario-content-YYYYMMDD` を作成し、WorkIDを `YYYYMMDD-scenario-content` とする。日付は実際の開始日の日本時間。同名の別作業とは枝番等で区別する。

| 項目 | 割当 |
|---|---|
| 作業ブランチ | 上記のシナリオ・探索内容専用ブランチ |
| 必須同期元 | `dev_design_tmp_assembly` の1本。開始時と成果反映前に確認・必要な取込みを記録する |
| 最新版を照合する参考先 | 世界観 `design/worldbuilding-20260910`、UI `ui/readability-20260910`、開始済みなら登録索引で見つけたビジュアルWork。確認SHA・文書版・影響を記録し、循環する必須マージを作らない |
| 成果の統合先・担当 | `dev_design_tmp_assembly`／設計Work `20260909-design-assembly` |
| 直接更新範囲 | 新設する `docs/仕様案/シナリオ・探索内容/`、`docs/作業資料/シナリオ・探索内容/`、必要時の `docs/検証/シナリオ・探索内容/`、自Work設定。既存の同名成果があれば担当を確認する |
| 共通文書担当 | 世界観正本・正式用語・世界観DBは世界観Work。ゲーム進行・計算・共通エンジン・数値検証は設計本筋。UIと試遊の専用成果・共通運用は既存担当。画風・演出の比較はビジュアルWork |
| 設定と登録 | 実際の分岐SHA・確認HEAD等を `docs/作業資料/Work/<WorkID>.md` へ保存し、現段階の集約先 `Work分担.md` に自Workの索引行を登録する |

専用フォルダに入口READMEを置き、案件IDごとの概要、場面、対象、札・心得との対応、本文、依存事項を分ける。既存WB-IDは維持し、DB本文を複製して独立更新せず、参照と案件固有の差分を管理する。新しい汎用素材案は自Work側に案IDを付けて保存し、世界観DBへの収録案として渡す。

未決定の共通設定は複数案や仮置きで進められる範囲を進める。成果は対象コミット・ファイル・仮設定・各担当への接続事項を記録し、世界観側には共通原則の提案、ビジュアル側には素材要求、UI側には表示すべき内容を渡せる形にする。Work間の会話や自動起動は前提にしない。
