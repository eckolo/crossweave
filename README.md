## 更新するとき

1. 正式な仕様・目指す遊び方の変更はユーザーへ確認する。試行仮設定は、目的・条件・維持前提・範囲・結果・限界を記録して個別確認なしに進めてよい。検証用の仮ステータスもこの扱いで設定してよく、設定のためだけに判断を仰がない。要検討項目が残る間は1項目ごとに停止せず、関連する検討・記録・更新を続ける。停止はユーザーの採用判断や意図確認が必要な場面に限り、必要な理由と具体案を先に用意する（2026-09-08の最新継続指示）。
2. 採用した内容は基本設計へ反映し、仕様案・要検討事項の状態と参照先も更新する。検証結果だけを理由に正式採用へ昇格させない。
3. 過去の判断理由・試験結果は記録として残す。変更された古い判断を、現在の判断待ちとして再提示しない。
4. ファイル名は固定する。設計版は文書内で管理し、版番号付きの同種ファイルを増やさない。
5. リポジトリ内資料は相対リンクにする。Dropbox専用ZIPはGitHub上の外部成果物一覧へのリンクにし、実体がGitHubにあると誤認させない。
6. 保存先は情報区分で選ぶ。新しい検証分野や実装資料が増えるまでは、既存区分を優先して使う。
7. 通常の検討・検証・実装に伴うファイル更新と、日本語メッセージによるコミット・対象作業ブランチへのPushは逐一確認なしに進めてよい。現在の作業ブランチは `dev_design_tmp_assembly`。関連差分を意味のある単位にまとめ、更新直前のHEADを確認して他の変更を上書きしない。GitHubに反映されたコミットと内容を照合して保存完了とする。Git記録と正式仕様の採用は別に扱う。
8. Dropboxは外部成果物一覧で指定された大型ZIPの保存に用いる。通常の設計文書やローカルの `.git` をDropbox連携で書き換えない。外部成果物の更新は元ファイルを保全し、利用中のツールの権限・確認条件に従う。保存失敗を成功と扱わず、元の正本を破壊する回避策を取らない。
